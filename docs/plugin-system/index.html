插件机制审视

后续：第二轮审视（2026-11-04），这页里 G7 的结论和「多版本索引」已被它更新。

2026-11-03 · 把 Mooring 的插件机制和 12 个产品对照（文末附 DeepSeek Harness 一节）：同类 Agent 工作台（下文称 H，它有终端版插件和桌面版 mods 两套）、Zellij、WezTerm、tmux、Kitty、Warp、VS Code、Zed、Raycast、Obsidian、Claude Code。Mooring 部分读的是当前 main（70deadd）的源码，并在本机实跑核对过；别家来自官方文档、源码和 issue，链接列在文末。

这页要支撑的决定

插件机制下一步改什么、按什么顺序改。每条建议都标了结论：采用是建议做，待验证是先确认有真实需要再定，不做是看过别家之后决定不跟。

放弃条件：一项改动如果不能让现有某个插件（claude-quota、notify-macos、pane-facts、common-actions）写得更简单、更安全或者更好排查，就不做，哪怕别家都有。

结论

  1. 总体路线是对的，不用推倒。Mooring 的写法是「声明式 JSON + 子进程跑 shell 命令 + 插件画不了界面，由宿主来画」。这和 H 的终端版插件、Claude Code 插件同属一类，也是三类做法里门槛最低、最难把 App 搞崩的一类：另外两类是 VS Code、Obsidian、H 桌面版那样的进程内代码，以及 Zellij 那样只能用 WASM。另外，有两件事 Mooring 比别家做得好：
    • 可逆的 setup / teardown。11 家里没有一家提供「装上时改别的程序、卸载时改回来」的声明式钩子。H 的社区插件只能在 README 里让用户再手动跑一次 setup，忘了跑就以为没装好，这是它们最常见的抱怨。
    • 插件不画界面。完成动画、左栏、额度这几类都只提交数据，由宿主统一画，所以主题和深浅色不会被插件弄乱。H 桌面版走的是反方向，让插件自己画，结果已经出现性能问题（issue #88）。
  2. 有 4 个问题现在就该修。其中 3 个是这次核对时找到的真 bug，1 个是文档过期，见第三节的 B1 到 B4。
  3. 还有 5 处机制短板，都有别家的现成做法可以照抄。按重要程度：
    • 插件和 App 的版本不配套时会出问题；
    • 传给插件命令的上下文，每种类型给法都不一样；
    • 插件没有自己的设置项；
    • 插件命令跑没跑、报了什么错，在 App 里看不到；
    • 安装前的说明只按插件类型笼统地写，没说具体会动哪些文件、会不会联网。
    这五项都不涉及大改，排期见第五节。
  4. 不跟的做法：让插件在 App 进程里跑代码、每种类型都改成 WASM、靠人工审核来把关插件市场、第三方插件自动更新。理由见第四节。

一、Mooring 现在有什么

一个插件就是 ~/.config/mooring/plugins/<id>/ 下的一个目录。plugin.json 写明它提供哪几类，每类对应一个固定文件名，可以同时提供多类。加载时一个插件出错不影响别的插件，每份文件的加载结果都会显示在 设置 › 插件 › 声明文件明细 里。

三、这次核对找到的问题

编号问题证据后果严重度结论
B1在设置页卸载、开关插件时，setup / teardown 在主线程上同步运行settings/plugins.rs 的 uninstall 直接调用 plugin::uninstall，开关调用 plugin::set_enabled，两者都会跑 setup::run，超时上限 30 秒；市场安装走的是后台线程插件的脚本一慢，整个窗口就卡住。claude-quota 的 JXA 脚本大约要 0.2 秒，还不明显高采用：和安装一样放到后台，界面显示「正在卸载…」
B2mooring 命令在终端外默认去 mooring-workbench 找后台，没有走改名后的兼容逻辑control.rs:166-172 写死了路径，没调 legacy::runtime_dir。本机实跑 env -u MOORING_RUNTIME mooring list 报 RPC connect: No such file从 Keepline 升级上来的机器上，hook、窗格装饰、quota 命令和外部脚本调 mooring list/read/send 都会失败。「整个 CLI 就是插件 API」这条路在这些机器上走不通高采用：改成 legacy::runtime_dir，同时给所有插件命令传 MOORING_RUNTIME（见 G2）
B3文档过期market.rs 开头还写着「安装时不运行任何东西」，但现在装上就会跑 setup；plugin.rs 开头还写着「目前只有 agent，actions 等以后做」；旧规格稿 specs/plugins/plugin-system.md 只在老仓库里，见重复来源清单 M8照着注释写插件、做安全判断的人会被误导中采用：一并改掉，并把规格稿搬进本仓库 docs/
B4旧 App 遇到不认识的插件类型，会拒掉整个插件Kind 是 serde 枚举，Manifest 又设了 deny_unknown_fields。现在本机运行中的旧 App 就把 claude-quota 判成坏插件只要发布新的插件类型，没更新 App 的用户就会看到报错，而且他们装着的插件里能用的部分也一起失效中采用：见 G1

四、机制上的短板，以及别家的做法

编号短板别家怎么做建议结论
G1版本兼容：不能声明最低 App 版本；旧 App 遇到不认识的类型或字段，会拒掉整个插件H 写 最低宿主版本字段，VS Code 写 engines；Obsidian 的 versions.json 让旧 App 拿到兼容的旧版插件；Claude Code 对未知字段只警告plugin.json 加 "mooring": ">=0.x"，市场里不列不满足的插件；不认识的类型只警告并跳过，其余类型照常加载采用
G2每类插件拿到的上下文都不一样：actions 用模板，hooks 用 stdin 加环境变量，decorations 只有环境变量，setup 和 quota 用 PLUGIN_DIR/DATA。没有哪一类拿得到 mooring 程序的路径和后台位置，脚本也找不到自己插件目录里的文件H 给所有命令统一传 BIN_PATH、SOCKET_PATH、PLUGIN_{ID,ROOT,CONFIG_DIR,STATE_DIR}，外加 CONTEXT_JSON每条插件命令都统一带上 MOORING_PLUGIN_ID/DIR/DATA、MOORING_BIN、MOORING_RUNTIME、MOORING_CONTEXT_JSON；各类型现有的变量保留。这样 notify-macos 能读自己的设置，装饰脚本也能调 mooring采用
G3插件没有自己的设置项：notify-macos 想只在出错时通知、quota 想改刷新间隔，现在只能改插件文件，而一更新就被覆盖Claude Code 的 userConfig、Raycast 的 preferences、VS Code 的 configuration：写一份 schema，界面自动生成；敏感值进钥匙串；用环境变量传给命令，不往 shell 命令里插值plugin.json 加 options（字符串、数字、开关、单选，可以标敏感），设置页在每个插件下面生成表单，值存进 plugin-data/<id>/options.json，以 MOORING_OPTION_<KEY> 传给命令待验证：先确认至少两个插件真用得上
G4看不到插件运行的结果：hook 的结果只写在后台日志里，装饰和 quota 命令失败时什么都不显示，setup 的报错只在点按钮那一下出现H 有 plugin log list（命令、退出码、截断的输出）；H 桌面版出错时继续跑旧版，错误写在 status 里；Claude Code 有 Errors 页每个插件保留最近 20 次运行记录（哪类、退出码、耗时、输出前 300 字），在设置页的插件行展开查看；命令行加 mooring plugins log <id>采用
G5安装前的说明太笼统：只按类型写「会跑命令」「会改别的程序」，没说具体动哪个文件、会不会联网H 安装前列出要跑的全部命令；Zed 声明能跑哪些程序、从哪里下载；H 桌面版要求说明会不会联网、会不会读插件目录以外的文件setup 类加 touches（会改哪些外部文件，比如 ~/.claude/settings.json），quota 和 hooks 加 network: true/false，安装确认时列出来。只做展示，不强制拦截采用（小）
G6卸载后数据目录一直留着Claude Code 卸载时默认删，加 --keep-data 保留；Zellij 也删teardown 成功后删除；teardown 不成功（比如里面还存着原设置的备份）就保留，并在提示里说明采用（小）
G7插件命令继承 App 的环境：用干净环境启动 App 时 PATH 里只有系统目录，node、python3 都找不到（旧规格稿第 8 步已经记过这个缺口）H 用 argv 数组，并明确写出给插件的环境；VS Code 远程宿主会读取登录 shell 的环境App 启动时用登录 shell 解析一次 PATH，传给插件命令；文档写明这一点待验证：先查哪个插件真被这个问题绊倒过
G8改了 agent 类插件要重启后台H 装新版本到新目录，旧进程继续用旧版；Claude Code 正在跑的会话继续用旧版，/reload 才换暂不改：agent 插件很少，而且页面上已经写明不改
G9插件只能被动地等宿主来要数据：装饰和 quota 都是宿主去拉，插件不能自己往界面上推一个值H 用 report-metadata --token NAME=VALUE --ttl-ms 推送具名值，怎么显示由用户配置决定等有真实需要再做；quota 的「文件变了就重读」已经能覆盖推送这种用法不做（现在）

看过之后决定不跟的做法

  • 插件在 App 进程里跑代码（H 桌面版、Obsidian）：H 桌面版热重载 85 次后，旧代码都留在共享的 JS 上下文里，渲染慢到 0.4–1.4 秒（#88）；Obsidian 官方明说「没有权限系统」。Mooring 是 GPUI 原生 App，一旦在进程内跑插件代码，就等于把卡顿和崩溃的风险交给第三方。
  • 每种类型都改成 WASM（Zellij、Zed）：门槛太高，只有 Rust 好写，Zed 的审核还要积压几周。WASM 只留在左栏这类真需要写逻辑的地方，和原规格稿的定位一致。
  • 靠人工审核把关插件市场：现在没有第三方作者，没必要。等出现了，先学 H 的做法，在市场上标「未经审核」。
  • 第三方插件自动更新：VS Code 的 GlassWorm 事件就是靠自动更新扩散的。Claude Code 只对官方市场默认开自动更新，Mooring 保持手动。
  • 多种合并规则、多层启用优先级（Claude Code）：它为此要专门写排查文档。Mooring 维持现在这一种：插件只追加，不覆盖内置。
  • 授权只按 URL 记（Zellij）：将来要做授权，应该绑定文件的 sha256。

附：DeepSeek Harness（DSH）怎么做

读的是 deepseek-ai/deepseek-harness 当前默认分支的文档：architecture、capability-seams、user/develop、plugin-manager 的 README、SAFETY；生态数字来自本机的 dsh-plugin 索引站（已发布 5808 个，另有 2767 个因为清单不合格被拒）。

方面DSH和 Mooring 比
定位「一切皆插件」：底层框架是 Cordis，没有一个享有特权的内核。模型适配器、工具注册表、会话日志，连 agent loop 本身都是插件，ctx 上有 109 个服务。每个可替换的能力叫一个 seam，由三部分组成：声明接口的一方、提供实现的一方、使用它的一方Mooring 的核心（终端、PTY、状态判定）不开放，插件只在 9 个固定位置往里加东西。DSH 是框架，Mooring 是产品，所以这一点不该照搬
插件长什么样TypeScript 模块，导出 apply(ctx, config)，在宿主进程里运行；用 inject 声明依赖哪些服务，依赖就绪才加载，依赖没了就自动卸载Mooring 是 JSON 声明加子进程，插件代码不进 App 进程
撤回插件通过 ctx 注册的东西，卸载时都会自动撤回，包括监听、工具、适配器和 ctx.effect 返回的清理函数。热重载也靠这一点。但对外部程序的改动它没有特别处理，和别家一样Mooring 的声明式类型本来就不留状态，卸载就等于撤回；只有改外部程序的那部分要靠 setup/teardown。两边思路一致，各自的边界不同
配置插件导出 schema（Schemastery），加载时校验并填默认值，配错了加载失败并报原因；约定「凡是不同部署可能取不同值的参数，都必须做成配置项」；改了配置就热替换这个插件Mooring 没有插件配置项（G3）。DSH 的经验说明这件事有用，G3 值得往前排
组合bundle 是一个 npm 包，用 dsh.bundle 指向一份 YAML patch，patch 可以插入新的行，也可以按 id 覆盖已有的行。profile 是一个目录，里面有按顺序排好的 bundle 列表，外加用户自己的 patch。叠加顺序：各 bundle → profile 的 patch → home 下的 patch → 命令行 --patch。后面的层按行胜出，覆盖时整份 config 一起换掉，不做深度合并。--dump-config 打印叠完之后的最终配置Mooring 只允许追加、不允许覆盖，规则简单得多。值得学的是「能看到最终生效的是什么」：mooring plugins 可以加一个视图，列出每一项最终来自哪个插件
开关停用某一行，就是往用户的 patch 里写一条 disabled: true；如果和 bundle 自带的状态一样就不写，只记录与 bundle 不同的部分Mooring 用 disabled.json 记，效果相近
安装与兼容插件就是 npm、git 或 tarball 包，由 pnpm 装进 profile 目录。engines.dsh 版本范围在安装时和启动时都会检查；不兼容但想硬用，需要写一条带 acceptRisk 的豁免，而且只对精确的「插件版本 × DSH 版本」组合有效。git 包要跑构建脚本时需要单独授权（allowBuilds），授权时钉到具体提交。安装失败会把清单和锁文件恢复原样正是 G1 要补的东西。索引里每个版本单独写 engines，旧 App 自动挑兼容的那个版本，这一点比只写一个最低版本更好
市场索引是 JSON（format: 1），按插件列出多个版本，每个版本带来源（npm，或 git 的 40 位提交）、发布时间和 engines；不认识的字段直接忽略；App 不内置任何索引源，由用户自己添加Mooring 的索引每个插件只有一个版本，也没有 engines。可以照这个格式升级
谁来管理插件插件管理是一个服务，Web 页面和 plugin_manager 工具共用它。Agent 自己就能装插件、开关插件，每次操作要用户批准，或者处在完全放开的权限模式下Mooring 的 Agent 已经可以用 mooring plugins install 和 mooring --skill plugins 写插件、装插件，但这一步没有批准环节
安全SAFETY 文档写明「尚未经过安全审计」；宿主代码在宿主进程里运行，不受工作区沙盒限制；只能靠用户自己核对插件来源和 VS Code、Obsidian 同一档。Mooring 的插件代码不进 App 进程，这一点上更稳
复杂度代价光是 plugin-manager 的 README 就讲了注册表回退、peer 依赖解析、HMR 期间的重启原因、构建授权等十几种情况；核心文档总共约 4.3 万行用 npm 做分发、在进程内跑代码，就要付出这么多处理边角情况的代价。Mooring 不该走这条路

从 DSH 能借的：每个版本带 engines 的索引格式，配合兼容版本自动挑选（强化 G1）；插件配置写 schema、改了就热生效，并且约定可调参数都做成配置项（G3 往前排）；一个「最终生效了什么」的视图；Agent 动插件之前要用户批准。不借的：一切皆插件的内核、插件代码在进程内运行、npm/pnpm 依赖解析。
