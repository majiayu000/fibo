结论

  1. 方向不用改，不加新类型，先修「它说的和实际做的不一致」。「JSON 声明 + 子进程 + 少量 WASM」这条路线两边都认可。问题集中在失败路径上：安装说成功但旧版已被坏包替换、setup 失败却显示 ✓、检查全绿而运行时丢了插件、命令找不到却记成正常。
  2. 最该马上修的是 4 件事，改动都不大。写给 Agent 的通知示例能被事件文字注入并执行 shell 命令；「更新」和完成动画里的「安装」绕过确认；坏包能替换掉好的旧版；文档和实现有 6 处矛盾。
  3. 最值得做的一次重构是统一「跑一条插件命令」。setup、quota、hook、装饰现在各写了一份子进程逻辑，修复只落在其中一部分（上次只修了 hook 和装饰），所以 setup 和 quota 的超时至今管不住。这正好违反项目的「一个事实一个所有者」。合成一份后，超时、进程组、错误记录、PATH 只用改一处。
  4. 优先级按真实用法排。这台机器只装了 3 个插件（claude-quota 和两个完成动画），没有第三方作者，主要入口是用户让 Agent 写插件。所以 Agent 写出来能不能跑、坏了看不看得见，排在市场和分发之前。签名、多版本索引现在不做。

当时定的「明确不做」（前两条之外的五项已被上面的实施结果推翻）

  • 发布者签名、人工审核、多版本带 engines 的索引。没有第三方作者，也没有过不兼容版本。上一轮记下的「多版本索引」改成否定；出现第二个外部市场，或第一次真遇到版本不兼容时再议。来源记录和确认（F02–F05）已经覆盖现在的风险。
  • 进程内 JS、全面 WASM 化、开放终端和状态判定。解决不了上面任何一条，还会扩大边界。
  • Agent 类热重载。维持上一轮的决定，只把需要重开什么说准确（F26）。
  • 持久化 hook 队列、公平调度、推送总线、增量左栏协议、通用注册框架。都是局部修复能解决的。结构上只合并「跑命令」这一处；新增一种类型要改 5 个文件，但类型很少增加，不值得为此建框架。
  • options 进钥匙串。现在没有哪个插件要存密钥。第一个要存的插件出现时再做。
