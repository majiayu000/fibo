# Mooring 重构与界面计划

2026-11-03 定。

## 要支撑的决定

把现有代码（从 Keepline `next/` 搬来）逐步改成目标结构，同时补完还没做的界面稿。每个阶段做完都有一个能每天用的版本。

- **方式**：在现有代码上分阶段改，不从零重写。允许大规模破坏性改动：内部结构、宿主协议、数据库表都可以推倒重来，不为旧格式留兼容。
- **底线**：用户每天在用的 App 始终能用；换包时终端不断（宿主交接的协议要么保持，要么在同一次换包里新旧两边都认）。
- **放弃条件**：写在每个阶段下面。某阶段的前提被数据否定，就回到设计改方案，不硬做。

目标结构的来源：Keepline 仓库 `specs/architecture/` 下的目标设计（blueprint）、设计稿（design）、问题清单（issues，41 条），以及设计索引 `specs/terminal-workbench/design/index.html`。下面的编号 I1–I41 指问题清单里的条目。

## 目标结构要点

1. **请求有回执**：每个请求带 `client_id` + `request_id`，回执分为已落库 / 被拒（附对象现状）/ 重复（返回上次结果）。客户端的请求状态是挂起 / 已确认 / 被拒 / 结果未知，不再有「忙时丢弃」。成功提示等回执再显示。
2. **写入只带它在意的前提**：没有全局版本号当锁。新建不带前提；改结局带「我看到的结局」；布局是一个个具体操作，不整块覆盖。
3. **状态只在一处判定**：`core::status::of` 是唯一入口。需要你注意的状态必须有活着的 Agent 支撑，Agent 没了就落成「中断」。
4. **宿主内部**：状态线程只改内存，不做 I/O；写库在单独的线程里；PTY 读写不等全局状态；长期线程有监督者，出错时进入 Degraded 并显示出来，宿主不退出。
5. **交接两阶段**：Prepare → READY → COMMIT → SERVING。READY 之前失败，旧宿主继续服务。
6. **外来输入要显式授权**：本机进程（包括 Agent）可信；配对链接要先确认；每台手机独立 token。

### 第 1 阶段 · 编辑不再被挡、不再丢（I1–I7、I10、I11）

- 会话内容单独计数，不再推高全局版本号。
- 请求信封 + 回执 + 去重表（`requests` 表保留 24 小时，和改动在同一事务里写）。
- App、CLI、手机共用一个请求状态机；表单在确认后才关；超时显示「不确定是否成功」，并给出用同一个 id 重试的按钮。
- 编辑按对象带前提：AddTask 不带；SetOutcome / SetTaskOutcome 带「我看到的结局」，SetOutcome 还带 turn_key；UpdateTask 拆成按字段改。
- 布局改成操作：CreateTab、RenameTab、MoveTab、SplitPane、ResizeSplit、MovePane、ClosePane{expect_terminal}、CloseTab{expect_terminals}。去掉 PutTab。

验收：Agent 持续输出时连续标记完成 100 次，0 次被拒；回执前断开再重发同一个 id，待办只多一个；Agent 分屏的同时改标签名、拖分隔线，三个改动都在；关标签确认框打开后 Agent 新开分屏，关标签被拒并要求重新确认。

### 第 2 阶段 · 不批错、状态不说谎（I8、I9、I12–I17）

- 审批实例：id = 指纹（问句 + 命令行），回答必须带 id，宿主重读画面核对；手机去掉不核对画面的「选 1 / 2 / 3」「Esc」；卡片展示命令全文。
- `status::of`：Waiting 要求 Agent 活着，否则落成「中断」（注明原因）。
- 宿主健康 Healthy / Degraded：写库失败进入重试队列；状态栏小提示。
- 识别：检查点只在一批事件处理成功后前进；读不了的文件进隔离名单。
- 长期线程交给监督者；Draining 超时。
- **界面**：在侧栏里直接答审批（方向稿 C），开放题直接打字回答。依赖上面的审批实例 id。

放弃条件：开工前用 Claude、Codex 各录 20 个真实审批画面测指纹。同一个审批的 id 会抖动，就先改指纹规则。

验收：问句相同、命令不同的两个审批先后出现，用旧卡片点允许被拒；Ctrl-C 掉等审批的 Agent，1 秒内卡片变「中断」、手机推送撤回；第一次写库返回 SQLITE_BUSY 时出现提示，随后自动消失，数据正确。

### 第 3 阶段 · 宿主内部（I18–I24）

- 写库改为 `synchronous=NORMAL`；结束的终端回收（Reclaimed，释放 fd 和缓冲）。
- 按第 0 步压测结果决定：停顿超过 16ms，就上「状态线程 + 写库线程」；否则只把 fsync、fork、ps、hook 挪出锁。
- 交接两阶段，每一步都能注入失败做测试。

验收：开关 200 个终端后，fd 和内存回到基线；PTY 读最大停顿 < 16ms；在 Prepare / READY / COMMIT / SERVING 前后各注入一次失败，终端都不断。

### 第 4 阶段 · 手机和外来输入（I25–I37）

- 每台手机独立路由 token；关闭码 4401 撤销 / 4403 改角色 / 4429 踢出（5 分钟冷却）。
- 手机请求 10 秒超时 + 幂等 id；心跳 15 秒；events 流断了自动重订；终端里换了对话时推 `session_switched`。
- 配对链接先确认再保存；握手前的连接 10 秒超时；动作模板只做单引号转义；在不可信目录里跑 git 时关掉 fsmonitor。

验收：撤销手机 A，A 的 token 无法让本机掉线，手机 B 照常；断网时发送、恢复后消息只出现一次；终端里 /new 之后，手机 5 秒内切到新会话。
