多平台架构

2026-11-07 · 状态：待验证（第 2 步做完 Linux 后复核）· 工作清单见 Windows 计划

结论：新建一个 mooring-platform crate，所有依赖操作系统的代码只能放在里面，上层只调它的统一接口。每个平台一个目录，Windows 的文件在 Mac 上根本不参与编译。

这样改一个平台的实现，影响不到另一个平台。唯一能同时影响多个平台的地方是接口本身，而改接口时，每个平台都会编译报错或测试失败，不会悄悄出错。

要支撑的决定：按什么结构移植 Windows 和 Linux。放弃条件：见文末。

为什么现在就要做

现在平台代码散在各处。下面是扫描仓库源码的结果（不含测试文件，正则统计，是估算）：

如果直接给这些文件加 #[cfg(windows)]，平台分支会散进 100 多个文件的业务逻辑里。每次改业务都要同时想三个平台，这正是要避免的情况。relay 和 plugin-host 不用改就能在 Windows 上通过测试，说明没碰系统的代码本来就跨平台，要收拢的只是那些碰系统的部分。

分层

产品层：mooring-app、mooring-host窗口、状态判断、Agent 管理、远程协议处理。不写任何平台判断，不直接调系统接口。
共享逻辑：mooring-core、mooring-remote、mooring-relay状态规则、协议、插件格式。手机和中继看到的内容与平台无关。

为什么不用别的方案

方案结论原因
散落的 cfg否决分支进入业务逻辑，改业务就要碰三个平台，也无法机械检查。
每个平台一个 crate暂不采用隔离和单 crate 一样（目标平台外都不编译），但多了门面层和依赖配置。将来 unix/ 共享成为负担再拆，改动不大。
运行时 dyn Trait否决平台在编译时就确定，没有运行时切换的需求，却要多一层间接调用；终端读写还是性能敏感路径。
单 crate，按平台分目录采用编译时选定，没有运行时开销。可以用测试检查边界，也和仓库现有的 guard 机制一致。

具体函数签名在迁移每个能力时才定，届时有两个实现可以对照。这里不提前设计，避免接口被第一个平台绑死。

做不到的能力，用能力表说清楚

能力表要等第一个能力真正需要时再加（第 3 步的换包交接）。在那之前，做不到的调用返回 Unsupported，比如 Windows 上的 link_program。

// 上层只问能力，不问平台
if platform::capabilities().handoff {
    handoff::hand_over(...)
} else {
    tell_user("升级后台会结束正在运行的终端")
}

上层永远不写 if windows。将来 Windows 做了交接，只把能力表改成 true，上层一行都不用动。

五条规则，靠机器检查

规则怎么检查
1. 平台代码不出界。mooring-platform 之外不能有 cfg(target_os/unix/windows)、libc::、std::os::unix、写死的 /bin/sh、直接读 HOME。扩展现有的 guard 棘轮：现状记成基线，只能减少，新增就失败。不用一次改完。
2. 行为由同一套测试约定。接口的每条承诺写成一个测试，三个平台跑同一份。tests/contract/。这也是发现平台差异最便宜的办法，比如这次的 sh 缺失。
3. 平台依赖不外泄。libc、windows-sys 只出现在 mooring-platform 的 [target.*] 依赖里。guard 检查各 Cargo.toml。
4. CI 按改动范围跑。只改 Windows 实现，Linux 不跑；改接口或共享代码，三个平台全跑。GitHub Actions 路径过滤：platform-linux.yml、platform-windows.yml，改别的平台的实现文件不会启动它们。macOS 的检查是必过项，每个 PR 都跑，不能按路径跳过，但 windows.rs 不参与 Mac 编译，所以它只多花时间，不会被别的平台影响。新平台先不挡合入，稳定后再改成必过。
5. 协议不带平台。手机和中继不解析路径、不判断系统。路径在协议里是不透明的字符串，只负责显示。协议测试向量加入 Windows 路径的样例。

同样要分开的还有三处

  • 读屏规则：样例按平台分目录。规则默认共用，确实不同才加平台覆盖，这样改 Windows 的规则不会影响 Mac。
  • 打包和发布：packaging/{macos,linux,windows} 各自独立，流水线也独立，Windows 打包失败不挡 Mac 发版。
  • 测试夹具：测试里不写死 Unix 路径和 sh，统一用共用的测试工具。这次 Windows 上 18 个单元测试失败，其中大半是这个原因。

迁移顺序

每一步都是小 PR，先原样搬动，不改逻辑；用 macOS 现有测试和性能门禁确认没有变化，再加新平台。这样也减少和 main 上并行工作的冲突。

步内容Mac 行为变化怎么算完成
0建 crate，加棘轮 guard 和 CI 矩阵；把 core 里已写好的进程、时间、shell 搬进去，目录能力收掉 HOME（已做）无guard 生效；三个平台的 core 测试都过
1host 的进程、文件监听、系统信息搬入接口，Linux 实现补上（已做；managed_session 里 Mac 专用的资源测量留给第 2 步）无Linux 上 host 库编译通过，库测试通过，并由 CI 守住
2Linux 跑通全链路：先让 managed_session 在 Linux 上编译和运行；然后容器和真机上配对、手机连接、真实 claude 和 codex 状态。然后复核接口无手机能看到并操作 Linux 上的 Agent。测试已过（模拟手机经中继、假 CLI）；真手机和已登录的真实 CLI 还没做
3终端和本机连接：Unix 实现搬入接口，再写 ConPTY 和 Windows 的 Unix 套接字原样搬动，靠测试和门禁确认Windows 上 host 能启动，list/read/send 能用
4Windows 全链路：配对、手机、Agent 状态、钩子、读屏差异无你的 Windows 电脑上端到端可用
5窗口（gpui_windows、gpui_linux）、打包、发布；决定交接方案 B无按平台单独决定发不发

为什么先做 Linux：它的错误最少，成本最低，还能用第二个实现检验接口是不是被 macOS 绑死了。这样 Windows 这个最贵的实现开工时，接口已经验证过一次。

已经测到的事实

  • Windows 真机（build 26200），GNU 工具链加动态 ghostty：core 单元测试 227 过、1 个按设计忽略；remote、relay、plugin-host 全过。core 有 3 个集成测试失败，因为测试副本没有 git 记录和 .deps/zed，属于环境问题。
  • Linux（Docker，ARM64）：同样 4 个 crate 的单元测试全过；同样 3 个集成测试因环境问题失败。这一轮的代码早于本次修复，修复后没有重跑。
  • host 在 Linux 上（第 1 步后）：库编译通过，库测试 313 过、4 个按设计忽略。之前是 86 个编译错误、10 个文件。Windows 的 251 个错误是移植前的数字，第 3 步再量。
  • ConPTY：OSC 7、133、7501、9、8 都能穿过；中文和 emoji 正常；claude 和 codex 能启动并录到画面。鼠标模式 ?1000h 被吞；部分模式序列会排到文字前面；输出是整理后的屏幕，不是原始字节。
  • 接口测试（第 0、1 步）：同一份 tests/contract 在 macOS、Windows 真机、Linux 容器上都过。Windows 的 Job 对象第一次真正运行：结束整棵进程树、丢弃句柄不结束进程。Windows 上读别的进程的参数、环境变量、目录、套接字，以及文件监听，按接口约定返回 Unsupported，第 4 步补上。
  • host 全部测试在 Linux 上（第 2 步）：Debian ARM64 容器 549 过、0 败、39 个按设计忽略，包括真实终端和经中继的手机协议；GitHub 的 Ubuntu x86 也全过，CI 从此守住。Ubuntu 上才冒出来的差异：PROMPT_COMMAND 是数组且多一个 systemd 钩子。同一份资源预算：40 个空闲终端 CPU 约 0%，4 个 Agent 写 30 秒 host 用 0.52 秒 CPU，追加的日志只读一遍。Linux 数不了指令，这项靠只读一遍来判断。
  • 重启补扫（手动 scan_bench，调试版，按真实规模 2208 个目录、6402 个文件）：Linux 装监听 38 毫秒，日志没变时补扫约 250 毫秒，不打开文件、不写库；Mac 约 400 毫秒（当时负载更高）。首次导入 3.4 到 4.2 秒，只代表文件数量的开销，真实日志正文要长得多，没量。
  • 真实 CLI 在 Linux（手动 real_cli，不带凭据）：claude 2.1.319、codex 0.167.0 都能从进程认出。npm 的 claude 文件叫 claude.exe，codex 由 node 带起原生子进程。登录后的状态、日志和钩子没测，那需要账号。
  • 第 3 步，本机连接改用 AF_UNIX，不用命名管道（决定）：host 依赖克隆后一边读一边写、读超时、shutdown 叫醒读、peek，这些都是套接字的语义，命名管道要用重叠 I/O 一项项模拟。Windows 1803 起有 AF_UNIX，ConPTY 本来就要 1809，不多添限制。实机结果：同一份接口测试过，16 MiB 约 70 毫秒。两个差异在接口内吸收：套接字必须带 WSA_FLAG_OVERLAPPED，否则读会挡住写、超时不生效；Winsock 的 shutdown 不叫醒读，靠 CancelIoEx，没有轮询。放弃条件：真实 host 在 Windows 上跑不稳就回到命名管道，接口不用改。
  • 第 3 步，ConPTY：同一份终端接口测试在 Windows 实机上过（输出、输入、改大小、退出码、关闭）。Mac 的主路径搬动后，CI 的完整检查和窗口性能门禁都过。
  • 第 2 步接口复核：第二个实现没有让任何已有能力改签名，只新增了能力，不触发放弃条件。Linux 和 Mac 的差异都在接口之内吸收：没有重放（MUST_SCAN）、临时端口从 32768 开始（first_handed_out_port）、进程名按文件取。
  • 接口第一次被第二个实现检验（第 1 步）：Linux 的 inotify 没有日志可重放。接口没有改签名：start 从旧检查点开始时报 MUST_SCAN，由已有的补扫接手。代价是 Linux 上 host 每次重启都要扫一遍日志目录。
  • Zig 和 MinGW 混用会悄悄算错：静态链接 ghostty 后 powf 返回 0，亮度变成 NaN。改用动态库后恢复。

还没定的事

  • Windows 发布工具链：计划用 MSVC，这是 Rust 在 Windows 上的标准目标，但这个组合还没跑过。真机测试需要安装 VS Build Tools（会改动系统，并要接受微软的许可），可以先走 GitHub 的 windows-latest。
  • ConPTY 改写输出的影响：要接上 libghostty 后才知道读屏规则是否受影响。OSC 133 能穿过，可以作为补充依据。
  • Linux 真机：Docker 没有桌面和登录会话，Secret Service 和通知要真机才能测。x86_64 也还没测。

放弃条件

  • 第 2 步复核时，如果接口要为 Linux 大改（一半以上的能力要改签名），说明抽象没选对，停下来重新设计，不继续做 Windows。
  • 任何一步如果 macOS 的测试或性能门禁变差且一天内查不出原因，这一步回退。Mac 是现在唯一在用的平台，优先级最高。
  • 第 4 步如果读屏在 ConPTY 下不可靠，且钩子和日志也补不上，Windows 就只发基础终端功能，或者先不发。
