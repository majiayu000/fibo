这页要定什么

决定：默认的会话优先布局选哪种排法；待办要不要搬出会话列表。

看什么：打开窗口后，能不能一眼找到下一个要处理的会话；看到的概念是不是比现在少；从主屏点到一个会话不多花步骤。

放弃条件：用一周后如果经常找不到正在跑的会话，或反复展开“停着的”才能找到要的会话，就退回 B（在跑单独一行），再不行恢复分组标题。

为什么觉得复杂

侧栏同时回答了三个问题：还没开始的事、正在跑的、跑完的。鸟瞰已经用五列回答过这三个问题了，侧栏又答一遍，而且待办在现在的侧栏里出现了三处：列表上方的提示、“＋ 新建待办”、底部的“待办 N”。

所以分工改成：鸟瞰看全局，侧栏只负责跳到下一个要你的会话。

不变的

  • 顶部标签栏、右边窗格、状态栏都不动；搜索和空间标签也不动。
  • 切到新排法后，会话一个都不能少：停着和做完的都收在一行里，点开还是全部。
  • “机器栏”“按机器”“目录”三种布局不在这次范围内；如果 A 定下来，再决定它们的列表要不要跟。
  • 不按待办或分支给会话归组（之前的数据已否定：454 个会话挂到待办的是 0 个）。

待办搬到哪

  • 底部“待办 N”点一下去鸟瞰的待办列，Esc 回来。底部这个位置现在就有这个入口，不用重新学。
  • 旁边的“＋”就地记一句：工作区里在底部弹输入框，回车记下，不离开当前会话；在鸟瞰里则打开列内输入卡，和 鸟瞰新待办 demo 一致。
  • 去掉列表上方的“还没有待办”提示和待办展开列表。

如果要做进 App

  • 主要改 sidebar/view.rs 的分组和 sidebar/todos.rs；分组归属仍来自 core 的 status::of 和 sidebar_rank，不在界面里重新判断状态。
  • “在跑排最上”要改排序：现在 sidebar_rank 的顺序还没按这个核对过。
  • 侧栏性能规则要遵守（docs/performance/index.html），列表变长或折叠的动画都要过门禁。
  • WASM 插件布局（flat、wasm）拿到的数据不变。
