# 返工复盘

改代码之前读一遍。这里只记**同一类错犯了不止一次**的事：规则、为什么、证据。单次的错和它的修法在提交说明里（`git why`），手机真机才发现的在 [real-device-findings.md](phone-app/real-device-findings.md)，这里不重复。

**要支撑的决定：** 下次改动前该先防哪类错，哪条规则值得升进 `CLAUDE.md`。

**怎么用：**

- `python3 scripts/rework-pairs.py --since <日期>` 列出哪些修复在补最近几天的提交（追溯修复改掉的行，不靠印象）。哪些算同一类错要人看，看提交的 `Why:`。
- 每条记「出现」的天数，按修复提交的日期算。满 3 天升进 `CLAUDE.md`，这里留一行指过去。
- 能写成测试或守卫的先写测试，写不成的才留规则。规则多了没人看，只留还在犯的。

做法学自 [yetone/magpie 的 LESSONS.md](https://github.com/yetone/magpie/blob/main/LESSONS.md)；为什么这样试、什么时候放弃见[决定记录](decisions/2026-11-07-rework-review.md)。

## 2026-11-07 第一遍（11-01 到 11-07）

536 个提交（不含合并）里 208 个是修复，其中 91 个在补 5 天内的提交，56 个隔不到 24 小时，25 个是在补上一个修复。91 不全是错：有些是看了效果接着调。下面是读完这 91 对的 `Why:` 后归出来的类。

### 换了版本，旧的东西还在（已升进 CLAUDE.md）

**规则：** 改状态判定、接口或文件格式时，试一遍旧的还在：宿主刚重启、插件在宿主启动后才更新、旧版写的文件和脚本。只对新数据成立的修复，要说清旧数据怎么办。

**为什么：** 测试都从干净状态开始，用户每次换 App 都不是。

出现 4 天：

- 11-03 `2d60dbf` 插件在「装上就换成它」之前装的，一直播印章。`e2f3ce0` 改名前装的状态栏脚本还往旧目录写额度。
- 11-05 `1ee2249` 换 App 后判定要用的命令只在内存里，活着的轮询掉进要你处理；`85d21e7` 接着发现重启后前 45 秒还是错的。
- 11-06 `0638fe9` Codex 留下的后台命令，换 App 也掉状态。
- 11-07 `cb67e91` 子 Agent 起的后台任务，换 App 又掉。`1dcdbaf` 手机连的进程比插件早启动 7 秒，注册表是旧的。

### 修了一个，没修它的兄弟

**规则：** 修 Agent、入口或进程层级相关的 bug 时，列出其他 Agent、手机和桌面、子 Agent，当场一起修，或者在提交里写明没修什么并记下来。

**为什么：** 报告只描述用户眼前那一个。用户下一次碰到的多半是旁边那个。

出现 2 天：

- 11-06 `39d8f1a` 手机「停下」按 Agent 发对的键（`38e4c5c`），桌面的中断还是 Ctrl-C。`0638fe9` 后台 shell 判定只覆盖了 Claude（`3fb2791`）。
- 11-07 `cb67e91` 又漏了子 Agent（`1ee2249`）。`2c790db` Codex 的父子会话做完（`7b27043`），OpenCode 和 Cursor 还没有。

### 限制没盖住所有能到达的路

**规则：** 加限制时先列出所有能到这件事的路，再写限制。安全边界每补一个口子，就问一遍同一个思路还能从哪进。

**为什么：** 一轮 review 只能发现一层，真绕过往往在下一层。

出现 2 天：

- 11-06 手机 diff 接连补了四轮：`7f09c69` 任意目录，`6246db6` 内嵌 git 目录执行配置，`ffa1277` 压缩包自带 filter，`c30e6ec` lfs extension。
- 11-07 `7d08fda` 先不管的空间：插件通知、新建待办、手机开终端都绕过去了（上一版 `09b7005`，隔 36 分钟）。

### 读失败当成没有

**规则：** 读不到、解析不了是「不知道」，不是「空」。尤其是接下来要写回的文件。

**为什么：** 当成空之后下一次保存就把原文件覆盖了，用户的东西没了，而且没有任何报错。

出现 2 天：

- 11-05 `9a00e45` 证据列解析不了当成没有证据。`1ff09ea` machine-id 写不进去就每次换一个。
- 11-06 `d9a56fb` 机器配置读坏后，新增机器会覆盖原配置（#92）。

### 界面做完才发现不是用户要的

**规则：** 用户描述的是观感时（「字符在变」「对得上」），先出最小的一版给用户看，再铺开。

**为什么：** 这类返工不是修 bug，是整段重写。

出现 2 天：

- 11-04 `df10c73` 七个完成动画改纯字符，隔 24 分钟重写了 594 行（`1e4042c`）。
- 11-05 `80d79d6` 先不管的飞行动画对不上，重写 136 行（`d2e445a`）。

### 演示数据测不出真实情况

已有规则和记录，见 [real-device-findings.md](phone-app/real-device-findings.md)。这里只补一个桌面和电脑端也算的例子：`d7b8f84` 演示数据全是短命令，真实 Bash 命令中位 433 字符。

### 重跑掩盖了根因

**规则：** 偶发失败先注入延迟或抓现场，不靠重跑判断。`target/ci-test-retries.txt` 要有人看。

**为什么：** 重跑让 CI 变绿，同一个用例可以一直红下去。

- 11-06 到 11-07 的 47 条重跑记录里，41 条是同一个用例 `codex_rebind::an_older_conversations_words_on_the_screen_are_not_what_the_pane_runs`。原因是一半夹具一半真问题（`updated >= started` 在同一秒成立，等于猜）。
