重复来源清单

2026-11-03 · 全仓库只读审计，范围包括 core、app、host、remote、mobile、native.m。找的是同一件事存了两份、或在两处各自判定的地方。同一份数据换个说法显示的不算。

这页要支撑的决定

哪些地方要并成一份、按什么顺序做，以及要不要把「每件事只有一个所有者」写进架构原则并加守卫测试。每条都给了结论：采用是要并成一份，待验证是先实跑复现再定，不改是有意为之或不值得改。

放弃条件：一类问题如果修起来要改协议又没有用户看得到的错，就只加测试守住，不重构。

结论

  1. 根因只有一个：core 已经有唯一的判定入口（status::of、session_title、tab_title），但宿主在对外边界上（手机卡片、mooring 命令、插件事件）绕开了它们，直接读原始字段重新拼一遍。手机端缺字段，只好再推一遍。A、C、D 三类大多出在这里。
  2. 名字（B 类）在标签页和会话上各存一份，优先级还正好相反。今天的修复只让显示对上了，底下仍是两份。
  3. 「要你处理」（C 类）在侧栏、顶栏、看板、菜单栏、手机上有 4 种数法、4 种叫法、3 种颜色。
  4. 先做 A、B、C，它们现在就能被看到。其余的放第二批，最后补守卫测试。

A · 宿主对外的数据绕开 core 的判定

根因：rp::Card、control.rs、plugin_hooks.rs 没调用 status::of 和 session_title，而是从 Content 原始字段自己拼。

I · 守卫测试的空白

ui/tone.rs 的守卫只匹配 Status::X.colors() 这种字面写法，管不到下面几种：

  • 把状态先存进变量再取色，或通过 widgets::badge 间接取色；
  • 白名单按整个文件放行，所以 sidebar.rs 和 board.rs 里任何地方都能借状态色；
  • 反方向：会话的东西用了 Tone 的色（C4）；
  • 写死的状态词（D 类）；
  • native.m 和手机端完全不扫。

建议的顺序

  1. 第一批（现在就能看到的错）：A1–A4，B1–B3，C1–C4，D1。核心改动是给 core 加三个唯一出口：status::of（已有）、session_title（已有）、新增的「要你处理」判定和组名。宿主的 Card、CLI、插件事件和 App 都只调这三个；名字只存在会话上。
  2. 第二批：E1、E2、F3、G2、G3、H1–H3、D2–D5。
  3. 先复现再定：F1、F2、F4、G1。
  4. 守卫：在 docs/plan.md 架构原则里加一条「每件事只有一个所有者：状态、名字、要你处理、更新时间都只在 core 判定」。补测试：同一个会话在标签、侧栏、手机卡片、CLI 拿到的名字和状态必须一样；扫写死的状态词（含 native.m 和 mobile）。
