# 第 1 阶段：编辑不再被挡、不再丢

状态（2026-11-03）：开工。对应 [plan.md](../plan.md) 第 1 阶段（I1–I7、I10、I11），也是多机第 2 步（远程打字和审批）的前提。

## 要支撑的决定

- 窗口、`mooring` 命令、手机和另一台电脑发来的写请求，能不能都走同一套「信封 + 回执 + 去重」，让用户在 Agent 持续输出时做的操作不再被拒、不再被悄悄丢掉，断线重发也不会做两遍。
- 指标就是 plan.md 的验收：
  - Agent 持续输出时连续标记完成 100 次，0 次被拒；
  - 回执前断开、再用同一个 id 重发，待办只多一个；
  - Agent 分屏的同时改标签名、拖分隔线，三个改动都在；
  - 关标签的确认框打开后 Agent 新开了分屏，关标签被拒，要求重新确认。

## 现状（11-03 摸底）

- **只有一个全局版本号**：`Workspace.revision` 只在 `Host::commit` 里加一，但会话输出、绑定、标题和画面提示、后台 shell 也都走 commit，Agent 输出时大约每秒加一次。
- **9 种编辑带全局版本号检查**，对不上就回「工作台已变化，请刷新后重试」。这 9 种是：AddSpace、UpdateSpace、AddTask、UpdateTask、SetTaskOutcome、SetPendingTask、SetOutcome、AssignTask、SaveSessionTask。其余编辑不检查，按 id 直接应用。
- **App 忙时会丢请求**：App 只有一个 `busy` 标志，忙时只排队「不查版本号」的编辑，其他请求直接丢掉，界面上不说。
- **布局靠整块覆盖**：拖分隔线、移动窗格、改标签名、开会话、启动后放窗格，都发 `PutTab` 整块覆盖。
- **没有请求 id、没有去重**：重发 AddTask 会回「ID 已存在」的错。

## 分步

| 步 | 做什么 | 验收 |
|---|---|---|
| A 按对象带前提 | 去掉全局版本号检查。SetOutcome 带「我看到的结局」和 turn_key，SetTaskOutcome 带「我看到的结局」；AddTask、AddSpace、AssignTask、SetPendingTask、SaveSessionTask 不带前提；UpdateSpace、UpdateTask 按 id 改 | Agent 持续输出时连续标记完成 100 次，0 次被拒；Agent 在你看过之后又开了新一轮，「标记完成」被拒并说明原因 |
| B 信封、回执、去重 | 写请求外面包一层 `{client, request, edit}`；回执分三种：已落库、被拒（附对象现状）、重复（返回上次结果）；`requests` 表和改动在同一个事务里写，保留 24 小时 | 回执前断开、用同一个 id 重发，只生效一次；宿主重启后重发也一样 |
| C 一个请求状态机 | App、CLI、手机共用：挂起 / 已确认 / 被拒 / 结果未知。忙时不再丢，排队；表单等回执才关；超时显示「不确定是否成功」，给出用同一个 id 重试的按钮 | 拔掉宿主再接上，挂起的请求要么确认、要么显示结果未知，没有一条无声消失 |
| D 布局改成操作 | CreateTab、RenameTab、MoveTab、SplitPane、ResizeDivider、MovePane、ClosePane{expect_terminal}、CloseTab{expect_terminals}；去掉 PutTab | Agent 分屏的同时改标签名、拖分隔线，三个改动都在；关标签确认后有新分屏，关标签被拒 |
| E 远程协议用信封 | `mooring remote` 的写操作带上 client 和 request，回执原样传回去 | 手机和另一台电脑断线重发，只生效一次 |

- A 先做：改动最小，单独就能解决「被挡」。
- B 要改存库：`Store::save` 接收可选的请求记录，写进同一个事务。

## 放弃条件

- A 做完后，用 Agent 持续输出的真终端测「标记完成」，如果被拒仍然超过 1%，说明问题不在全局版本号，回到设计重新找原因。
- B 的去重表让每次 commit 的耗时 p99 增加超过 5 ms：改成只给用户请求写表，内部 commit 不写。

## 不做

- UpdateTask 拆成按字段改（plan.md 原有）：待办只有窗口一个写入方，宿主、`mooring` 命令和手机都不改待办，所以整块覆盖冲不掉别人的改动。等出现第二个写入方（比如手机能改待办）再拆。

- 会话内容单独计数（plan.md 第 1 条）放到第 3 阶段和写库线程一起做。A 去掉全局检查以后，内容加一不会再挡住编辑；剩下的问题是每秒一次整表对比的写库开销，那属于第 3 阶段。

## 结果

### A 按对象带前提（2026-11-03）：完成，待真机验收

- 宿主不再核对全局版本号。`Edit::SetOutcome` 带 `seen: { outcome, turn }`，`SetTaskOutcome` 带 `seen`，都由 core 的 `Workspace::stamp` 按窗口当时的副本填写，窗口的 `edit()` 统一调用它；宿主只在这个会话的结局变了、或 Agent 开始了新一轮时拒绝，并说明原因。已经是目标结局的，直接算成功。脚本不带 `seen`，照旧应用。
- App 忙时，除新建（AddTask、AddSpace、SaveSessionTask）以外的编辑都排队，不再丢；新建仍丢，防止双击建出两个，等 B 有请求 id 后再改。
- `Request::Edit` 的 `revision` 字段暂时保留但不再读，B 用信封替换它。
- 已验：core 单测（Agent 输出把版本号推高 100 之后，在旧副本上做的「标记完成」照样生效；重发不报错；新一轮、被别人改过、待办结局被改过都被拒）；宿主集成测试（版本号过期的编辑只因对象不存在而失败）；core、宿主、App 全部测试，守卫测试。
- 验收测试 `marking_done_while_the_workspace_moves_is_never_refused`：真宿主进程绑上一个 Codex 会话，另一个线程每 2 ms 提交一次让版本号前进（测试中前进几百次），同时用 5 ms 前的副本连续标记完成和重新打开 100 次：0 次被拒。临时放回旧的全局检查后，同一测试 100 次全被拒。
- 11-03 已换进正在用的 App，换包前后 43 个 Agent 进程一致。
- 没验：真 Agent 输出时在窗口里手点「标记完成」；版本号是用宿主请求推的，不是真 Agent 日志。

### B 信封、回执、去重（2026-11-03）：完成

- `Request::Edit` 去掉没人读的 `revision`，换成可选的 `request: { client, id }`（core 的 `RequestId`）。窗口的每次编辑和 `mooring` 命令的写操作都用 `RequestId::fresh()` 取号：一个进程一个 client，id 按顺序递增。脚本不带 `request` 时照旧应用，但没有去重。
- 宿主新增 `requests` 表（client、id、时间、错误），每次写入时顺带删掉一天前的记录。
  - 编辑生效时，这条记录和改动在 `Store::save_applying` 的同一个事务里写入，要么一起落库，要么都不落。
  - 编辑因为自身原因被拒（对象不存在、结局已被改过、分屏放不下等），单独记下错误。
  - 存库或索引出错不算被拒，不记录，重发会重新执行。
- 回执沿用原来的回复形状，没有加新类型：
  - 已落库：回 `Workspace`；
  - 被拒：回同一条错误；
  - 重复：上次生效的回当前的 `Workspace`，上次被拒的回同一条错误。
  - 「被拒附对象现状」没有单独做，因为窗口本来就通过订阅拿到最新工作台。远程协议在 E 步再决定要不要随回执附上现状。
- 编辑入口从 `client.rs` 挪到 `host/client/edit.rs`。`store.rs` 和 `host/mod.rs` 的单测挪成同目录下的 `tests.rs`，两个超长文件都变短了。
- 已验：
  - 集成测试 `a_named_edit_takes_effect_once_across_hangups_and_restarts`，起真宿主进程：
    - 发出新建待办后不等回执就挂断，再用同一个 id 重发 3 次，待办只有 1 个；
    - 不带 id 重发同一个新建，被拒「ID 已存在」，说明是去重在起作用；
    - 另一个 client 用相同的 id 发请求，照常生效；
    - 一次被拒的标记，在它要找的待办建出来之后用同一个 id 重发，回的仍是第一次的错误；
    - 杀掉宿主、在同一目录重启后，用同一个 id 重发，生效过的回工作台，被拒过的回同一条错误，待办没有多出来。
  - 临时去掉宿主的去重检查后，这个测试在重发那一步失败。
  - 单测：一天前的记录在下次写入时删掉。
  - 全部测试通过，含守卫测试。
- 放弃条件没有触发：同一宿主上各连续编辑 400 次、跑 3 轮。不带 id 时 p99 为 0.12–0.24 ms，带 id 时为 0.14–0.18 ms，差距远小于 5 ms。内部提交不写这张表。
- 没验：
  - 窗口还不会自己重发。忙时排队的编辑带着原来的 id，但断线后不会重试；这是 C 步的事。
  - 远程协议（手机、另一台电脑）的写操作还没带 id，这是 E 步。
  - 宿主在事务中途崩溃的情况，没有用故障注入测；能保证一起落库，靠的是两者写在同一个 SQLite 事务里。

### C 一个请求状态机（2026-11-03）：完成，窗口里的样子待真机看

- core 新增 `delivery` 模块，窗口和 `mooring` 命令共用。手机走远程协议，到 E 步再接。一个请求的结局只有三种：
  - 已确认（`Confirmed`）；
  - 被拒（`Refused`）：重发也会得到同样的结果；
  - 结果未知（`Unknown`）：其中 `sent` 区分「没发出去」和「发了没等到回复」。
- `deliver` 在 `PATIENCE`（10 秒）内用同一个请求重发，从 0.1 秒开始退避，最长间隔 1 秒，所以宿主重启或换包时请求不会丢。
  - 只有安全的请求才会在可能已送达之后重发：带 id 的编辑、读工作台、读识别状态、重载插件。
  - 其他请求只在确定没发出去（连不上）时重试，发出去后断了就直接报结果未知，不会重发。
  - `rpc` 改为调用 `delivery::attempt`，只试一次。
- 窗口的改动：
  - 忙时不再丢请求，一律排队，只丢「重复的同一下」：同一类新建（待办、空间、同一会话存待办）或刷新已经在等时，第二次直接丢掉，防止双击建出两个。
  - 表单等回执才关：保存后表单留着，被拒或结果未知时连同已填的内容一起留下；等回执期间再按保存不起作用。
  - 结果未知时，错误条上出现「重试」按钮，用同一个请求、同一个 id 再发一次，宿主最多执行一次。
- `mooring` 命令的两处写操作（开分屏后放窗格、关窗格）也改用 `deliver`。
- 已验：
  - core 单测 3 个，用一个假宿主：
    - 连不上时等满耐心，报「没发出去」；
    - 读完请求就挂断时，带 id 的编辑会重发多次，最后报「不确定是否成功」；不带 id 的停止只发一次；
    - 被拒和成功都只发一次。
  - 验收测试 `a_write_made_while_the_host_is_away_lands_once_it_is_back`：
    - 先停掉真宿主，在它停着的时候发一个新建待办，1.5 秒后宿主在原目录重启，这次写入等到它回来后落库；
    - 用同一个请求再发一次（模拟窗口的「重试」），待办仍然只有一个；
    - 宿主一直不回来时，报「没发出去」。
  - 临时去掉重发后，验收测试失败。
  - 全部测试通过。
- 没验：
  - 没在真窗口里看错误条和「重试」按钮，也没手动拔过宿主（不做模拟点击）。
  - 宿主不在时，窗口会显示最多 10 秒的「正在更新…」，期间其他操作排队。这比原来立刻报错慢，用起来是否可以接受还要看实际体验。
- 没做：
  - 开终端（Launch 加 PutTab 两步）忙时仍然丢，等 D 步把布局改成操作后再处理。
  - 快速新建待办的输入框提交后马上清空，被拒时输入的字会丢。

### D 布局改成操作（2026-11-04）：完成，窗口里的拖拽待真机验

- 去掉 `PutTab`（拿窗口手里的整块标签覆盖宿主的那份）。窗口、`mooring` 命令和脚本改用下面这些按对象下发的操作，宿主按它当时的布局逐个应用：
  - `CreateTab`：新建标签；id 已经有了就拒绝，不再覆盖。它摆进来的终端，会从原来所在的标签里移走，原标签空了就关掉。
  - `RenameTab`：改标签名。
  - `MovePane { terminal, target, side }`：拖到目标窗格旁边，或在同一个标签里互换位置。同样的移动重复做一次，结果不变。
  - `ResizeDivider { tab, path, axis, anchors, ratio }`：拖分隔线。`anchors` 是按下时两侧各一个窗格 ID；该路径、方向或任一锚点所在侧变化时拒绝，提示「再拖一次」。子比例变化或两侧内部新增分屏仍可合并。旧 `ResizeSplit` 已移除，版本混用会拒绝解析而非忽略身份检查，见 [分隔条身份](../decisions/2026-11-10-divider-identity.md)。
  - `ReplacePane { old, new }`：中断的终端重开后，回到它原来的格子。
  - `SplitPane` 加了 `forced`：窗口里手动分屏时为 true，不做「两半够不够大」的检查；脚本和 Agent 的分屏照旧检查。
  - `CloseTab` 加了 `expect`：用户同意关掉的那几个终端。标签里的终端变了就拒绝，什么都不停。
  - `MoveTab` 和 `ClosePane` 原样保留。
- 这些标签操作的处理代码挪进了 core 的 `model/tabs.rs`，`model.rs` 比原来短了 60 行。
- 窗口开终端时，先发 `Launch`，再按情况发 `CreateTab`、`SplitPane` 或 `ReplacePane`。两步都走 `deliver`；`Launch` 带着终端 id，重发不会多开，所以也算可以安全重发的请求。
- `scripts/visual-fixture.py` 和 `eval/gpu-bench/bench.py` 也改成了新的请求形状：编辑不再带 `revision`，`PutTab` 改成 `CreateTab`。
- 已验：
  - core 单测 3 个：
    - 先建一个两窗格的标签，再把 Agent 分屏、改名、拖分隔线三个改动按 3 种顺序依次应用，三个改动都在；
    - 分隔线所在的结构变了，拖动被拒；
    - Agent 新开分屏后，按旧名单关标签被拒；
    - 窗格可以互换、跨标签移动，被移空的标签会关掉；
    - 重复移动没有变化；新建标签不覆盖已有的。
  - 集成测试 `layout_changes_from_two_hands_all_stay` 用真宿主进程：
    - 窗口先记下它看到的标签；
    - 宿主收到 Agent 的分屏，以及窗口的改名和拖分隔线；
    - 三个改动都在；
    - 按窗口看到的旧名单关标签，被拒，三个终端都还在跑；按新名单再关，关掉了。
  - 全部测试通过；守卫基线里 `tabs.rs` 对 `tab.title` 的直接读取从 3 处降到 2 处。
- 没验：
  - 没在真窗口里拖窗格、拖分隔线、改名（不做模拟点击）。
  - 截图场景 `MOORING_SPLIT_EVIDENCE` 用不上：在 main 上它也在 menu 一步就失败了，而且隔离启动时没有预先建好那几个标签，截出来是空工作台。
  - 旧做法会丢掉 Agent 分屏，这一点是从代码推出来的，没有专门写测试复现：窗口用自己手里的旧副本整块覆盖宿主的标签，Agent 刚分出来的格子就没了。
- 没做：
  - 窗口忙时，开终端仍然直接丢弃，不排队。开终端本身是先 `Launch`、再摆放的两步组合，排队要连同界面状态（开在哪个标签、要不要接着启动 Agent）一起保存，这次没做。

### E 远程协议用信封（2026-11-04）：完成，手机端还没接

- 远程协议（`mooring remote`，手机和另一台电脑共用）新增三处，全部可选，旧客户端不受影响：
  - `hello` 可以带 `client`，填稳定的设备 id；
  - `send`、`keys`、`answer` 可以带 `request`；
  - `hello` 的回复多了 `requests: true`，告诉客户端这台机器支持去重。
- 两者都带时，宿主把这次写操作包成 `Request::Once`，id 由 `remote:<client>` 加 `request` 组成。用的还是 B 那张 `requests` 表：重发拿回第一次的结果，被拒的仍然被拒。
- `Request::Once` 只包打字、按键、回答审批。编辑仍然用 `Edit` 自己的 `request` 字段，好让记录和改动写在同一个事务里。
  - 这三种操作不改库。11-04 起先记「开始了」、再执行、再记结果：宿主恰好在中间被杀掉的话，重发不会再打一次字，而是回「不确定执行了没有」，让人看一眼再决定（宁可少打不多打）。
  - 同一时间只处理一个带 id 的操作，免得重发在第一次还没结束时就并排执行。
- `delivery::resendable` 把 `Once` 算作可以安全重发的请求。
- 已验：
  - 集成测试 `a_remote_write_sent_again_after_a_reconnect_is_typed_once`，起真宿主和真的 `mooring remote --stdio`：
    - 手机（client 是 phone-1）发出带 `request: r1` 的一句话，然后断开连接；
    - 重新连接后用同一个 id 再发一次，终端里这句话只出现 1 次；不带 id 的同一句话发两次，出现 2 次；
    - 一个被拒的按键，用同一个 id 重发，得到同样的错误。
  - 临时让服务端忽略 `request` 后，带 id 的那句出现了 2 次，测试失败。
  - 全部测试通过。
- 没做：
  - 手机 App 和桌面的远程客户端还没有带 `client` 和 `request`。手机要在 `hello` 里报设备 id、给每条写操作取号、断线后用同一个号重发（`docs/phone-app/spec.md` 已写上）。桌面在多机第 2 步做打字和审批时接上。
  - 远程连接上的设备操作记录（`access.record`）遇到重发时，会多记一条。

## 第 1 阶段小结（2026-11-04）

决定：采用。A–E 全部合进 main，B、C、D 已经换进日常用的 App。四条验收都有测试：

- Agent 持续输出时，连续标记完成 100 次，0 次被拒；
- 回执前断开再用同一个 id 重发，只生效一次（窗口、命令和远程都是）；
- 三处同时改布局，三个改动都在；
- 关标签确认之后多出分屏，关标签被拒。

没验的都在真窗口里：手点标记完成、拖拽、重试按钮。放弃条件都没有触发。
