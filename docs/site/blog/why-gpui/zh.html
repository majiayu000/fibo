Fibo 的终端为什么不用 Tauri + xterm.js：一轮测评后换成 GPUI + libghostty-vt 原生绘制

Fibo 要在一个窗口里同时挂 40 个 Coding Agent 会话，原计划是 Tauri + React + xterm.js，后台用 alacritty_terminal。一天的测评量下来，WebView 同负载内存约是原生 Ghostty 的 3.5 倍，alacritty_terminal 存 40 个会话要 1.29 GiB。Fibo 因此改成后台用 libghostty-vt 持有终端状态、窗口用 GPUI 在 GPU 上直接画格子，代价是长期维护一个 GPUI 补丁分支。

Fibo 是什么：一个给 Claude Code、Codex 这类 Coding Agent 用的原生工作台，开源（MIT）。每个会话是窗口里的一个真实终端，后台进程 fibo serve 持有全部终端，窗口关掉会话也不停。它的前身叫 Mooring，更早叫 Keepline，这篇里的测评发生在 Keepline 时期。安装：下载 DMG，或 brew install --cask majiayu000/tap/fibo。

01 要什么：40 个会话、4 个画面、不比 Ghostty 重 1.2 倍

Fibo 的目标用户同时开 10 到 40 个 Claude Code、Codex 会话。产品形态在 10-19 夜里定下：一个专门跑和管理 Agent 的 App，每个会话是 App 里的一个真实终端，原生 CLI 跑在 App 自己的 PTY 里。当时的要求原话是「需要一个高性能的终端类的产品」。

「高性能」要先变成能测的数。工作视图是「空间 + 标签 + 每个标签 2 到 4 个画面」，所以负载定成 40 个会话、同一标签 4 个画面可见、其余 36 个只在后台解析不绘制。预算定成相对值：同一台机器、同样负载下，总占用不超过 Ghostty 的 1.2 倍。另有两条绝对要求：窗口隐藏时不渲染，空闲时不轮询。

口径上吃过一次亏。最早一轮用 ps 的 RSS 估算，一个长期运行的 Ghostty 只有 121 MB；改用 phys_footprint（把显存和被压缩的内存都算进去）后是 800 MB。RSS 漏掉了 GPU 和压缩内存，比较图形程序时会严重低估。之后所有数字都按 phys_footprint 计，并把 WebKit、XPC、GPU 这些辅助进程算进被测集合；CPU 按累计 CPU 时间除以墙钟时间。

项目测评里的定义
负载40 个会话，4 个画面可见（2×2），每画面 120×40；窗口 1440×900 pt，Menlo 12 pt
内存被测进程集合的 phys_footprint 之和，每 5 秒采样，报中位数和峰值
CPU被测集合累计 CPU 时间 ÷ 墙钟时间，100% 等于一个核
预算相对同机同负载的 Ghostty ≤ 1.2 倍；两边 CPU 都低于 0.5% 时算「低于噪声」
重复每组 5 次，顺序打乱，报中位数；单次的初测只用来判断方向
负载来源合成输出，加一段 250 秒、1.5 MB 的真实 Codex 录制（4223 个同步输出帧，含大量光标定位和中文）

02 原方案：Tauri + React + xterm.js

上一代 Keepline 是 Bun 命令行、网页面板加一个 Tauri 菜单栏 App，发到 v1.1.4。10-19 写的终端工作台 Spec 顺着这套栈往下走，两条关键决定是：

  • D01：App 是主入口，沿用 Tauri + React，复用已有的工作台界面、菜单栏和通知。
  • D03：Rust 后台用 alacritty_terminal 解析 PTY，持有权威的终端状态；窗口里用 xterm.js 显示一份镜像，借它现成的输入、绘制、选择和输入法能力。

Spec 自己把 D03 标成「本方案最高风险的实现点」：后台要把 alacritty 的状态重新编码成 xterm.js 能吃的 VT 序列，快照要覆盖两套屏幕、滚动区、字素、光标、各种输入模式，还没有现成的序列化接口。

后台也有问题。Keepline 原来的 Bun 服务只观察 73 个会话，就常驻约 240 MB 数据，每 5 秒轮询扫描一次；Bun 运行时本身只有约 22 MB，重的是数据整份放在内存里和定时轮询。这一条和渲染路线无关，换成什么界面都躲不开，所以先定了另一件事：常驻部分全部收进一个 Rust 后台进程，会话记录按偏移增量读、事件驱动，Bun 不再常驻。

03 WebView 负对照：内存约 3.5 倍，大头在 GPU 进程

为了知道 WebView 这条路的底线在哪，先写了一个最小的 macOS 测试程序：系统 WKWebView 里放 xterm.js 6，和一个用独立配置新开的 Ghostty 跑同样的输出（中英混排、带颜色），同样按 phys_footprint 计。

场景内存（phys_footprint）CPU
Ghostty，1 个窗口，400 KiB/s289 MiB14%
WebView + xterm.js（WebGL），1 个画面，400 KiB/s1029 MiB，3.56 倍15%
WebView + xterm.js（WebGL），4 个画面各 100 KiB/s742 MiB，其中 WebKit GPU 进程 466 MiB23%
WebView + xterm.js（DOM 渲染），4 个画面各 100 KiB/s452 MiB128%，掉帧
WebView 窗口最小化，4 个画面各 100 KiB/s未记录0.3%

CPU 两边接近，差在内存，而且涨在 WebKit 的 GPU 进程里。这部分由 WebKit 的进程模型决定，跟 xterm.js 写得好不好关系不大：「一个画面一个 WebView」和「一个 WebView 里多个 WebGL 上下文」都绕不开。换 DOM 渲染内存降了，CPU 涨到 128%。最小化时 CPU 降到 0.3%，说明 WebKit 会节流看不见的内容；这一条后来进了所有候选的正确性清单，原生方案也必须做到「看不见就不画」。

这组是单次测量，没有按 5 次重复。测评记录里给的理由是：3.5 倍的差距远大于任何可能的测量噪声，1.2 倍的预算在内存上不可能达成，补测也推翻不了。WebView 路线在这一步否定，D01 和 D03 一起作废。

04 后台的终端状态：三个 VT 库

后台要同时持有 40 个会话的屏幕和滚动历史，还要能在窗口重新连上时把当前画面完整交出去。测评没有直接拿某个终端的整体，而是按层拆开：PTY、VT 解析与状态、Unicode、字体、GPU 渲染、输入法与键盘、滚动缓存、会话复用协议、界面框架、现成终端组件，一共 10 层，登记了 99 个条目（69 个候选、30 个参照）。VT 这一层进入实测的是三家：libghostty-vt（经 libghostty-rs 绑定）、原方案里的 alacritty_terminal 0.26.0、rio-vt 0.5.28。

几处细节：

  • esctest 的绝对失败数很高：esctest2 以 xterm 为准，大量用 DECRQCRA 读屏幕校验和，三家都不支持，所以只看相对差。alacritty 和 rio 比 Ghostty 多失败 59 项（DECRQM、DECRQSS、左右边距 DECLRMM 相关的光标移动等），反过来只有 14 项。rio 和 alacritty 的失败集合完全相同，rio 的终端核心派生自 alacritty。
  • 一条结论被推翻了：合成的随机真彩 TUI 负载下，libghostty-vt 解析比 alacritty 慢 1.9 倍。换成真实 Codex 录制复测，三家差距在 7% 以内，libghostty-vt 最快。慢是负载造成的：每行一个随机 24 位色，样式表一直膨胀，真实 TUI 不这样。这条从结论里删掉，原始数据留着。
  • 解析 CPU 不构成区分：最坏情况 4 个画面各 100 KiB/s，解析只要约 0.5% 个核。

libghostty-vt 的代价也写在决策记录里：上游没有正式版本，快照接口只在 main 分支，必须锁 commit；绑定库是个人维护；构建要引入 Zig 0.16 工具链，而且 Cargo 的 debug 设置会把 Zig 部分编成 Debug，要显式设 LIBGHOSTTY_VT_SYS_OPTIMIZE=ReleaseFast；它静态带 simdutf，不能和同样带 simdutf 的 rio-vt 链进同一个二进制；要显式开 mode 2027，字形簇宽度才和 Ghostty.app 一致。

05 窗口：三个原型对 Ghostty

后台定了 libghostty-vt，窗口还要选。客户端和后台之间先写了一个最小的会话复用原型 kl-relay（40 个空闲会话 35 MiB、CPU 0.13%），然后做了三个客户端原型，都连同一个后台：

  • P1：GPUI + alacritty_terminal，作对照。GPUI 是 Zed 编辑器的 Rust 界面框架，锁 Zed v1.24.3。
  • P2：Swift + GhosttyKit（libghostty-spm），终端画面直接用 Ghostty 的整块组件。
  • P3：GPUI + libghostty-vt，客户端和后台用同一个 VT 引擎，GPUI 自己画格子。

第一批 3 次的数据作废了。命令行启动、没有 App 包的 GUI 程序，macOS 不保证把窗口放到最前；窗口一被挡住，GPUI 和 GhosttyKit 都停止渲染，同一场景的结果两极分化，比如 P2 空闲一次 284 MiB、一次 58 MiB。之后测试窗口一律设成浮动层级，并把「有负载但 0 帧、或 CPU 低于 1%」的那次自动标成无效。下面是 5 次有效重测：

不过线的是空闲那一列：GPUI 窗口什么都不画，CPU 也有 0.8%。

06 反直觉的一条：GPUI 空闲时比 Ghostty 费 8 倍 CPU

空闲 0.80% 对 0.10%，是 Ghostty.app 的 8 倍，超过 0.5% 的可忽略阈值。看源码加 sample 采样，原因在 GPUI 的 macOS 后端：窗口可见时，CVDisplayLink 按屏幕刷新率每帧唤醒一次，检查 invalidator.is_dirty()，没东西画也照样唤醒；只有窗口被遮挡时才停。所以 4 个画面在同一个窗口里只有一条显示链接，但这条链接永远不睡。

办法是给 GPUI 打补丁：连续若干个 vsync 没有新的绘制请求，就停掉显示链接；窗口一被标脏，立刻重启，下一个 vsync 出帧。下面是补丁的核心逻辑（简化过，去掉了锁和字段初始化）：

// 每个 vsync 的回调末尾
if pause_idle {
    if frame_demand {
        idle_frames = 0;
    } else {
        idle_frames += 1;
        if idle_frames >= idle_frames_limit {
            stop_display_link();
            paused_for_idle = true;
        }
    }
}

// 窗口被标脏时（新增的 frame_waker）
frame_demand = true;
idle_frames = 0;
if paused_for_idle {
    paused_for_idle = false;
    start_display_link();
}

门槛长短有讲究。第一版设的是 3 帧，空闲确实降下来了，4 个画面阵发输出却变差：

场景（P3，5 次中位数）不打补丁补丁，门槛 3 帧 + 60 fps 节流
空闲 CPU0.86%0.07%（Ghostty.app 的 0.70 倍）
1 画面真实 Codex CPU5.9%7.4%
4 画面真实 Codex CPU13.2%17.1%
4 画面真实 Codex 帧率34 fps48 fps

原因是 Agent 的输出是一阵一阵的：显示链接反复停、启，每次重启立刻出一帧，把原来被 vsync 合并的几次重绘拆成了好几帧。60 fps 节流没起作用，帧率本来就没到 60。结论是方向可行，门槛要放长。补丁的门槛做成了环境变量 GPUI_PAUSE_IDLE_FRAMES，默认 60 帧，在 120 Hz 的屏幕上约 0.5 秒。做决定时 0.5 秒这一档还没测。

不用 Fibo，自己比较终端也可以照这几条做：

  • 内存用 footprint 看 phys_footprint，不要用 ps 的 RSS；WebView 方案要把 com.apple.WebKit.GPU 等辅助进程加进来。
  • CPU 用累计 CPU 时间的差值除以墙钟时间，不要用 top 的瞬时值。
  • 被测窗口要保持在最前、不被遮挡；被挡住的窗口很多框架会停画，测出来的是假的低值。
  • 参照终端用独立配置新开一个实例（Ghostty 是 --config-default-files=false），不要测自己天天在用、开了很多窗口的那个。
# 一个进程某一刻的 phys_footprint（字节）
footprint -f bytes -p <pid>

07 四条路线放在一起

P2 在单画面 CPU 上最好，为什么还是选了 P3？当时两条路线各有一项不过或未知：GPUI 空闲 CPU 不过线，要靠补丁；P2 在 4 画面下资源偏高，真实 Codex 比 GPUI 多 15% 内存，合成高吞吐时 536 MiB / 39%。4 画面的 Ghostty 基准一直没测成，所以两边都判不了是否在 1.2 倍以内。剩下的理由是结构上的：

  • 前后台同一个引擎：后台已经用 libghostty-vt 持有全部状态，P3 的客户端只为看得见的 2 到 4 个画面再解析一遍，attach 时直接用 libghostty-vt 的快照，不用在两种实现之间对齐行为。
  • 全部是 Rust：后台、协议、窗口共用类型和代码，一套 cargo 工具链。GPUI 也有 Linux 后端，Fibo 的 Cargo.toml 在 Linux 上打开了它的 x11 / wayland 特性。
  • 界面是自写的：鸟瞰卡片、状态栏这些本来就要自己写，GPUI 的输入处理（NSTextInputClient，bounds_for_range 定位候选窗）在社区框架里最完整；winit 系框架的输入法只给一个光标矩形。

10-20 下午测试停在补丁复测这一步，路线定为 GPUI + libghostty-vt。Swift + GhosttyKit 留作备选，写下三个切换条件，任一满足就重新评估：中文输入法清单有项不过、一个迭代内修不好；空闲补丁维护不下去（上游重构显示链接导致补丁失效且没有替代），或调了门槛也无法同时满足空闲 ≤ 0.5% 和 4 画面阵发不变差；补测 4 画面基准后 GPUI 超出 1.2 倍而 P2 不超。

08 中文输入法：硬门槛怎么过的

定案时输入法一项都没测，原型里根本没实现输入法。这是测评里唯一写明的硬门槛，Zed 当时也有两个没关的中文输入法 issue（zed#59882 间歇失效、zed#53537 第三方输入法下快捷键失效）。所以第一版实现当天就得过这一关，过不了就换 P2。

第一版的做法：组字中的文字（marked text）只存在窗口内存里，不进 PTY，画在终端光标处，带下划线，组字时隐藏终端自己的块光标；候选窗位置由 bounds_for_range 返回，它和绘制、PTY 改尺寸用同一份字体实测值，范围按 UTF-16 换算，不拆代理对。实测 Menlo 单格 7.525635 × 20 px，中文字 advance 15.051269 px，两格是 15.051270 px，宽字符按两格对齐，字间不再留缝。

输入法这道门槛过了，没有触发备选。记录里也写明了没覆盖的部分：苹果自带拼音的全链路，自动操作那一轮没取得合格证据（按键送到了窗口，系统输入法没有接管）；选字、回车、退格在更早一轮有人工确认，候选窗和两画面切换是用第三方拼音输入法手测的。

09 代价：一个月后的补丁分支

选 GPUI 时就知道要长期维护补丁。到 11-28，Fibo 仍锁在测评时的同一版本：Zed v1.24.3（2a857f5）和 libghostty-rs 0ef8041，由 bootstrap.sh 拉取并按顺序打补丁。补丁从测评时的 1 个变成了 6 个：

补丁做什么行数
gpui-idle就是上面那个空闲停显示链接；Fibo 启动时默认打开（GPUI_PAUSE_IDLE_DISPLAY_LINK=1）89
gpui-retained-backbuffer保留后台缓冲，只重画两帧之间变了的区域，一个转圈的动画只重画几个格子820
gpui-present-render-pass后台缓冲复制到屏幕时，把 blit 换成渲染通道：窗口图形内存 408.4 → 248.4 MB，总占用约 570 → 385 MB110
gpui-retained-group-rects把多处局部损伤合并进一个 Metal 渲染通道189
gpui-fit-truncated-row文字被截断时给省略号107
gpui-glyph-dilation让一段文字用固定的字形加粗值，不按颜色自动加粗；Fibo 的终端绘制里有一处用它关掉加粗47

6 个补丁文件一共 1362 行，大头是保留后台缓冲。present-render-pass 那条很典型：Metal 驱动在进程第一次用 blit 时多留了 20 块 8 MB 的缓冲，只要窗口一直在画就不还，写一个几十行的最小 Metal 程序也能复现。换成渲染通道后，真实窗口 194 帧里屏幕缓冲和后台缓冲逐字节一致。框架是自己能改的，这类问题才能在自己这一层修掉；代价是每次想升级 GPUI，这 6 个补丁都要重新对一遍，所以至今没升。

为了不让改动悄悄把性能改回去，窗口的重画开销现在有一道 CI 门禁：真机上按每帧退休指令数比基线，超 15% 就失败（CI 的虚拟机读不到指令数，退回比例检查），细节在仓库的 docs/performance/。

限制：还没测到的

  • 4 画面没有 Ghostty 基准：Ghostty.app 的 4 分屏需要自动化权限，一直没测成。GPUI 4 画面是否在 1.2 倍以内，测评结束时未知。
  • GPU 时间、耗电、输入延迟没测：耗电的脚本写了没跑，输入延迟只定了方法。
  • Claude Code 的全屏重绘没有真实录制：只录了 Codex，Claude Code 的全屏重绘只有合成负载。
  • 空闲门槛 0.5 秒那一档：定案时没测，这篇也没找到之后在 4 画面阵发输出下的复测数据。
  • WebView 那组是单次：每个场景 1 次、1 个采样点。差距是 3.5 倍，方向不会变，具体数字有误差。
  • 机器在负载下测的：测评自己的规则是 1 分钟负载均值超过 4 就作废，实际测量时是 8 到 26。比值都在同一批次里算，CPU 用累计时间，但绝对值会偏高。
  • 原始数据没公开：测评的 results/ 原始数据、原型和脚本在旧仓库的本地提交里，这篇的数字取自其中的汇总表和决策记录。

总结：三条做法

  • 先把「高性能」写成相对预算：同机同负载不超过 Ghostty 的 1.2 倍，内存只认 phys_footprint。这一条让 WebView 路线在一组 1029 对 289 MiB 的数字上就被否定。
  • 按层测，后台和窗口分开选：10 层、99 个条目。后台选 libghostty-vt 看的是 405 MiB 对 1.29 GiB、可压到 66.5 MiB、有完整快照；窗口选 GPUI 看的是 1 画面 0.91 倍内存、0.55 到 0.60 倍 CPU。合成负载得出的「慢 1.9 倍」用真实录制复测后删掉了。
  • 自己能改的框架，要准备好一直改下去：空闲 CPU 从 0.8% 降到 0.07% 靠一个 89 行的补丁；一个月后补丁有 6 个、1362 行，GPUI 一直锁在 v1.24.3。中文输入法写成硬门槛并留好 Swift 备选，第一版当天就过了这一关。
