一个窗口，管多台电脑上的终端

Coding Agent 一多，终端就不只在一台电脑上：长任务放在常开的 Mac mini 上，笔记本上也开着一排。Fibo 要做的是多台电脑、一个窗口：另一台 Mac 上的终端，和本机的一样开标签、一样分屏、一样打字，侧栏一眼看到每台电脑上谁在等你。这篇讲为什么这样做、背后的原理，以及在一条只有 54 KB/s 的慢链路上，一次刷新怎么从 3.59 MB 降到 660 字节。

为什么要做

Fibo 是一个原生 macOS 工作台：Claude Code、Codex 这些 Agent 在真终端里并排跑，侧栏告诉你哪个在等你。终端不归窗口管，归一个常驻的后台进程（fibo serve）：关掉窗口、更新 App，终端都还在。

Agent 多了，一台电脑就不够用，终端会分散在好几台电脑上。理想的样子是：不管终端在哪台电脑上，都在同一个窗口里打开、分屏、打字，和本机没有区别。下文把另一台电脑叫"远端 Mac"。

最早的远程是另起一套：窗口经 ssh host fibo remote --stdio 用手机那套协议连过去，每个终端拿回一张卡片，有标题、状态和目录。本机和远程拿到的东西完全不同：

本机远程（当时）
连接本机 Unix socket，原生协议ssh 进去跑手机协议
拿到的数据整个工作区：空间、标签、分屏、会话、待办每个终端一张卡片，没有标签和布局
能做的事85 种请求：分屏、移窗格、改名……看、打字、审批、开关终端、标完成

于是远程每补一样本机已有的功能，就要再写一遍界面。我们在一个 PR 里给远程补了主区域、开始页和分屏，自动审查（Codex）一天就提了 11 条意见，全部出在两套代码的接缝上：焦点落到被盖住的本机窗格、⌘W 关掉了看不见的本机 shell、⌘[ ⌘] 走的是本机布局、机器列表一变，开始页就指错电脑。

规格里早写过一条放弃条件：如果 App 要为本机和远程维护两套越走越远的终端代码，就改成只留一套。我们关掉了那个 PR（#340）。

别人怎么做

动手前先看了同类产品：

产品状态在哪怎么连
VS Code Remote-SSH远程的 VS Code Server本地界面经 SSH 连过去，和连本机同一套
Zed 远程开发远程的 zed-remote-server调用系统 ssh
WezTerm 多路复用远程的多路复用服务经 SSH 连远程 Unix socket，本机和远程的标签能在同一个窗口
iTerm2 + tmux -CC远程 tmux把 tmux 控制协议翻译成原生标签

前三家的共同点是：状态留在那台，本地只是界面，用的是和连本机同一套协议，没有谁另造一套摘要协议再在本地补界面。iTerm2 翻译别人协议的做法，最像我们刚关掉的那条路，也是用户抱怨最多的。

原理一：终端住在后台，窗口只是客户端

Fibo 本来就是客户端和服务端分开的。后台持有终端、工作区和状态规则；窗口经 Unix socket 发请求，协议是带长度前缀的 JSON 帧；每个终端窗格单独一条连接，收画面、发按键。

所以连另一台电脑，并不需要新协议，只要能连上那台的 socket。OpenSSH 能直接转发 Unix socket：

ssh -N -o Compression=yes -o StreamLocalBindUnlink=yes \
    -L ~/.local/share/fibo/m/mac-mini/workbench.sock:<那台的 workbench.sock> mac-mini

窗口照连本机的方式连这个本地 socket，后面就是同一套代码：标签、分屏、⌘T、⌘D、运行 Agent。那台的后台存下这些标签和分屏，那台自己的窗口也看得到。一条 ssh -L 上可以跑任意多条连接，正好对上一个窗格一条连接。

真正踩坑的是那些写死"后台就在本机"的地方：

  • 旧后台检测。窗口发现后台的程序和自己不是同一个构建，就当它是旧版，要么接管它的终端，要么按它报的 pid 把它停掉。连另一台时，这个 pid 是那台的进程号，在本机上可能是任何一个程序。我们加了挂接模式：别人的后台一律不启动、不停止、不替换。
  • 本机文件系统。开终端前，窗口会先查目录在不在，不在就退回本机 home，结果被那台的后台拒绝。挂接时改成交给那台去判断。
  • socket 在哪。由那台自己说（fibo socket）；没有这个命令的旧版本，就按旧的运行目录去找。

原理二：一套界面，每台电脑是一个数据来源

第一版是这么做的：点远端 Mac 的空间，就给它建一整份工作台，再把整个窗口交给它去画。数据和界面在同一个结构里，复制数据的同时，界面也被复制了一份。那份工作台以为自己是唯一一台，侧栏也画成单机的样子：本来只想打开另一台的一个空间，结果整个窗口都变了样，回来还得找入口。

正确的拆法是两层：

每台电脑一份（数据来源）每个窗口一份（界面）
连接和请求队列侧栏：筛选、折叠、滚动位置
那台的整个工作区鸟瞰、搜索、⌘J 的排序
那台的终端窗格主题、字号、快捷键
在那台选的空间、标签和焦点当前看的是哪台

本机就是第 0 台，和别的电脑走同一条路。侧栏读所有电脑的工作区，用和本机同一套状态规则按电脑分组，切到哪台都不动；主区域只画当前那台。⌘J（跳到下一个要你处理的）跨电脑按同一套规则排序。

顺手还去掉了一条连接。原来侧栏里远端 Mac 那一组是经手机协议拿的卡片，点进去以后主区域又经原生协议连一次：同一台电脑两条连接、两份状态，侧栏和主区域看到的可能不是同一个时刻。现在每台电脑只剩一条 ssh -L。

这一部分前后分成几个 PR：#349 侧栏不跳，#352 启动就连上各台，#353 侧栏读各台自己的工作区，#354 看板和 ⌘J 跨电脑。

慢链路：从 3.59 MB 到 660 字节

同步方式本来很简单：后台的工作区一变，就经状态连接推一个版本号；窗口发现自己落后了，就要一份完整的工作区，连续几次变化合并成一次。本机上一份 1.6 MB 的 JSON，一次不到 10 毫秒，从来不是问题。

直到有一天，到一台远端 Mac 的网掉到约 54 KB/s。那台有几百个会话，工作区约 3 MB，每变一次都要整份过一遍链路。偏偏打字也走这条 ssh，按键被排在几 MB 的 JSON 后面，界面上的延迟显示 1765 ms。我们分三步把它缩下来。

第一步：压缩，并且别太早放弃

先给转发开 Compression=yes：同一条链路上，3 MB 从约 35 秒降到约 11 秒。另一个问题是，后台写回复时只要 5 秒一个字节都没写出去，就断开连接，在慢链路上一份工作区根本传不完。我们把超时放到 30 秒，而且只在一个字节都写不出去时才计时，写着在走的不受影响（#358）。

这一步只解决了"连得上"，没解决"卡"。每次变化仍要 10 多秒。

第二步：只发变了的会话

本机实测，一份工作区约 98% 是会话和每个会话的内容。所以协议加一种请求：窗口把刷新、编辑和启动都包成 Brief(上次那份的编号, 原来的请求)，后台按会话和内容逐个比对，只回变了的部分；窗口把变化拼回整份，再交给界面。界面代码一行没改，它拿到的仍是一份完整的工作区。

struct Delta {
    stamp: u64,              // 这份是哪份：由内容的哈希算出
    base: Option<u64>,       // 对着哪份比的；None 表示整份
    sessions: Vec<Session>,  // 新的或变了的会话
    order: Option<Vec<Id>>,  // 顺序变了才带
    content: Map<Id, Content>,
    gone: Vec<Id>,           // 没了的
    rest: …,                 // 工作区的其余部分
}

几个设计点：

  • 编号用内容的哈希，不用版本号。后台重启以后，版本号会从头再数，可能和窗口手里那份撞号；内容哈希不会。
  • 两边都留几份。后台记最近 16 份发出去的索引，够本机窗口、菜单栏和别的电脑的窗口一起用；窗口记 3 份，因为一次刷新和一次操作可能同时在路上，后回来的那个还要对着上一份拼。
  • 底稿丢了就要整份。窗口手里没有回复所对的那份，就再发一次，明确要整份。
  • 旧后台不会收到它看不懂的请求。旧后台遇到读不懂的请求会断开连接。所以新后台在状态里报一个 brief 能力，窗口看到它才发 Brief；只升级一边时，照旧发整份。

同时加了限频：对另一台电脑，一次刷新用了多久，就再等多久才做下一次，最多等 10 秒。这样链路至少有一半时间留给打字；本机不等（#362）。

在本机数据上量，一次刷新从 1.6 MB 降到 14 KB。

第三步：再量一次，发现其余部分也不小

第二步的提交里，我们明确否决过"其余字段也按字段比"：工作区 98% 在会话里，其余的整份发更简单。两台都换上新版后，我们在真实的远端 Mac 上又量了一次：

其余部分里最大的字段大小
终端列表（677 个）186 KB
任务日志81 KB
结果历史66 KB
任务39 KB
Agent 启动记录36 KB

本机只有 4 个终端，其余部分不到 3 KB，所以本机的测量看不出来。远端 Mac 上，一次刷新即使没有任何会话变化，也有 352 KB。

要不要细到每个终端？我们先用最便宜的办法看了一下：两分钟里取 12 次，这些字段一次都没变。它们只在开关终端、任务结束时才变。所以按顶层字段比就够了：后台给每个字段算一个哈希，只回哈希变了的字段，窗口把它们盖到后台上次发来的那份上（#380）。

这里有一个容易出错的地方：窗口自己会改它手里那份工作区，比如拖分隔条时先改一下预览。如果把回复盖到这份被改过的上面，没出现在回复里的字段就会把本地的改动留下来。所以窗口另外留着后台原样发来的那份，只往那份上盖。

协议兼容又走了一遍同样的路：Brief 是一个两元素的元组变体，旧后台读不懂多一个元素的元组，会直接断开连接。所以加的是一个新请求 BriefAll，加一个新能力 brief_all；回复里的 rest 在线上仍是一个工作区对象的样子，旧窗口照样读得懂。还有一个测试守着一个前提：工作区的每个顶层字段即使是空的也会写出来。否则"回复里没有"就分不清是"没变"还是"变空了"。

最后一条里剩下的，基本就是那一两个变了的会话本身，外加一个 revision 字段。在 54 KB/s 的链路上，压缩后约 420 字节只要几毫秒就传完，原来是十几秒。打字不会再排在它后面。

谁拿着键盘

两个窗口可以同时开着同一个终端：本地的窗口和远端 Mac 自己的窗口。两边同时打字，字会交错，所以同一时刻只有一个窗口能输入，另一边显示"只读 · 点击接管输入"。

原来的规则是先拿到的一直拿着。可实际情况往往是：你在那台上开过这个终端，回到本地的窗口想接着打字，却发现是只读的。我们改成后开的接管：哪个窗口新打开这个终端，输入就归哪个。偷看是例外：只是瞄一眼，第一次打字才接管。

这个改动上线当天就被另一轮审查抓到一个问题：窗口启动时，会给每台电脑在后台建一份工作台，给侧栏供数据。这份没画出来的工作台也按"正在显示"行事，一启动就挂上了那台第一个标签的所有终端，并且接管了输入。你还没点过那台电脑，它那边的窗口就变成了只读。修法是让工作台知道自己是不是正被画出来：没画时不建窗格；被画出来的那一帧才补建窗格、接管输入（#367）。

换版本不断终端

两台都要换上新版，新协议才会生效。换版本时后台要换成新程序，终端不能断，因为里面跑着几十个 Agent。

新程序启动时带 --takeover：旧后台把每个终端交给新后台，然后自己退出。新版窗口打开时，如果发现后台是旧的，也会自动走这一步。这次在远端 Mac 上换版本，日志里是 handed 43 terminals to a newer host，43 个终端一个没断。

几条心得

  • 先找到差异从哪来，再决定补还是统一。远程的问题看起来是一个个界面 bug，根子是两套协议、两套界面。补得越多，接缝越多。
  • 数据和界面分开放。"每台一整份工作台"之所以出问题，是因为数据和界面住在同一个结构里，复制数据的同时把界面也复制了。
  • 在真数据上量，而且换上以后再量一次。"其余部分很小"在本机是对的，在有 677 个终端的那台就不对了。第二次测量花了两分钟，省掉了后来的猜测。
  • 协议改动先想旧的那一边。旧后台读不懂新请求会断开，所以每一步都由能力标记打开；只升级一边时，一切照旧。
  • 用真机器验收。每一步都有证据脚本，在假 ssh 和真实的远端 Mac 上各跑一遍：侧栏切换前后截图逐像素比较，数 ssh 连接条数，数交接的终端数。

还没做的：打字回显的 p95 超过 200 ms 才做本地预测回显（像 WezTerm 那样），目前没有必要；那台的终端里点文件链接在本机打开编辑器，也还没有做。
