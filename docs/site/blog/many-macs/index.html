One window for terminals on every Mac

Run enough coding agents and their terminals stop fitting on one machine: long tasks go to an always-on Mac mini while the laptop runs a row of its own. Fibo's goal is many machines, one window: a terminal on another Mac opens, splits and takes typing exactly like a local one, and the sidebar shows who is waiting on every machine. This post covers why we built it this way, how it works underneath, and how, on a link of 54 KB/s, one refresh went from 3.59 MB to 660 bytes.

Why we did it

Fibo is a native macOS workbench: Claude Code, Codex and other agents run side by side in real terminals, and the sidebar tells you which one is waiting for you. The terminals don't belong to the window. They belong to a background host (fibo serve), so closing the window or updating the app leaves them running.

With enough agents, one machine isn't enough, and terminals end up spread across several. The goal: wherever a terminal runs, open it, split it and type into it from the same window, with no difference from local. Below, the other machine is called "the remote Mac".

The first remote was a separate path. The window ran ssh host fibo remote --stdio and spoke the phone protocol, getting back one card per terminal: title, state, folder. Local and remote saw very different things:

LocalRemote (then)
ConnectionLocal Unix socket, native protocolssh in, phone protocol
DataThe whole workspace: spaces, tabs, splits, sessions, to-dosOne card per terminal, no tabs or layout
What you can do85 kinds of request: split, move a pane, rename…Watch, type, approve, open and close terminals, mark done

So every local feature the remote needed had to be written again. One PR that gave the remote a main area, a start page and splits drew 11 comments from automated review (Codex) in a single day, every one of them at the seam between the two code paths: focus landing on a hidden local pane, ⌘W closing a local shell you couldn't see, ⌘[ and ⌘] following the local layout, the start page pointing at the wrong machine after the machine list changed.

The spec already had a stop condition for this: if the app ends up maintaining two drifting sets of terminal code for local and remote, keep only one. We closed that PR (#340).

What others do

Before writing code we looked at how others handle it:

The first three agree: state stays on the remote machine, the local side is only UI, and it speaks the same protocol it uses locally. None of them invents a summary protocol and rebuilds the UI on top. iTerm2's translation approach is the closest to the path we had just abandoned, and it's also the one users complain about most.

How it works, part 1: terminals live in the host, the window is a client

Fibo was already split into client and server. The host owns the terminals, the workspace and the state rules; the window sends requests over a Unix socket using length-prefixed JSON frames, and every terminal pane opens its own connection for screen updates and keystrokes.

So reaching another machine needs no new protocol, only a way to reach that machine's socket. OpenSSH forwards Unix sockets directly:

ssh -N -o Compression=yes -o StreamLocalBindUnlink=yes \
    -L ~/.local/share/fibo/m/mac-mini/workbench.sock:<its workbench.sock> mac-mini

The window connects to that local socket the same way it connects to its own, and from there it's the same code: tabs, splits, ⌘T, ⌘D, running an agent. The other host stores those tabs and splits, so that machine's own window sees them too. One ssh -L carries any number of connections, which fits one connection per pane.

The real traps were the places that assumed the host is on this machine:

  • Stale-host detection. When the window finds a host running a different build, it treats it as outdated and either takes over its terminals or stops it by the pid it reports. Across machines that pid belongs to the other Mac and could be any process here. We added an attached mode: a host that isn't ours is never started, stopped or replaced.
  • The local file system. Before opening a terminal the window checked that the folder exists and fell back to the local home when it didn't, which the other host then refused. When attached, the other host decides.
  • Where the socket is. The other machine says (fibo socket); older versions without that command are found by their old runtime folder.

How it works, part 2: one UI, each Mac a data source

The first version worked like this: click a space on the remote Mac, build a complete workbench for that machine, and hand the whole window to it. Data and UI lived in one structure, so copying the data copied the UI too. That workbench believed it was the only machine, and drew the sidebar that way: you meant to open one space on another machine, the whole window changed, and getting back meant hunting for the way out.

The right split has two layers:

One per machine (data source)One per window (UI)
Connection and request queueSidebar: filters, collapsed groups, scroll position
That machine's whole workspaceOverview, search, the order of ⌘J
That machine's terminal panesTheme, font size, shortcuts
The space, tab and focus picked thereWhich machine is shown

This Mac is machine 0 and takes the same path as the others. The sidebar reads every machine's workspace and groups them with the same state rules, and it never moves when you switch; the main area draws only the current machine. ⌘J, which jumps to the next session that needs you, orders across machines by the same rules.

We also dropped a connection along the way. The remote Mac's group in the sidebar used to come from phone-protocol cards, while the main area connected again over the native protocol: two connections and two copies of state for one machine, so the sidebar and the main area could show different moments. Now each machine has exactly one ssh -L.

This landed as several PRs: #349 keeps the sidebar in place, #352 connects to every machine at start, #353 has the sidebar read each machine's own workspace, and #354 takes the board and ⌘J across machines.

The slow link: from 3.59 MB to 660 bytes

Syncing was simple. When the host's workspace changes it pushes a revision number over the status connection; a window that is behind asks for the whole workspace, with bursts of changes merged into one request. Locally that's 1.6 MB of JSON in under 10 ms, never a problem.

Then the link to one remote Mac dropped to about 54 KB/s. That machine has hundreds of sessions and a workspace of about 3 MB, sent whole on every change. Typing went over the same ssh, so keystrokes queued behind megabytes of JSON, and the window showed 1765 ms of latency. We brought it down in three steps.

Step 1: compress, and don't give up too early

First, Compression=yes on the forward: on the same link, 3 MB went from about 35 seconds to about 11. Second, the host dropped a client whenever 5 seconds passed without a byte of a reply written, so on the slow link a workspace never finished. We raised that to 30 seconds and count only time in which not a single byte goes out, so a write that is moving is never cut off (#358).

That made the machine reachable again, but not responsive. Every change still took more than 10 seconds.

Step 2: send only the sessions that changed

Measured locally, about 98% of a workspace is sessions and their content. So the protocol gained a request: the window wraps refreshes, edits and launches as Brief(stamp of the last one, original request), the host compares session by session and content by content, and replies with only what changed. The window rebuilds the whole workspace before handing it on, so not a line of UI code changed; it still receives a complete workspace.

struct Delta {
    stamp: u64,              // which workspace this is: a hash of its content
    base: Option<u64>,       // what it was compared against; None means whole
    sessions: Vec<Session>,  // new or changed sessions
    order: Option<Vec<Id>>,  // only when the order changed
    content: Map<Id, Content>,
    gone: Vec<Id>,           // sessions that went away
    rest: …,                 // everything else in the workspace
}

A few design points:

  • Stamps hash the content instead of using the revision. A restarted host counts revisions from the start again and could collide with the one a window holds; a content hash can't.
  • Both sides keep a few. The host remembers the last 16 indexes it sent, enough for this Mac's window, the menu bar and other machines' windows together. The window keeps 3, because a refresh and an action can be in flight at once and whichever returns second still needs the earlier base.
  • No base, ask for the whole. If the window no longer holds the workspace a reply was built against, it asks again, explicitly for the whole.
  • Old hosts never see a request they can't read. An older host drops the connection on an unknown request, so the new host advertises a brief capability in its status and the window sends Brief only when it sees it. With one side updated, everything goes whole as before.

We also throttled refreshes: for another machine, after a refresh the window waits as long as that refresh took (at most 10 seconds) before the next one, so typing gets at least half the link. The local machine doesn't wait (#362).

On local data, one refresh went from 1.6 MB to 14 KB.

Step 3: measure again, and the rest isn't small

The step-2 commit explicitly rejected diffing the other fields as well: 98% of a workspace is sessions, so sending the rest whole is simpler. With both machines updated, we measured again on the real remote Mac:

Largest fields in the restSize
Terminal list (677 terminals)186 KB
Task logs81 KB
Outcome history66 KB
Tasks39 KB
Agent launch records36 KB

This Mac has 4 terminals and a rest under 3 KB, which is why the local measurement missed it. On the remote Mac, a refresh with no session changes at all still carried 352 KB.

Should we diff down to each terminal? We tried the cheapest check first: 12 samples over two minutes, and none of those fields changed once. They change when a terminal opens or closes, or a task ends. So diffing by top-level field is enough: the host hashes each field and sends only those whose hash changed, and the window lays them over the copy the host last sent (#380).

One trap here: the window edits its own copy of the workspace, for example the preview while you drag a divider. Lay a reply over that copy, and any field missing from the reply would keep the local edit. So the window also keeps the copy exactly as the host sent it, and only ever lays replies over that one.

Compatibility took the same path again. Brief is a two-element tuple variant, and an older host can't read a tuple with an extra element; it would drop the connection. So it's a new request, BriefAll, with a new capability, brief_all. The reply's rest still looks like a workspace object on the wire, so older windows read it as before. A test guards one assumption: every top-level field of a workspace is written even when empty. Otherwise a field missing from a reply could mean either "unchanged" or "now empty".

What's left in the last bar is essentially the one or two sessions that changed, plus the revision field. On a 54 KB/s link, about 420 compressed bytes take a few milliseconds instead of more than ten seconds. Typing no longer waits behind a refresh.

Who holds the keyboard

Two windows can have the same terminal open: the local one and the remote Mac's own. Typing from both at once would interleave the keystrokes, so only one window has input at a time, and the other shows "Read only · click to take over input".

The old rule was that whoever got input first kept it. In practice that meant: you'd opened the terminal over there, came back to the local window to keep typing, and found it read-only. We switched to "the one opened last takes over": whichever window newly opens the terminal gets its input. Peeking is the exception; a glance takes nothing until your first keystroke.

Another review caught a problem with that change the day it shipped. At start, the window builds a workbench for every machine in the background to feed the sidebar. Those undrawn workbenches behaved as if they were on screen: they opened every terminal in that machine's first tab and took over its input. You hadn't clicked that machine yet, and its own window had already gone read-only. The fix is for a workbench to know whether it's being drawn: undrawn, it builds no panes; in the frame it first appears, it builds them and takes input (#367).

Updating without dropping terminals

The new protocol only works once both machines run the new version. Updating means replacing the host with a new program, without dropping the terminals inside it, because dozens of agents are running there.

The new program starts with --takeover: the old host hands every terminal to the new one, then exits. A new window that finds an older host does this on its own. When we updated the remote Mac this time, the log said handed 43 terminals to a newer host, and all 43 kept running.

What we took away

  • Find where the difference comes from before choosing to patch or unify. The remote's problems looked like a string of UI bugs. The root was two protocols and two UIs, and every patch added more seams.
  • Keep data and UI apart. "One complete workbench per machine" went wrong because data and UI lived in one structure, so copying the data copied the UI.
  • Measure on real data, then measure again after it ships. "The rest is small" was true on a machine with 4 terminals and false on one with 677. The second measurement took two minutes and replaced a lot of guessing.
  • For every protocol change, think about the old side first. An older host drops connections on requests it can't read, so each step is switched on by a capability flag, and with only one side updated nothing changes.
  • Accept on real machines. Every step has an evidence script, run against a fake ssh and against the real remote Mac: sidebar screenshots compared pixel by pixel before and after switching, ssh connections counted, handed-over terminals counted.

Not done yet: local predictive echo, the way WezTerm does it, only if typing echo goes above 200 ms at p95, which it hasn't needed to. Clicking a file link in the other machine's terminal to open your editor here isn't done either.
