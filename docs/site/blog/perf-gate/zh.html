Fibo 的性能门禁：数退休指令而不看 CPU 时间，以及侧栏重画这本账

Agent 输出时窗口每帧都在重画，可同一帧的 CPU 时间会随机器负载差 2.5 倍，拿它做门禁要么误报要么漏报。我们发现退休指令数在不同负载下差不到 1%，于是门禁在真机上按指令数设 15% 的线，在读不到指令数的 CI 虚拟机上改查同一进程里的比例。用这把尺子，终端输出帧从 7430 万条指令降到 452 万，大半省在侧栏。

Fibo 是什么：一个给 Claude Code、Codex 这类 Coding Agent 用的原生 Mac 工作台，开源（MIT），用 Rust、GPUI 和 libghostty-vt 写成。窗口左边是会话侧栏，右边是终端。Agent 一输出，终端就要出一帧，所以「一帧花多少」直接决定窗口占多少 CPU。安装：下载 DMG，或 brew install --cask majiayu000/tap/fibo。

01 问题：CPU 时间不能当尺子

想让「窗口别变慢」成为每个 PR 都过的一道检查，先要有一把稳定的尺子。最顺手的是 CPU 时间：跑 300 帧，算每帧几毫秒。我们最早就是这么量的，很快发现它跟着机器的忙闲走。Fibo 的开发机上常常同时开着好几个 Agent 在编 Rust，负载从个位数到上百都有。

同一个版本、同一帧，机器负载 6 时和负载 40 时，CPU 时间差 2.5 倍（探针代码的注释里记的是同一帧 1.1 ms 和 2.7 ms）。原因不复杂：忙的时候进程会被排到能效核上，频率也会降，同样的活要多花时间。但 CPU 真正执行完的机器指令条数，也就是退休指令数（retired instructions），基本不变。下表把仓库记录和这次重测放在一起：

02 怎么数：每帧的退休指令数

macOS 上，进程可以用 proc_pid_rusage 读自己到现在退休了多少条指令。Fibo 的窗口有一个只在探针构建里编进去的模块，在帧前后各读一次，相减再除以帧数（下面是简化过的代码）：

/// 读本进程退休的指令数。和 CPU 时间不同：同样的活，
/// 在忙的机器上、能效核上、降频时都数出一样的数。
fn instructions() -> u64 {
    if std::env::var_os("MOORING_PERF_NO_COUNTER").is_some() {
        return 0; // 在真机上模拟虚拟机，测门禁自己的退路
    }
    let mut info: libc::rusage_info_v4 = unsafe { std::mem::zeroed() };
    let ok = unsafe {
        libc::proc_pid_rusage(std::process::id() as i32,
                              libc::RUSAGE_INFO_V4, (&raw mut info).cast())
    };
    if ok == 0 { info.ri_instructions } else { 0 }
}

// 一个阶段：画 300 帧，报每帧的 CPU 时间和指令数
let (cpu, ins) = (cpu_secs(), instructions());
/* ……画 300 帧…… */
let per_frame = (instructions() - ins) as f64 / 300. / 1e6; // M 条/帧

量什么也要定下来。探针用一个造出来的测试工作区：2000 个会话、8 个空间、60 个终端都绑了会话、侧栏约 45 行，接近长期使用的真实安装（scripts/perf-fixture.py，不调模型、不碰用户数据）。窗口不上屏，按阶段各画 300 帧，最主要的两个阶段是：

  • frames-pane：只有终端变了的一帧。Agent 输出时每帧都是它，最常见。
  • frames-main：强制整窗重画。工作区每变一次（真实使用约每秒 1.4 次），侧栏就整个重画一次，代价接近它。

另外还有滚一行中文（frames-scroll）、侧栏动画、机器栏、插件页、设置页、启动到首帧等阶段，共 25 项进基线文件 crates/fibo-app/perf-baseline.txt。

找大头的两种办法

指令数稳定之后，找原因的办法也跟着变简单：

  • 去掉一块量一次：临时让某块界面不画（比如侧栏返回空），看指令数掉多少。「侧栏占终端帧 88%」「去掉『今天』那 50 行，整窗重画 96 M → 16.5 M」都是这么量出来的。
  • 二分提交：门禁报警后，在单独的 worktree 里逐个提交编译、只跑一个阶段，几轮就能定位。下面第 04 节那次「侧栏套进横向 flex，整窗 75 → 130 M」就是这样找到的。

定位到视图之后，再用 sample 采调用栈：自身时间集中在 taffy::compute_flexbox_layout、line_wrapper，问题在排版；集中在业务函数和 SipHash，问题在每帧重复计算。

03 门禁：真机看指令数，虚拟机看比例

门禁是 scripts/perf-gate.py：在 CI 上单独编一份探针版 release，跑完各阶段，对基线比。它先判断这台机器读不读得到指令数（所有阶段的读数都大于 0，且没设 MOORING_PERF_NO_COUNTER），再走两条路之一。

虚拟机上的退路：同一进程里的比例

虚拟机读不到指令数，CPU 时间又不稳，那就让机器的快慢自己抵消：终端帧和整窗重画在同一个进程里前后挨着量，算终端帧 ÷ 整窗。机器忙，两个数一起变慢，比值基本不动。这个比值叫 pane-share，现在的基线是 0.12；侧栏每帧都重画的坏版本是 0.96。线定在基线的 2 倍。11-27 一次 main 的 CI 上读到 0.09。

比例的分子分母要挨着量。主题帧原先和开头单独量的一段终端帧比，中间隔了几秒，虚拟机在这几秒里忽快忽慢，同一套代码 theme-share 在 0.73 到 2.37 之间跳，一次超线变红。现在每个主题和原本的外观交替画 10 段、每段 30 帧，相邻两段算一个比值，取中位数。

只靠计时拦不住的，改成数次数

有几类 bug 和「每帧多贵」无关，而是「多画了几帧」或「画错了」。这些都改成按次数和像素断言，在虚拟机上照样拦得住：

  • 补画循环：最初数的是 5 秒里补画的总数，CI 机器有屏幕会自己出帧，正常版本也有 9–15 次，于是误报。改成数 bug 的直接特征「补画自己那一帧又排了补画」：正常版本恒为 0，坏版本 15（8678054）。
  • 分屏跳转亮圈淡完还在画：每帧指令数一点没变，变的是帧数。旧版亮圈消失后仍按 120 帧/秒请求重画，三窗格的测试里占一个核的 25.24%（#461）。门禁加了一项：亮着时必须请求帧，淡完后强制画一帧也不能再请求。
  • 滚一行中文：按交给 CoreText 的段数断言。正常一行 18 段，排字缓存失效的坏版本 774 段；0 段说明根本没滚，量的是静止画面。

基线只能跟着往下走

15% 的线是相对基线的。优化之后基线不降，门禁就悄悄松了。11-25 发现 frames-main 和 frames-railrest 比基线低了 25–27%，按 15% 预算要再涨 40% 以上才会报警，这两项等于没开（#568）。修法是只改这两行，取两次完整门禁里较高的一次：frames-main 55.35 → 41.32 M。没有用 MOORING_PERF_UPDATE=1 全量重写，因为那会把其他项 ±3–8% 的漂移一起写进基线。现在门禁在某项低于基线 15% 时会打印提示，提醒降基线。

门禁每个改到原生代码的 PR 都会跑，这次看的一轮 CI 约 10 分钟（含编译）。它目前不是合并的必过项：main 的规则只要求 Workbench Rust checks。这也是为什么规则 R7 要求动了渲染的人在真机上自己跑一遍。

大项目怎么做

门禁定型前，我们看过几个大开源项目的做法（11-04 调研，记在性能文档第 9 节；uv 的工作流 11-28 重新核对过）：

项目量什么拦 PR 吗
pandasasv 基准在专用机器上对每个合入的提交跑，事后用阶跃检测找变慢的提交不拦，官方说明同代码同机器结果也会差得明显
uvCodSpeed：专用机器上的 walltime 模式，加 simulation 模式（模拟执行，不受机器负载影响），结果贴回 PR可以
Rust 编译器（rustc-perf）默认指标 instructions:u，约 0.3% 的变化能稳定看出；每周人工看曲线人工判断
Zed（GPUI 的来源）CI 只编译 benchmark crate没看到性能门禁

共同点是：要在 PR 上拦，就得用和机器负载无关的指标（指令数或模拟执行）；用墙钟时间只能事后提醒。Fibo 的门禁照这个思路，真机用指令数；CI 上没有专用机器，只好退到同进程比例。

第一刀：终端输出不该让侧栏重排

11-03 之前，终端每输出一帧要 7430 万条指令。「去掉一块量一次」显示侧栏占了 88%。原因在 GPUI 的重画规则：cx.notify() 会把一个实体和它所有祖先标脏。窗格的观察回调里写的是 cx.notify()，等于终端每输出一次，整个工作台连同侧栏都重新排版。

b1438ae 把侧栏包成缓存视图（AnyView::cached）：没被标脏、边界不变时直接复用上一帧的绘制。窗格变化改为通知一个空的子视图 Tick，工作台照样重画标题栏和窗格标题，侧栏不动。侧栏要显示的其他变化，最多晚 1 秒由补画追上。终端帧 7430 万 → 1030 万，CPU 4.5 → 0.8 ms。11-19 标签栏也照此改成缓存视图，终端帧的基线从 6.96 M 降到现在的 4.52 M。

缓存会带来新的 bug 类型：侧栏该刷新时没刷新。所以同一个提交里加了 redraw-check：每一步都把「不刷新画的一帧」和「强制刷新画的一帧」逐像素比对。

贵的是每一行，不是行数

终端帧降下来以后，剩下的大头是整窗重画。11-16 在真实窗口上采样，侧栏重画占主线程约一半。先猜的是行太多，做了「只排看得见的行」的实验：夹具里只排前 20 行，整窗重画 91.6 M → 91.3 M，几乎没省。换成「去掉一块」：去掉「今天」那 50 行，96 M → 16.5 M，一行约 1.6 M。贵的是每一行本身。

原因在排版引擎 taffy：要算一个靠内容撑开的容器有多大，得把里面的东西量好几遍，每嵌套一层再乘一次。单行的会话行原来是「行 → 纵向容器 → 标题、空间、时间」。#365 让只有一行字的会话行少套这层纵向容器，行高直接给定为 ONE_LINE_ROW，整窗重画 105 M → 57 M（新旧交替两轮：104.7 / 105.5 → 57.0 / 57.2）。像素用 visual-check.py shots 比对过，外观不变。

同一个 PR 里还有两刀是纯计算。每个「先不管」的空间，每次重画都把全部会话过一遍，而且先算最贵的「属于哪个空间」（比路径）。把条件按便宜到贵排，先看会话开没开（大多数没开，立刻排除），3 个先不管空间时整窗 237 → 98 M；再把「重启时断掉的会话」表 lost_agents 收成集合，98 → 61.5 M。对 main 合计是 238.6 → 61.5 M。

放弃的方案也记在提交里：空间标签拆成两个子元素只省 3%，时间改成右对齐文字不到 2%，按放弃线没做；悬停提示改成悬停时才算约省 2.5%，但提示弹出时去读工作台，若那一刻工作台正被渲染占着会崩，不值。

回到真实窗口：24.3% → 8.1%

夹具上的指令数不能直接换算成用户看到的 CPU 百分比，所以每轮之后还要回到真实窗口采样。11-17 一次采样发现，侧栏渲染每 10 秒 1.4 s，其中 1.04 s 是在问 33 个空间的目录还在不在（stat）：同样 33 个目录，在终端里 stat 一遍才 28 µs，在 App 进程里慢得多。#386 按路径把结果记 2 秒，代价是目录删掉后最多晚 2 秒才标出来。

连同 #365、菜单栏改要增量（#376–#378）、后台增量回复沿用哈希（#388），换包前后同样在跑十几个 Agent 的真实窗口上：窗口 CPU 24.3% → 8.1%，每 10 秒的整窗绘制 2647 → 338 ms，侧栏渲染 1395 → 126 ms。这是一次前后对比，在跑的会话从 16 个变成 19 个，只能当粗对比。

两次没被每帧指令数拦住的回退

11-19 窗口又变卡。门禁基线和脚本都没变。查下来有一个来源是分屏跳转的亮圈：它先预约下一帧，再判断自己是否已经淡完，所以淡完以后仍按显示刷新率每秒请求约 120 帧。每一帧都很便宜，帧数却一直不停。#461 改成先判断再预约，同时给门禁加上「淡完后请求帧数为 0」这一项。教训是：每帧指令数只管「一帧多贵」，「多画了多少帧」要单独数。

另一次是滚屏。真实窗口采样里终端排字 shape_cell 占主线程约 5%（433/8980 个样本），多半在 CoreText 新建排版。排字缓存按「第几行第几段」存，内容一滚动全对不上；中文每个字是单独一段，于是 Agent 每输出一行中文，整屏重新排字。#398 在按位置找不到时，再按内容（文字、列宽、颜色、粗斜体）去上一帧的段里找：每行 419 M → 52 M，交给 CoreText 的段 774 → 18。11-24 的 #569 又发现每段中文要排两次（先按终端字号排，再按算出的比例重排），而同一字体的字形不随字号变，第二次只是把数乘上比例。改成只排一次、画的时候按比例放大，frames-scroll 39.41 → 26.54 M（−33%），13 个终端渲染夹具加一个中日韩混排夹具，新旧 PNG 逐字节相同。

05 从这些账里收出来的十条规则

每次修完，原因都写成一条规则放进性能文档第 4 节，改界面前先读。编号按加入的先后，R8 加在 R9 之前：

规则一句话来自哪次
R1窗格变化不要通知工作台，走 adopt_pane / pane_changed终端帧 7 倍（b1438ae）
R2侧栏要显示的状态，改动时要让工作台 notify，否则最多晚 1 秒缓存视图漏刷新
R3补画触发的那一帧必须设 asked，否则补画自己排补画坏版本 5 秒 15 次
R4每帧都要的派生值不在 render 里扫全部会话，按「revision + 当前秒」缓存frame_facts、额度、标签名
R5大列表不要放进横向 flex，它会把整张列表多量一遍整窗 75 → 130 M（348d005）
R6每帧按 id 查的表用 FxHashSipHash 曾占终端帧约一成
R7动了渲染要在真机跑门禁；基线只在真机、有意时改，并写原因虚拟机写不了基线
R8一小块要连续动时，放进单独的小视图，页面当缓存视图动画卡片 79 → 12 M
R9每行都有的元素少套靠内容撑开的容器，高度已知就写死整窗 105 → 57 M
R10对全部会话的过滤先判便宜的条件，循环里要查的表先收成集合238 → 61 M

不用 Fibo，自己的项目也能这样做：在 macOS 上，系统自带的 /usr/bin/time -l 会打印退休指令数，不用装任何东西（11-28 在 macOS 上跑过）：

/usr/bin/time -l ./your-bench 2>&1 | grep 'instructions retired'
#   34227777414  instructions retired

# 想看同样的活在能效核上：CPU 时间涨几倍，指令数基本不动
taskpolicy -b /usr/bin/time -l ./your-bench

# 想看按时间分布的计数，用 Instruments 的 CPU Counters 模板录一段
xcrun xctrace record --template 'CPU Counters' \
    --output run.trace --launch -- ./your-bench

程序里自己读，就是上面那段 proc_pid_rusage(pid, RUSAGE_INFO_V4, …) 取 ri_instructions，帧前后各读一次相减。三件事比工具重要：读数为 0 时当「无法测量」处理，不当通过；在 GitHub 的 macOS 机器上它就是 0，要准备一个同进程比例之类的退路；每加一项检查，先做一个坏版本确认它真的会红。Linux 上对应的计数是 perf 的 instructions:u（rustc-perf 的默认指标），这次没在 Linux 上跑。

06 11-28 实测

写这篇时，我们在一台 Apple Silicon 的 Mac 上把门禁完整跑了 6 次（11-28 01:39–02:00，同时有别的 Agent 在编译，1 分钟负载 30–151）。两个构建交替跑：新是当天的 main（441231a2），旧是写下现行 frames-scroll 基线的那次合并（34ca0380，#569）。两者都用 cargo build --release -p fibo-host -p fibo-app --features fibo-app/visual-test 编，再跑 python3 scripts/perf-gate.py target/release。

表里是每帧（或每次）的指令数，括号里是相对基线的变化。同期的 CPU 时间：终端帧 0.35–0.42 ms，整窗重画 2.86–3.17 ms；pane-share 六次都在 0.11–0.14 之间，基线 0.12。从这张表能读出四件事：

  • 同一台机器上，指令数很稳：新构建三次的整窗重画在 39.52–39.71 M 之间（差 0.5%），旧构建两次 40.08 / 40.11 M。CPU 时间这次没有拉开 2.5 倍（2.86–3.17 ms），负载数字本身不说明进程被排到了哪类核上，所以 CPU 时间稳不稳要碰运气，指令数不用。
  • 指令数不能跨机器比：写下 26.55 M 基线的那份代码，在这台机器上读 30.33 M，高 14%；首次打开插件页高 26%。两项都主要花在系统的 CoreText 排字和字形栅格化上，系统版本和硬件不同，这部分指令数就不同。终端帧和整窗重画大部分是 Fibo 自己的代码，反而低了 3–10%。所以基线只在同一类机器上有意义，这台机器上的「红」不能直接算成回退。
  • 新旧之间真实的差别很小：同一台机器、交替跑，滚一行中文从 30.33 / 30.34 M 到 31.07–31.75 M，中位数涨 3.6%，在 15% 线以内；其余 21 项的中位数变化都在 ±2.1% 以内。
  • 虚拟机模式看不到这些：设 MOORING_PERF_NO_COUNTER=1 后，所有指令数读 0，门禁只查比例，pane-share 0.12、theme-share 1.06 都在线内。上面那些 +14% 到 +33% 在这条路上一个都不会报。

还有一个顺带看到、没查原因的现象：新构建的 4 次运行里有 2 次（含模拟虚拟机那次），探针在设置 › 插件页断言「缓存的面板和强制刷新的不一样」后退出；旧构建 2 次都没有。这类按像素的检查在虚拟机上也会报，所以它要么是新出现的偶发 bug，要么是这台机器在高负载下的时序问题，需要单独复现。

限制：还没测到的

  • 虚拟机上的缺口：CI 只有比例检查，线在 2 倍。文档记录的正常 cardplay-share 是 0.17–0.19（11-27 那次 CI 是 0.23），变慢两倍以内会漏过。只有真机的 15% 指令数线拦得住，这要靠 R7 让改渲染的人自己跑。
  • 基线绑在写它的那类机器上：现行基线是在另一台 Mac 上写的。11-28 在这台机器上，同一份代码的滚一行中文高 14%、首次打开插件页高 26%，主要是系统排字库的差别。换一台开发机，要先用同一份代码重写基线，才能拿 15% 的线判断回退。
  • 门禁不是必过项：合并只要求 Workbench Rust checks。门禁红了不会挡住合并，要靠人看。
  • 第一次打开设置：读冷文件，同一版本 9–12 M，波动太大没法设线。只有第一次变慢（实测多 4 M）门禁不报，只能从日志看。
  • 显卡和合成器的开销：指令数只数 CPU。背景图和半透明主题让 WindowServer 多花多少 GPU，11-05 测过一轮，当时有别的会话在开窗口，没有结论。
  • 真实窗口的日常 CPU：11-20 之后那批优化合入后，安装版在日常负载下的窗口 CPU 没有干净的前后对照，几次采样都碰上锁屏、编译或刚重启。
  • 后台进程：fibo serve 按每行日志的指令数断言（≤ 100 万），但这一项没做过坏版本测试。
  • 只有 macOS：门禁只跑在 macOS 上，Windows 版窗口还没有对应的门禁。

总结：三条做法

  • 先换尺子：同一帧 CPU 时间随负载差 2.5 倍，退休指令数差不到 1%。门禁按指令数设 15% 的线，读不到指令数的虚拟机退到同进程比例（2 倍线），并把读数为 0 当作「无法测量」。
  • 再拆成本：「去掉一块量一次」找到侧栏占终端帧 88%、一行约 1.6 M；缓存视图和少套一层容器让终端帧从 74.3 M 到 4.52 M、整窗重画从 11-16 的 105 M 到 41.32 M（4.52 M 和 41.32 M 是现行基线）。
  • 门禁也要被测：每加一项先做坏版本（+666%、+544%、+48.5% 都被拦下），帧数、像素、CoreText 段数按次数断言，优化之后把基线跟着降下来，不让 15% 的线悄悄变成 40%。
上一篇关掉窗口、更新 App，终端都不断：Fibo 的常驻后台和终端交接下一篇不改 Agent，Fibo 怎么知道它在等你
