不改 Agent，Fibo 怎么知道它在等你

Claude Code、Codex 停在审批框上时，不会通知任何人。会话日志、Hook、屏幕、程序上报和进程这五个来源各有盲区，单看哪一个都会判错。Fibo 把五路证据按固定顺序叠到同一张会话卡片上，只在 core 的 status::of 一处算出状态，再用一个按文件计数的测试防止别处另算一遍。

Fibo 是什么：一个给 Claude Code、Codex 这类 Coding Agent 用的原生工作台，开源（MIT）。Agent 跑在 Fibo 开的真终端里，Fibo 在侧栏、看板、菜单栏和手机上告诉你哪个会话在等你。安装：下载 DMG，或 brew install --cask majiayu000/tap/fibo。

01 问题：「在等你」没有接口

同时开五六个 Agent 时，最费时间的是挨个翻标签，看谁停在审批框上、谁已经答完了。要让工作台替你看，它得知道每个会话此刻在干什么。

Agent CLI 没有为此留接口。Claude Code、Codex 不会主动向别的程序报告「我停在审批框上了」，Fibo 也不改它们的模型和循环，只在真终端（PTY）里原样运行它们。能用的只有它们本来就会留下的痕迹：写到磁盘上的会话日志、用户可以选装的 hook、终端里画出来的字、程序打印的转义序列、操作系统里的进程。

Fibo 给每个会话算出一个状态，一共 10 种。词、符号和归组都由 crates/fibo-core/src/status.rs 里的 Status 定义，别处不再拼写：

状态什么时候要你处理响铃
◐ 在跑一轮正在进行，或回合结束但后台任务、子 Agent 还在替它干活否否
◆ 等你回答审批框、提问、计划确认停在那里是是
✕ 出错了回合报错，或终端进程非零退出是是
◇ 等你验收这一轮结束了，做没做完由你看是否
◔ 等后台回合结束，只剩定时唤醒或监视任务，之后会把它叫醒是否
○ 新开的Agent 开着，还没开始第一轮否否
‖ 停下了你中断了，或 Agent 没结束就走了否否
◷ 稍后再看你推迟到某个时间否否
· 很久没动超过设定天数没有动静否否
✓ 做完了你标记完成或放弃否否

「要你处理」是一组状态：等你回答、出错了、等你验收、等后台 4 种（Status::needs_you）。其中只有前 2 种会响提示音、把计数标成橙色或红色（Status::blocked），因为 Agent 没有你就走不下去。这条在 11-03 定下，之前侧栏数 4 种、顶栏和看板只数 2 种，同一时刻会出现「要你处理 5」和「要你处理 2」。

02 五个来源，各有盲区

后台进程 fibo serve 持有所有终端，替每个会话收集下面五路证据。单看哪一路都会判错，所以五路都要。

来源能看到什么多快靠得住的地方什么时候失效
会话日志
~/.claude 的 jsonl、Codex 的日志等		一轮开始、结束、中断；说了什么、调了哪些工具。聊天内容全从这里来文件变动时读CLI 自己写的记录，结束和中断写下了就是事实有些事答完才写：Claude 的提问框在回答前日志里没有；长会话只读到尾巴时，看不到这一轮的开头
Hook
可选装，Claude 装 6 个事件		UserPromptSubmit 开始，PermissionRequest、Notification 在等，Stop 结束并列出后台 shell事件发生时就到审批、提问在日志写下之前就知道；Stop 带后台任务清单没装 hook 的电脑上全没有；继承了终端环境变量的别的进程也会发 hook（见 06）
屏幕
终端画面和标题		此刻弹着的审批框、选择题、计划菜单；标题里的转圈符号、画面上的计时行画面安静 1 秒后读一遍；有输出时每秒看一次计时行日志还没跟上时，只有它知道「现在」CLI 改了措辞或布局就认不出；窄窗口会把问句折成两行（见 06）
程序上报
OSC 7501		程序用一行转义序列说自己 working、blocked、done、error打印出来就到是程序自己的话，不是猜的要程序自己打印；脚本、构建加一行 printf 就有
进程
进程树、监听端口		回合结束后留下的后台 shell 还活着没有、开没开端口每 5 秒看一次能分出「会结束的任务」和「不会结束的服务」只能间接猜：看端口和时长，看不出命令的意图（见 05）

另有两个辅助信号只用来确认弹框：Claude 的 claude agents --json 和 Codex 共享守护进程的只读状态接口。代码注释写明它们可能比日志和 hook 都慢，所以只能结束或确认一次等待，不能开始或结束一轮（content/mod.rs 的 official）。

Hook 的写法也要防止拖慢 Agent。Fibo 写进 settings.json 的命令先把 stdin 读进变量，在后台转给 fibo hook，然后立刻 exit 0；超时设 5 秒，只用来兜住卡死的 shell。不在 Fibo 终端里时（找不到 Fibo 设的环境变量），这条命令直接退出，不影响 CLI。

03 叠加顺序：谁的话算数

五路证据先叠到同一张会话卡片（Content）上，不各自出结论。卡片记着回合在哪个阶段（turn）、后台还剩什么（background）、在等什么（waiting）。日志和 hook 写同一个解析器，形成底稿；后台每次把工作区发给窗口和手机之前，再按固定顺序把运行时的观察叠上去（host/snapshot.rs 的 overlay）。

这个顺序背后有三条原则：

  • 看到的只能加，不能减。标题在转圈，说明一定有一轮在跑，哪怕日志只读到了尾巴；标题不转，什么也证明不了，所以不能用它把「在跑」改成别的。
  • 此刻压过记录。画面上弹着审批框，而日志还没写到这一步，就先记成等你回答，并在卡片上写明「画面上的提示」，免得被当成日志里的记录。
  • 自己说的压过猜的。程序通过 OSC 7501 报了状态，就按它的来。但 idle 和 working 不开新回合：代码注释记着，Codex 在两轮之间会自己报几秒 working，真正的一轮很快就会出现在日志里。

叠完之后只剩一个函数做判断。下面是活着的会话那一支（简化，省掉了参数类型）：

fn live(w, s, c, now) -> Status {
    match turn {
        Turn::Waiting => return Status::Waiting,
        Turn::Running => return Status::Running,
        // 子 Agent 或它在等的任务还在干活：这一轮没完
        Turn::Completed if background.keeps_working() => return Status::Running,
        _ => (),
    }
    if let Some(d) = decided(w, s, now) { return d; } // 你标的完成、稍后再看
    if fresh(c) { return Status::Fresh; }
    match turn {
        Turn::Error => Status::Error,
        // 只有会把它叫醒的才算等后台；服务叫不醒任何东西
        _ if background.wakes() => Status::Background,
        Turn::Interrupted => Status::Paused,
        _ => Status::Review,
    }
}

注意顺序：你的决定排在「在等你」和「在跑」后面。你把会话标成做完了，Agent 又被你发的一句话叫起来，它仍然显示在跑；回合结束后，才轮到你的决定。

04 一轮结束是等你验收，不是做完了

Agent 说「全部完成」，不等于活干完了。所以回合结束只到「等你验收」，「做完了」只有你能标（11-02 定）。Agent 在回复里说做完了，只会把卡片上的下一步提示换成「按用户原话逐项核对机械证据，再决定是否验收」（completed_claim），状态不变。

分开「等你验收」和「做完了」有实际后果。等你验收的会话留在要你处理的计数里，按 ⌘J 跳到下一个，也可以进「逐个验收」一个个过：读 Agent 最后说了什么，再决定标完成还是打回去（留着服务的会话进不了逐个验收，因为它的回车会关掉终端）。如果回合一结束就算做完了，这一步就没了，没检查过的改动会混进做完的那一列。

05 服务不算在等：后台 shell 改了四版

最难判的是回合结束后还留着后台 shell 的会话。Claude 的 Stop hook 会列出还有哪些 shell，但不说它们会不会自己结束。有的会结束（测试、构建、CI 轮询），结束时 Claude 会被唤醒接着干；有的不会（http.server、中转、tail -f）。这条规则改了四版：

版本规则判错的情况出处
最早后台还有 shell 就算在跑开着 http.server 的会话一直转圈11-03 决定记录
11-03 下午只剩后台 shell 一律算「等后台」，进要你处理回合结束后还在跑的测试、构建被误报成要你处理1058984
11-03 晚上看进程树：监听固定端口（< 49152）或跑满 2 小时算服务，其余算任务；换边要连续两次（每次隔 5 秒）11-04 渲染脚本开给无头 Chrome 的临时端口；脚本自己起的固定端口中转3fb2791、1ab8b0f
11-07判定不变，判出服务后显示「等你验收」加一行小字「后台留着 1 个服务 · 端口 5569」（现行）决定记录 a-server-is-not-waiting

最后一版的起因是「等后台」这个词装了两件事：监视任务和定时唤醒真的会把 Agent 叫醒；常驻服务什么都不会带回来。用户看到 Codex 显示「等后台 · 1 时」，问它到底在等什么，答案是一个没人连的预览服务。所以现在只有会把 Agent 叫醒的才叫等后台，只留服务的回合就是结束了，状态是等你验收，服务写在小字里。

现行规则按顺序判断，第一条符合的算数（background_shells.rs 的 judge，节选）：

看到什么算为什么
宿主刚重启 2 分钟内，还没看过任务误报在跑几十秒，好过误叫你来处理
已跑满 2 小时服务兜底：任何猜错的情况都不会永远转圈
同一棵进程树里另一个进程连着树内的固定端口任务服务只是脚本的零件，脚本跑完会一起退出
监听固定端口（< 49152），连续两次看到服务它在等外面的人访问
只有临时端口（≥ 49152）或没有端口任务临时端口是工具给自己用的

试过但没用的做法：按命令文字猜（名字叫 relay 的，可能是常驻服务，也可能是脚本的零件）；外层是脚本就算任务（npm run dev 也包着一层）。每次判错都在决定记录的案例表和 known_cases 测试里各加一行，现在测试里有 13 个案例，改规则时任何一行都不能变红。

读屏规则因此写成数据，不写死在代码里：内置的 claude.json 有 3 条规则（审批、选择题、计划），codex.json 有 2 条，每条只挂在一个锚点行和它旁边的编号菜单上，形状不对就当没看到，不去猜。规则用保存下来的画面做测试：Claude 28 张、Codex 18 张，其中 19 张直接从真 CLI 录下，17 张是「看起来像但不是」的反例，比如已经答过的菜单、正文里提到的选项、输入框里自己打的字（11-28 数 crates/fibo-host/tests/fixtures/screens）。

不用 Fibo，自己也能拿到「停下来」的信号：Claude Code 的 hook 会在事件发生时运行你写的命令，并把事件的 JSON 从 stdin 传进来。下面这段写进 ~/.claude/settings.json，回合结束或请求权限时发一条系统通知（macOS 的写法；Linux 可换成 notify-send）：

{
  "hooks": {
    "Stop": [{ "hooks": [{
      "type": "command", "timeout": 5,
      "command": "osascript -e 'display notification \"这一轮结束了\"'"
    }] }],
    "Notification": [{ "hooks": [{
      "type": "command", "timeout": 5,
      "command": "osascript -e 'display notification \"在等你\"'"
    }] }]
  }
}

stdin 里有 hook_event_name、session_id、transcript_path，Notification 还有 notification_type（例如 permission_prompt）。两点经验：命令要立刻返回，慢的活放后台；Stop 只说明这一轮结束了，后台 shell 还在不在要另外看（Stop 的 JSON 里 Claude Code 2.1.317 起有 background_tasks）。

07 只在一处判定：用测试守住

五路证据叠起来已经够复杂，如果每个界面再各算一遍，结果一定对不上。Fibo 的前身仓库就是这样：「统一状态词」这件事手工修过 4 次，每次过一阵又分叉（docs/single-source，11-03 翻了老仓库 697 个提交）。11-03 的两轮只读审计又找出 78 条同一件事有两个来源的地方，例如：

  • 桌面显示「出错了」或「等你验收」，手机和 fibo list 显示「空闲」，fibo wait --until idle 碰到出错也照样返回。原因是宿主对外的接口只读 turn 自己拼了一遍。
  • 菜单栏写死「出错」，主窗口是「出错了」。
  • 手机写「干活中」，桌面写「在跑」，状态栏写「工作中」。

手工统一会回退，所以改成让机器守，分两步：

  1. 让编译器列名单。把关键字段临时改成 pub(crate)，编译器报出 core 以外 420 处直接读写，其中观测层写入约 200 处（合理），做判断的读取 146 处。这些读取逐个改成调 core 的出口：status::of、Status::label、status::needs_you、session_title、session_updated。
  2. 用棘轮防回退。Rust 分不清读和写，字段没法一直不可见，所以 crates/fibo-core/tests/guard.rs 用正则按文件数两类东西：core 之外读原始字段（.turn、.background、.turn_started 等），和 status.rs 之外手写的状态词（含走样的「出错」「工作中」「干活中」「空闲」「需要你」）。数目和 tests/guard-baseline.txt 不一样就失败，多了少了都要改这个文件，审查时看得见。

11-28 实测：在 fibo-host 的一个文件开头加一行读 c.turn 并返回 "在跑" 的函数，跑 cargo test -p fibo-core --test guard，失败信息是（第一行括号里的提示省略了）：

raw reads or hand-written state words changed (...):
field turn	crates/fibo-host/src/pictures.rs: new, 1
word 在跑	crates/fibo-host/src/pictures.rs: new, 1

同样一行加在文件末尾的 #[cfg(test)] mod tests 后面就不会被数到，因为守卫把行内测试模块之后的部分当测试代码跳过。

基线也会涨。从 git 历史里把每个版本的基线加总（11-28 实测，git log --first-parent 上动过基线的 52 个提交）：

类别11-03 第一版基线11-26 最新基线变化
手写状态词8068−12
core 之外读原始字段6670+4（最高 80）

状态词降得最多的一次是 11-03 把「要你处理」合成一组，一个提交少了 9 处。原始字段读取涨过几次，比如 11-06 让 Codex 的后台命令也分任务和服务，涨了 5 处。守卫不禁止涨，它让每一次涨都写进提交、经过审查。

守卫只防「另起炉灶」，不验证结果一致。另有 tests/one_owner.rs：用一份覆盖 16 种状态和命名情况的样例，断言标签和侧栏同名；再跑 200 组随机操作（改标签名、改侧栏名、同一终端新开对话、标记完成），每一步检查名字和状态只有一个答案。宿主的 fibo list、手机卡片、插件事件也逐字段对照 core 的结果。

限制：还没做到的

  • 读屏跟着 CLI 的界面走。11-25 新版 Codex 把提问改成先发一个不等回答的问题再 sleep，电脑和手机都显示在跑，手机没有提问卡片。这一条记下了，还没修。
  • 没装 hook 时更慢也更容易错。审批、提问只能靠读屏，要等画面安静 1 秒；CLI 改了措辞就认不出，直到加规则。
  • 不在 Fibo 终端里的会话只能读日志：一条「在跑」的日志 15 分钟没动就不再算在跑，在等你的问题也没人能替你按键。
  • 后台 shell 靠猜。不监听端口、又永远不结束的程序要等满 2 小时才算服务；进程树里互相连接的常驻服务会被当成任务。
  • 守卫是正则。先把字段存进变量再读、换个写法拼状态词，它都数不到；它只能让最常见的写法回不来。
  • OSC 7501 要程序配合。最可靠的「自己说」这一路，现在主要给脚本和构建用，Agent CLI 打不打印由它们自己决定。

总结：三条做法

  • 五路证据叠在一张卡片上，按固定顺序：日志和 hook 打底，再叠进程、画面、程序上报 4 步；画面只往「更忙」或「在等」改，程序自己说的压过猜测。
  • 状态只在一个函数里判：10 种状态、4 种算要你处理、2 种响铃，都由 status::of 和 Status 给出；编译器列出的 420 处直接读写改完后，由守卫按文件计数，手写状态词从 80 处降到 68 处。
  • 每次判错留一个案例和一个测试：后台 shell 规则改了 4 版，测试里有 13 个案例；读屏规则有 46 张保存的画面，其中 17 张是反例。
上一篇Fibo 的性能门禁：数退休指令而不看 CPU 时间，以及侧栏重画这本账下一篇Fibo 的终端为什么不用 Tauri + xterm.js：一轮测评后换成 GPUI + libghostty-vt 原生绘制
