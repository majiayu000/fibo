关掉窗口、更新 App，终端都不断：Fibo 的常驻后台和终端交接

终端开在窗口进程里，关掉窗口或更新 App 就会挂断里面跑着的 Agent。Fibo 把终端放进后台常驻进程 fibo serve，换新版本时，旧后台用 SCM_RIGHTS 把每个终端的 PTY 文件描述符和画面快照交给新后台，新后台回「taken」之前任何一步失败都由旧后台继续服务。常驻也带来一类新坑：一把锁、一次 sendmsg 报错、拉起它的环境，影响的都是所有终端。

Fibo 是什么：一个给 Claude Code、Codex 这类 Coding Agent 用的原生桌面工作台，开源（MIT）。正式版是 macOS，Windows 和 Ubuntu 有预览版。安装：下载 DMG，或 brew install --cask majiayu000/tap/fibo。前两篇讲了跨机终端和远程贴图，这篇讲它们共同的地基：终端住在哪。

01 终端为什么要住在窗口外面

普通的终端 App 自己持有每个终端的 PTY 主端。App 一退出，主端被关闭，内核给终端里的进程发 SIGHUP，shell 和里面的 Claude Code 跟着退出。跑了半小时的 Agent，会因为关错一个窗口、或者装一次更新就没了。

Fibo 把终端放进一个后台常驻进程 fibo serve。窗口进程 fibo-app 启动时如果找不到后台，就拉起一个：用 setsid 让它脱离窗口的会话，标准输入接空，错误输出写进 host.log。之后窗口只通过一个 Unix socket（workbench.sock）和后台说话，它手里没有任何 PTY。终端的画面状态也在后台：后台用 libghostty-vt 解析输出，窗口连上时先拿一份画面快照，再接着收增量。

发生了什么终端在窗口进程里Fibo：终端在 fibo serve 里
关掉窗口、退出 App主端关闭，SIGHUP，Agent 退出后台不受影响；再打开时拿快照接着显示
App 崩溃同上同上
更新 App先退出，所以同上新后台接过所有终端（下一节），进程号不变
后台本身退出不适用所有终端断开。所以后台要尽量不退出（第 05 节）
重启电脑全没了终端进程也没了；能做的是把被打断的会话恢复成同一段对话

窗口重新打开时，先跟后台握手（Hello），后台报上自己程序文件的指纹：文件内容的 FNV-1a 哈希加长度。和窗口旁边那份后台程序一样，就直接连上；不一样，就说明后台还在跑旧代码。这时有两条路：停掉旧后台再起新的，所有终端断开；或者让新后台把终端接过去。Fibo 走第二条。

02 交接：以「taken」为界的四个阶段

要让终端不断，新后台必须拿到同一个 PTY 主端，而不是新开一个。Unix 上进程之间传文件描述符的标准办法是 Unix socket 上的 SCM_RIGHTS 控制消息：内核在接收方进程里新建一个指向同一个打开文件的描述符。旧后台把每个终端的主端 fd 发过去，新后台拿着它读写，shell 和 Agent 看不出任何变化。

光传 fd 还不够。屏幕上现在是什么、光标在哪、终端标题，这些在旧后台的内存里，所以旧后台还要发一份画面快照。难点在于顺序：旧后台什么时候可以放手。放早了，新后台万一起不来，终端就没人持有了。Fibo 的规则写在 docs/plan.md 第 5 条：交接两阶段，Prepare → READY → COMMIT → SERVING，READY 之前失败，旧宿主继续服务。代码里，分界点是新后台回的一帧 ACK "taken"。

阶段谁做什么超时这里失败会怎样
0 启动窗口带 --takeover 拉起新后台；新后台先查 workbench.sock、.sock-start 两个位置是不是本用户的 socket窗口等 20 秒新后台退出，窗口提示「新后台没能接手终端，旧后台照常运行」
1 Prepare新后台连上旧后台，发 Hello、Handoff。旧后台等每个终端已接受的输入写完，然后锁住所有终端，发终端清单和每个终端的画面快照等输入 10 秒；新后台读 15 秒连接断开，旧后台放开锁，照常服务
2 READY每个终端的快照后跟一帧 READY；最后一条消息用 SCM_RIGHTS 带上所有主端 fd。新后台还原画面、打开数据库、在 .sock-start 上监听（还不公开）发 fd 等 10 秒新后台不回 ACK、直接断开；旧后台读到断开，恢复输入，照常服务
3 COMMIT新后台回 ACK "taken"；旧后台 exit(0)，不给终端里的程序发任何信号旧后台等 ACK 10 秒等不到 ACK 就算没交接，旧后台继续服务
4 SERVING新后台等旧后台放开 host.lock，接上每个终端的读写线程，把 .sock-start 改名成 workbench.sock等锁 10 秒终端会断。这一段只剩等锁、起线程和一次改名

旧后台这边的核心逻辑如下（简化过，去掉了错误处理细节）：

// 旧后台：锁着所有终端时发出快照和 fd
send(&mut stream, CONTROL, &Reply::Handoff { terminals })?;
for (_, live) in held.iter_mut() {
    for chunk in live.vt.snapshot()?.chunks(MAX_FRAME - 1) {
        write_frame(&mut stream, SNAPSHOT, chunk)?;
    }
    write_frame(&mut stream, READY, &[])?;
}
term::send_masters(&stream, &masters)?;          // SCM_RIGHTS
match read_frame(&mut stream) {
    Ok((ACK, taken)) if taken == b"taken" => std::process::exit(0),
    other => Err(io::Error::other(format!(
        "handoff not confirmed, still serving: {other:?}"))),
}

几个细节：

  • 旧后台退出时不关 fd、不发信号。新后台已经持有每个主端的副本，旧后台的副本随进程消失，终端没有经历「主端全部关闭」那一刻。
  • 新后台在 ACK 之前就把能出错的事做完：还原每个终端的画面、打开 SQLite、读出工作区、建好监听 socket。只有必须等旧后台退出才能做的（拿 host.lock）留在 COMMIT 之后。
  • 先绑 .sock-start，最后才改名。bind 在 listen 之前就建出了路径，直接绑 workbench.sock 会让窗口连上一个还没准备好的后台。
  • 一条消息最多带 200 个 fd（MAX_FDS），一个后台不会开到这么多终端。

失败路径有三条注入测试守着，都起真的 fibo serve 和真 PTY：在 .sock-start 位置放一个普通文件（新后台必须起不来，旧后台的 shell 进程还活着）；在数据库里预先建一张格式不对的表（新后台在 ACK 前报错，旧后台的终端还能收输入、出输出）；用一个代理把画面快照的第一个字节翻转（新后台不能回 ACK）。

真实换包的记录：11-03 一次换包，交接 8 个终端，进程号不变（docs/plan.md）。Windows 的 ConPTY 交不出正在运行的控制台，所以 CAN_HAND_OVER 在 Windows 上是 false：有终端在跑时窗口继续用旧后台，提示「后台有更新 · 重启」，由人决定什么时候重启（PR #230）。Ubuntu 预览版走和 macOS 同一套交接代码，Linux 的 CI 也跑这组用例，但还没在真机桌面上换过包。

03 自动更新走同一条路

应用内更新只负责换 App 包，不另写一遍交接（docs/decisions/2026-11-08-self-update.md）。顺序是：

  • zip 下到缓存目录，对 SHA256SUMS；解到正在运行的包旁边的隐藏目录；在那里查包标识、版本、codesign --verify --deep --strict、团队 ID、spctl --assess。
  • 全过才换包：旧包先改名成 .retired，新包放进原位，失败就改回去，再删旧包。任何一步失败都清掉解出来的和下载的，原 App 不动。
  • 换包后等当前进程退出，再启动新包里的窗口。新窗口握手时发现后台指纹和自己不同、而且后台能交接，就走上一节的 --takeover。

所以一次自动更新里有两道「失败就退回」：换包靠改名，原包在改名成功前一直完整；终端靠 ACK，旧后台在 ACK 前一直持有。不用把这两件事绑成一个事务。

04 带描述符的 sendmsg 会报 EMSGSIZE

11-03 换包后，新窗口一片空白。旧后台照常在服务，终端都还在，所以表面上只像窗口出了问题。原因是发 fd 的那次 sendmsg 报了 Message too long。交接失败在 ACK 之前，回滚按设计生效，新后台没起来。

原因在 macOS 的 Unix socket 上：发送方阻塞模式下发一条普通数据，对端缓冲区满了会等；带 SCM_RIGHTS 的消息碰到对端缓冲区快满时，不等，直接返回 EMSGSIZE。交接时，fd 那条消息紧跟在画面快照后面发，快照正好把新后台还没读走的缓冲区填满了。修法（edc88987）是把 EMSGSIZE、ENOBUFS 和 EWOULDBLOCK 当成「暂时没空间」：每 10 ms 重试一次，最多 10 秒。回归测试先写入 8192 字节不读，再发 fd，修之前必挂。

11-28 实测：边界不是 8192，是 8192 减去控制消息的大小

提交里写的是「对端缓冲区正好积满 8192 字节」。我们用一个小程序在本机（macOS 27.2，net.local.stream.sendspace 为 8192）把边界量细了：socketpair 建一对阻塞的流式 Unix socket，先写入 N 字节不读，再用 sendmsg 发 1 字节加 1 个 fd；读的一方 300 毫秒后才开始读。每个值跑 5 次，结果一样。

看起来规律是：剩余空间放得下控制消息、放不下数据时等；连控制消息都放不下时报错。我们没去对内核源码，这只是测出来的行为。它解释了为什么这个问题难碰到：快照有几 KB 到几十 KB，新后台边读边收，只有 fd 消息发出那一刻缓冲区里恰好剩不到 16 字节（一个终端时）才会出现。终端越多，控制消息越大，窗口越宽。测试用的程序（简化过）：

import os, socket, threading, time

def trial(unread, nfds):
    a, b = socket.socketpair()              # 阻塞的流式 Unix socket
    r, w = os.pipe()
    def reader():                           # 扮演新后台：300 ms 后才读
        time.sleep(0.3)
        got = 0
        while got < unread:
            got += len(b.recv(unread - got))
        socket.recv_fds(b, 1, nfds)
    t = threading.Thread(target=reader); t.start()
    a.sendall(b"\x07" * unread)             # 扮演还没读走的画面快照
    try:
        socket.send_fds(a, [b"\x01"], [r] * nfds)
        result = "ok"
    except OSError as e:
        result = os.strerror(e.errno)       # Message too long
        a.shutdown(socket.SHUT_WR)
    t.join()
    return result

同一天还查到 SCM_RIGHTS 的另一个性质：发送方给 fd 设了 FD_CLOEXEC，接收方拿到的新 fd 上没有（11-28 本机实测：发出去是 1，收到的是 0），macOS 又没有 Linux 的 MSG_CMSG_CLOEXEC。不处理的话，新后台之后起的每个程序都继承所有旧终端的主端，能往别的终端写输入，新后台崩了旧终端也收不到挂断。修法是收到后逐个 fcntl(fd, F_SETFD, FD_CLOEXEC)（24656b96）。

06 一把锁，卡住所有终端的输入

丢键（#371）

窗口原来给每个按键占队列里的一格，128 格满了就丢。后台那边每收一个键，先拿终端锁写进 PTY，再拿全局锁记一笔「用户在答话」，写完才读下一个键。全局锁每隔几秒会被会话关联占住 0.2–0.37 秒；终端里的程序一时不读输入时，写 PTY 也会等。两样叠起来，窗口的 128 格就满了。

没选「只把 128 调大」：后台照样每键拿一次锁，只是晚一点丢。最后的改法是窗口和后台共用一个按字节的队列：连着的输入合成一条（每条最多 16 KiB），新的窗口尺寸替换排着的尺寸，鼠标上报有积压就丢，积压过上限（窗口 1 MiB、后台 4 MiB）才拒绝。后台读 socket 的线程只入队，写 PTY 和拿全局锁在另一个线程，一批只拿一次锁。

长粘贴被截断（#443）

macOS 上每个终端的输入缓冲约 1 KB。一个忙着刷屏的程序（比如转圈中的 Codex）要等自己的输出被读走才回来读输入，而后台写输入时一直占着终端锁，读输出也要这把锁。两边互等，5 秒后写入超时，粘贴只进去前 1022 字节。复现用的是一个模仿 Codex 的单线程刷屏程序：塞 4000 字节，程序写输出被卡 5.0 秒，5.2 秒后报错。

考虑过两个别的办法：写的时候临时放锁、另加一把写锁，读输出的线程回复终端查询时还要等这把写锁，同样会互等；加大超时只是让卡住更久。最后每个终端一个写输入的线程，按顺序写，调用方在锁外排队等结果。

两次的共同点：单进程服务所有终端时，任何一处在锁里做慢事，卡住的不是一个终端，是全部。#371 之后的规则是「写 PTY 不在锁里」；交接时要锁住所有终端，所以 #480 先等输入写完，等的时候把锁放开，让读输出的线程继续工作。

07 后台继承了拉起它的人

11-16，从另一台 Mac 经 SSH 给一台电脑远程换包，执行的是 env -i … nohup fibo serve --takeover &。交接本身成功了，但之后在 Fibo 里新开的 Claude 全部显示 Not logged in。环境变量已经清干净，问题出在 env -i 清不掉的东西：

继承的东西决定什么SSH 里拉起shell 里 & 拉起env -i 清得掉吗Fibo 怎么查
环境变量PATH、语言等带 SSH 的那套带那个 shell 的能不查
登录会话（审计会话）能不能读登录钥匙串：Claude 登录态、gh、https 的 git、代码签名、插件密钥远程会话，读不到跟着那个 shell不能审计会话标志位
nice 值所有终端的调度优先级命令里有 & 时同样 +5zsh 默认 +5，普通用户调不回来不能（11-28 实测仍是 5）读 nice 值
隐私权限的责任进程系统弹窗写谁的名字、用谁的权限算到 sshd 名下算到那个终端程序名下不能系统的责任进程接口

还有两层放大。一是后台开的每个终端都继承后台的这些属性，交接也不改变它们：新后台接过的旧终端还在原来的会话里。二是窗口重新打开时，同一版本的后台会被直接复用（第 01 节的指纹比较），所以退出再打开 App 修不好；当时窗口里的「重启后台」按钮只在版本不同时出现。修的时候还犯了同类的错：从一个终端里用 & 重起后台，又带进了 nice 5，责任进程变成了那个终端程序。

#368 的做法：后台启动时读出这三样（getaudit_addr 的远程、图形会话标志位，getpriority，responsibility_get_pid_responsible_for_pid），写进 host.log，在握手里交给窗口。窗口只提示重启能修好的那些（后台有、窗口自己没有的），状态栏出现原因和「重启后台」，点了走 --takeover，终端不断；窗口自己也是从 SSH 启动的，就提示从程序坞重新打开。正确的远程换包做法写进了 docs/lessons.md：先按进程号退出旧 App，再用 open 打开新包，由窗口拉起后台。这三项检查目前只在 macOS 上有，其他平台什么都不报。

不用 Fibo 时，让终端活过窗口：tmux 是同一个思路，会话住在 tmux server 里，终端窗口只是客户端。

tmux new -s work          # 开一个会话，在里面跑 Agent
# 按 Ctrl-b 再按 d 分离；关掉终端窗口也没关系
tmux attach -t work       # 之后重新接上

tmux server 也是常驻进程，上面那张表同样适用。11-28 本机实测：在 zsh 里 tmux new-session -d … & 拉起的 server，nice 是 5；直接运行是 0；先 setopt NO_BG_NICE 再 & 也是 0。所以第一次拉起 tmux server 最好在本机图形会话的终端里、前台运行，别在 SSH 里或用 &。

限制：还没测到的

  • EMSGSIZE 的边界只在 macOS 上量过：Linux 没量。Fibo 的重试在两个平台上都生效，CI 在 Linux 上跑同一条回归测试。边界规律是测出来的，没有对照内核源码。
  • COMMIT 之后的那一段：等 host.lock、起线程、改名失败时终端会断。现有的三条注入测试都落在 COMMIT 之前。
  • 200 个终端一次交接：上限写在代码里，没有测过这么多终端时交接要多久。
  • Windows 不能交接：更新前要先结束 Fibo 里的终端。
  • 启动环境的三项检查只在 macOS 上：Linux、Windows 上后台被别的方式拉起时，窗口不会提示。
  • 3000 键改后的耗时：测试只断言小于 1.5 秒，没有记录实际值。
  • launchd：用 launchd 托管 tmux 或类似进程、让它在登录时就起来的做法，这次没试，所以没写进提示框。

总结：三条做法

  • 以一帧 ACK 为界：新后台回「taken」之前，旧后台一直持有所有 PTY 主端，Prepare、READY 两段任何失败都退回旧后台。三条注入测试守着这条线，11-03 那次 EMSGSIZE 就是被它兜住的。
  • 能先查的都挪到 ACK 之前：socket 位置、数据库、画面快照都在 ACK 前验证，ACK 之后只剩等锁、起线程和 1 次改名。自动更新的换包也是同一个思路，靠改名，失败时原包不动。
  • 常驻进程不在锁里做慢事，也不在错误的地方被拉起：按字节合并排队后，4000 字节粘贴从 5.2 秒报错变成 28 ms 到齐；后台启动时自检 3 项继承属性，env -i 清不掉的由窗口按原样重启。
