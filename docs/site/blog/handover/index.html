Close the window, update the app, keep every terminal: Fibo’s background host and terminal handover

A terminal that lives in the window process takes its running agent down when the window closes or the app updates. Fibo keeps terminals in a long-running host, fibo serve; on an update the old host passes each PTY file descriptor and a screen snapshot to the new host over SCM_RIGHTS, and any failure before the new host answers "taken" leaves the old one serving. Being long-running brings its own problems: one lock, one failed sendmsg, or how the host was started, affects every terminal at once.

What Fibo is: a native desktop workbench for coding agents such as Claude Code and Codex, open source (MIT). The release build is for macOS; Windows and Ubuntu have previews. Install: download the DMG, or brew install --cask majiayu000/tap/fibo. The previous posts covered terminals on other machines and pasting screenshots over ssh; this one is about what both rest on: where the terminals live.

01 Why terminals live outside the window

An ordinary terminal app holds each terminal's PTY master itself. When the app quits, the master closes, the kernel sends SIGHUP to the processes in that terminal, and the shell exits with the Claude Code inside it. An agent half an hour into a task is gone because someone closed the wrong window or installed an update.

Fibo keeps terminals in a long-running background process, fibo serve. When the window process fibo-app starts and finds no host, it starts one: setsid detaches it from the window's session, stdin goes to null, stderr goes to host.log. From then on the window talks to the host over one Unix socket (workbench.sock) and holds no PTY at all. The screen state lives in the host too: the host parses output with libghostty-vt, and a window that connects first receives a snapshot of the screen, then the changes.

A reopened window first greets the host (Hello), and the host reports a fingerprint of its program file: an FNV-1a hash of its bytes plus its length. If that matches the host program shipped next to the window, the window just connects. If not, the host is running old code, and there are two ways forward: stop it and start a new one, which ends every terminal, or have a new host take the terminals over. Fibo takes the second.

02 Handover: four phases, split at "taken"

For terminals to survive, the new host has to get the same PTY master, not open a new one. The standard Unix way to pass a file descriptor between processes is an SCM_RIGHTS control message on a Unix socket: the kernel creates a descriptor in the receiving process that refers to the same open file. The old host sends each terminal's master fd, the new host reads and writes through it, and the shell and agent notice nothing.

The fd alone is not enough. What is on screen, where the cursor is, the terminal title: those live in the old host's memory, so the old host also sends a screen snapshot. The hard part is ordering: when may the old host let go? Too early, and if the new host fails to start, nobody holds the terminals. Fibo's rule is item 5 of docs/plan.md: a two-phase handover, Prepare → READY → COMMIT → SERVING; on any failure before READY the old host keeps serving. In code the dividing line is one frame from the new host, ACK "taken".

The old host's side, simplified (error handling trimmed):

// old host: with every terminal locked, send snapshots, then the fds
send(&mut stream, CONTROL, &Reply::Handoff { terminals })?;
for (_, live) in held.iter_mut() {
    for chunk in live.vt.snapshot()?.chunks(MAX_FRAME - 1) {
        write_frame(&mut stream, SNAPSHOT, chunk)?;
    }
    write_frame(&mut stream, READY, &[])?;
}
term::send_masters(&stream, &masters)?;          // SCM_RIGHTS
match read_frame(&mut stream) {
    Ok((ACK, taken)) if taken == b"taken" => std::process::exit(0),
    other => Err(io::Error::other(format!(
        "handoff not confirmed, still serving: {other:?}"))),
}

A few details:

  • The old host exits without closing fds or sending signals. The new host already holds a copy of every master; the old copies vanish with the process, so no terminal ever sees all its masters closed.
  • The new host does everything that can fail before the ACK: restoring each screen, opening SQLite, reading the workspace, binding the listening socket. Only what must wait for the old host to leave (taking host.lock) comes after COMMIT.
  • Bind .sock-start first, rename last. bind creates the path before listen; binding workbench.sock directly would let a window connect to a host that is not ready.
  • At most 200 fds in one message (MAX_FDS); a host never runs that many terminals.

Three fault-injection tests guard the failure paths, each with a real fibo serve and real PTYs: an ordinary file where .sock-start goes (the new host must fail and the old host's shell must still be alive); a malformed table planted in the database (the new host errors before the ACK and the old terminal still takes input and prints output); a proxy that flips the first byte of a snapshot (the new host must not ACK).

From the record: one update on 11-03 handed over 8 terminals with their pids unchanged (docs/plan.md). Windows' ConPTY cannot pass a running console, so CAN_HAND_OVER is false there: while terminals run, the window keeps using the old host and shows "host update · restart", leaving the timing to the person (PR #230). The Ubuntu preview uses the same handover code as macOS and the Linux CI runs these tests, but no update has been handed over on a real Linux desktop yet.

03 Self-update takes the same road

The in-app updater only swaps the app bundle; it does not reimplement the handover (docs/decisions/2026-11-08-self-update.md). In order:

  • Download the zip to a cache folder and check it against SHA256SUMS; unpack it into a hidden folder next to the running bundle; there, check the bundle id, version, codesign --verify --deep --strict, team id and spctl --assess.
  • Only if all pass, swap by renaming: the old bundle becomes .retired, the new one moves into place (renamed back on failure), then the old one is deleted. Any failure removes what was unpacked and downloaded and leaves the original app untouched.
  • After the swap, wait for this process to exit, then start the window from the new bundle. Its greeting finds a host fingerprint that differs from its own and a host that can hand over, and takes the --takeover path from the previous section.

So one self-update has two fall-back points: the bundle swap relies on renames, and the original bundle is whole until a rename succeeds; the terminals rely on the ACK, and the old host holds them until then. The two never need to be one transaction.

04 sendmsg with descriptors can fail with EMSGSIZE

After an update on 11-03, the new window came up blank. The old host was still serving and every terminal was there, so it only looked like a window problem. The cause: the sendmsg carrying the fds had returned Message too long. The failure came before the ACK, the fallback worked as designed, and the new host never started.

It comes from macOS Unix sockets. A blocking sender writing ordinary data waits when the peer's buffer is full; a message carrying SCM_RIGHTS that meets an almost-full buffer does not wait, it returns EMSGSIZE at once. During a handover the fd message goes right after the snapshots, which had just filled the buffer the new host had not yet read. The fix (edc88987) treats EMSGSIZE, ENOBUFS and EWOULDBLOCK as "no room yet": retry every 10 ms for up to 10 s. The regression test leaves 8192 bytes unread, then sends an fd; it failed every time before the fix.

Measured 11-28: the edge is not 8192 but 8192 minus the control message

The commit says the peer's buffer held "exactly a full buffer" of 8192 bytes. We measured the edge more finely with a small program on macOS 27.2 (net.local.stream.sendspace is 8192): a socketpair of blocking stream Unix sockets, N bytes written and left unread, then a sendmsg of 1 byte plus 1 fd, with the reader starting to read after 300 ms. Each value was run 5 times with the same result.

8192 − 8176 = 16, exactly the size of a one-fd control message, CMSG_SPACE(4). With more fds, the first failing value moves down as the control message grows, every time at 8192 − CMSG_SPACE(4n) + 1:

The pattern looks like this: if the free space fits the control message but not the data, the send waits; if it cannot even fit the control message, the send fails. We did not check this against the kernel source; it is measured behaviour only. It explains why the bug is rare: snapshots run from a few KB to tens of KB and the new host reads as they arrive, so it shows up only when, at the moment the fd message goes out, fewer than 16 bytes (for one terminal) are free. More terminals mean a bigger control message and a wider window. The test program, simplified:

import os, socket, threading, time

def trial(unread, nfds):
    a, b = socket.socketpair()              # blocking stream Unix sockets
    r, w = os.pipe()
    def reader():                           # the new host: reads after 300 ms
        time.sleep(0.3)
        got = 0
        while got < unread:
            got += len(b.recv(unread - got))
        socket.recv_fds(b, 1, nfds)
    t = threading.Thread(target=reader); t.start()
    a.sendall(b"\x07" * unread)             # the snapshot, still unread
    try:
        socket.send_fds(a, [b"\x01"], [r] * nfds)
        result = "ok"
    except OSError as e:
        result = os.strerror(e.errno)       # Message too long
        a.shutdown(socket.SHUT_WR)
    t.join()
    return result

The same day turned up another property of SCM_RIGHTS: a sender's fd may have FD_CLOEXEC set, but the receiver's new fd does not (measured 11-28: 1 on the way out, 0 on arrival), and macOS has no MSG_CMSG_CLOEXEC like Linux. Left alone, every program the new host starts afterwards inherits every old terminal's master: it can type into other terminals, and if the new host crashes the old terminals never get the hangup. The fix sets fcntl(fd, F_SETFD, FD_CLOEXEC) on each one received (24656b96).

06 One lock, every terminal's input

Dropped keys (#371)

The window used to give each key one slot in a queue and drop keys once 128 slots were full. On the host, each key meant taking the terminal lock to write it to the PTY, then the global lock to note "the user is answering", and only then reading the next key. Every few seconds session matching held the global lock for 0.2–0.37 s; when the program in the terminal was not reading input, the PTY write waited too. Together they filled the window's 128 slots.

We did not just raise 128: the host would still take a lock per key and drop later. Instead the window and host share a byte queue: adjacent input merges into one item (up to 16 KiB each), a new window size replaces a queued one, mouse reports are dropped when there is a backlog, and only a backlog past the limit (1 MiB in the window, 4 MiB in the host) is refused. The host's socket-reading thread only enqueues; writing the PTY and taking the global lock happen on another thread, once per batch.

A long paste cut short (#443)

On macOS each terminal's input queue holds about 1 KB. A program busy redrawing (Codex with its spinner, say) only comes back to read input once its own output has been taken, while the host held the terminal lock the whole time it wrote input, and reading output needs that lock. Each waited on the other until the write timed out after 5 s, with only the first 1022 bytes of the paste in. The reproduction used a single-threaded redrawing program modelled on Codex: with 4000 bytes pasted, the program's output was stuck for 5.0 s and the send failed after 5.2 s.

Two alternatives were considered: dropping the lock during the write and adding a separate write lock fails the same way, since the output thread answering terminal queries would wait on that write lock; a longer timeout only makes the stall longer. The fix is one input-writing thread per terminal, writing in order, with callers queueing and waiting outside the lock.

What both share: when one process serves every terminal, anything slow done under a lock stalls not one terminal but all of them. Since #371 the rule is "never write a PTY under a lock"; the handover must lock every terminal, so #480 first waits for input to drain, with the locks released meanwhile so output keeps flowing.

07 The host inherits whoever started it

On 11-16 an update was pushed to a computer from another Mac over SSH, with env -i … nohup fibo serve --takeover &. The handover itself worked, but every Claude opened in Fibo afterwards showed Not logged in. The environment had been wiped; the trouble was in what env -i cannot wipe:

Two things make it worse. Every terminal the host opens inherits these from the host, and a handover does not change them: terminals the new host took over stay in their original session. And a reopened window simply reuses a host of the same build (the fingerprint check in section 01), so quitting and reopening the app fixed nothing; at the time, the window's "restart host" button only appeared when the builds differed. The repair repeated the mistake once: restarting the host from a terminal with & brought in nice 5 and made that terminal app the responsible process.

#368: the host reads these three at start (the remote and graphic-session flags from getaudit_addr, getpriority, and responsibility_get_pid_responsible_for_pid), writes them to host.log, and hands them to the window in the greeting. The window only offers what a restart would fix (issues the host has and the window itself does not): the status bar shows the reason and "restart host", which goes through --takeover so no terminal ends; if the window itself was started from SSH, it says to reopen it from the Dock. The right way to update remotely went into docs/lessons.md: quit the old app by pid, then open the new bundle and let the window start the host. These three checks exist only on macOS so far; other platforms report nothing.

Without Fibo, keeping terminals alive past the window: tmux works the same way; sessions live in the tmux server and the terminal window is only a client.

tmux new -s work          # open a session, run the agent in it
# press Ctrl-b then d to detach; closing the terminal window is fine
tmux attach -t work       # reattach later

The tmux server is a long-running process too, so the table above applies. Measured 11-28: a server started from zsh with tmux new-session -d … & runs at nice 5; started directly, 0; with setopt NO_BG_NICE before the &, also 0. So start the first tmux server in the foreground, from a terminal in the local graphical session, not inside SSH or with &.

Limits: what we have not tested

  • The EMSGSIZE edge was measured on macOS only, not on Linux. Fibo's retry applies on both, and the Linux CI runs the same regression test. The edge rule is measured, not checked against the kernel source.
  • The stretch after COMMIT: if waiting for host.lock, starting threads or the rename fails, terminals drop. All three fault-injection tests sit before COMMIT.
  • 200 terminals in one handover: the limit is in the code, but how long such a handover takes has not been measured.
  • Windows cannot hand over: end the terminals in Fibo before updating.
  • The three start-up checks are macOS only: on Linux and Windows the window says nothing when the host was started some other way.
  • The 3000-key time after the fix: the test only asserts under 1.5 s and records no value.
  • launchd: having launchd keep tmux or a similar process running from login was not tried, so it is not in the tip.

Summary: three practices

  • Split at one ACK frame: until the new host answers "taken", the old host holds every PTY master, and any failure in Prepare or READY falls back to it. Three fault-injection tests hold that line, and it is what caught the 11-03 EMSGSIZE.
  • Move every check that can run early to before the ACK: sockets, the database and the screen snapshots are verified before it, leaving only a lock wait, thread starts and 1 rename after. The self-update's bundle swap follows the same idea with renames, leaving the original bundle untouched on failure.
  • A long-running host does nothing slow under a lock and is not started from the wrong place: with byte-merged queues a 4000-byte paste went from failing at 5.2 s to arriving whole in 28 ms; the host checks 3 inherited properties at start, and what env -i cannot clear the window fixes by restarting it properly.
