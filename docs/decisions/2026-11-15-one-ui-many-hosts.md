# 一个窗口只有一套界面，每台电脑只是一个数据来源

**要支撑的决定：** 窗口里点另一台电脑的空间时，界面怎么组织，才能做到"把那台的状态拿过来显示，在这边操作那边"，而且切换流畅、性能好。

用户的话：「我点 agent OS 的空间，只是想打开 agent OS 的空间，我没有说要变成那样子」「首先有状态有数据，然后我们只是说把另外一台 Mac 的东西或者数据提取过来，然后在这边展示，并不是说要去改变什么东西」「怎么样的是一个最好的设计呢？最流畅的设计，性能最好的设计」。

这条接着 [2026-11-14 窗口用本机那套协议直连别的电脑的后台](2026-11-14-one-window-many-hosts.md)：连接和协议的决定不变，改的是它第 2、3 步在界面上怎么落地。

## Context

### 现在是什么样（2026-11-15 查过代码）

点侧栏里 agentos 的空间 her，会发生这几步：

1. 第一次点时，`ssh -L` 把 agentos 的后台 socket 转到本机，读它的整个工作区（`workbench/hosts.rs` 的 `show_host`）。
2. 新建一份**完整的工作台** `Workbench`，用的是和本机同一套代码。
3. 本机窗口的 `render` 一看选的是别的电脑，就把**整个窗口**交给这份工作台去画（`render.rs:15`），侧栏也包括在内。
4. 这份工作台连的是挂接的后台，`start_machines` 直接返回空（`workbench/machines.rs:20`），它以为只有自己一台，侧栏就画成单机样子：没有"本机 / agentos"分组，多出"只看 her""本机"小块、"更早""先不管 · 3 个空间"。

所以侧栏会整个变样，回来还得点"本机"或"← 本机"。

### 数据层其实已经对了

| | 现在 |
|---|---|
| 状态在哪 | 每台电脑自己的后台：空间、标签、分屏、会话、待办、终端内容 |
| 怎么拿过来 | 后台有变化就经状态连接推一个 revision，窗口落后了就要一次整个工作区（`Request::Workspace`，`workbench/mod.rs` 的 `sync`，连续多次合并成一次） |
| 终端画面 | 每个窗格一条自己的连接（`terminal/pane.rs`），远程的走同一条 `ssh -L` |
| 操作 | 作为请求发给那台后台，那台改完再推回来 |

这一层就是"把那台的状态复制过来显示，在这边操作那边"。出问题的是界面层：复制的不只是数据，而是**一整套界面**。

### 为什么当初复制了整套界面

`Workbench` 把"一台后台的数据"和"窗口界面"放在同一个结构里：`self.workspace` 被读 448 处，`self.store` 66 处，`self.layout.panes` 50 处，都默认只有一台。改成能同时读几台要动这些地方。提交 29932b42 的 Rejected 写了另一条路（同一个工作台里换掉 store 和 workspace）为什么不行：订阅、缓存和窗格都绑着一台后台，换了会串台。于是 12d9cea4 选了"每台一整份工作台"，侧栏跟着一起被复制了。

11-14 那条决定的第 2 步原本写的是"把 `store`、`workspace`、`layout.panes`、`nav` 收进按电脑分的结构"，实际落地时走了捷径。

### 每台电脑还连了两次

侧栏里 agentos 那一组不是从原生协议来的，而是经 `ssh agentos fibo remote --stdio` 用**手机协议**拿的卡片（`fibo_remote::protocol::Card`，`self.machines` 用了 54 处）。点进去以后，主区域又经 `ssh -L` 用原生协议再连一次。同一台电脑两条连接、两套协议、两份状态，侧栏和主区域看到的可能不是同一个时刻。

### 别人怎么做

| 产品 | 界面 | 数据 |
|---|---|---|
| WezTerm | 一个窗口一套界面；本机、SSH、远程 socket 各是一个"域"，不同域的标签可以并排放在同一个窗口 | 每个域自己的多路复用服务 |
| VS Code Remote-SSH、Zed 远程 | 本地一套界面 | 状态在远程服务端，和连本机走同一套协议 |
| Rex | 后台持有会话，窗口只是客户端，Mac 版用"Add Remote Host…"加别的电脑 | 官方文档没写一个窗口里怎么摆多台；兼容实现断线后按已收字节续传，不重新要整屏 |

没有谁给每台电脑复制一套界面。

## Decision

**窗口只有一套界面。每台电脑是一个数据来源，界面按需要读一台或几台。**

### 拆成两层

| 每台电脑一份（数据来源） | 每个窗口一份（界面） |
|---|---|
| `store`（连接、请求队列） | 侧栏：筛选、折叠、滚动位置、布局 |
| `workspace`（那台的整个工作区） | 鸟瞰、搜索、⌘J 的排序 |
| 那台的终端窗格（`layout.panes`） | 设置页、主题、字号、快捷键 |
| 那台上选的空间、标签和焦点（`nav`） | 偷看、状态栏弹窗、手机 |
| 按工作区算的缓存（额度、上下文、标签名） | 当前看的是哪台 |

本机就是第 0 台，和别的电脑走同一条路。

### 各部分读什么

- **侧栏**：读**所有**电脑的工作区，用和本机同一套规则（`status::of`、`session_title`、`status::needs_you`）按电脑分组。切到哪台都不变，只把选中的空间高亮。
- **主区域**（标签栏、分屏、终端、状态栏）：只读**当前那台**。点 agentos 的空间，当前那台就换成 agentos；点本机的空间就换回来。
- **鸟瞰、⌘J、搜索**：跨所有电脑，按同一套规则排序。
- **操作**：发给拥有它的那台。标签和分屏的操作给当前那台；看板上拖卡片、标完成给那个会话所在的那台。

### 流畅和性能

- **切换不碰网络。** 连上以后每台的工作区一直订阅着、留在本机，切换只是改"当前那台"。目标：点了以后下一帧就画好，`scripts/perf-gate.py` 不退。
- **一台一条连接，一套协议。** 侧栏也改读原生协议拿到的工作区，桌面不再为侧栏连手机协议（手机照旧用它）。
- **同步沿用现在的方式。** revision 推送加整个工作区一次拿，连续变化合并。先量 agentos 的工作区多大、一次要多久，慢了再改成只发变化的部分。
- **看不见的终端少花钱。** 不在当前那台、或者被挡住的窗格，先量它们在后台收画面占多少；占得多就停收，切回来按已收字节续传（学 Rex）。
- **打字。** 沿用 11-14 那条：回显 p95 超过 200 ms 才做本地预测回显。

**不做的：**

- 不把几台的空间合进一个工作区。每台的 id 各管各的，请求发给谁一眼就清楚，也不同步两台的数据。
- 不做跨电脑的分屏（一个标签里一格本机、一格 agentos），和 11-14 那条一致。
- 不改手机协议，也不改连接方式（`ssh -L`、挂接模式、版本规则都照 11-14）。

## Consequences

- 点哪台的空间，侧栏都不动，右边就是那台，操作和本地一样。
- 本机加的界面功能，远程自动就有；侧栏和主区域看到的是同一份状态。
- 每台电脑少一条连接，桌面里手机协议的那套侧栏、看板和偷看代码（`self.machines` 那 54 处）可以删掉。
- 要改的地方多：`self.workspace` 448 处、`self.store` 66 处、`self.layout.panes` 50 处，大多是机械地换成"当前那台"，侧栏和看板要改成遍历所有电脑。
- 窗口同时订阅几台电脑，后台常驻的连接和内存随电脑数增长。电脑数是个位数，可以接受。

## Implementation Plan

| 步 | 做什么 | 验收 | 估计 |
|---|---|---|---|
| 1 侧栏先不跳 | 保留现在每台一份工作台，但本机窗口一直画自己的侧栏，只把右边主区域交给那台的工作台画（给 `Workbench` 加一个只画主区域的入口）。侧栏里点本机的空间就换回本机 | `visual-check.py shots`：点 agentos 的空间前后，侧栏这一块一样；`scripts/hosts-evidence.sh` 照旧 PASS | 几小时 |
| 2 拆数据和界面 | 每台电脑一个数据来源（`store`、`workspace`、`layout.panes`、`nav`、按工作区算的缓存），`Workbench` 只留一份，记"当前那台"；删掉 `hosts.rs` 里每台一份的工作台 | 本机和 agentos 的空间来回点，两边的标签、焦点、分屏都在，切换不发请求；`scripts/perf-gate.py` 不退 | 3–4 天 |
| 3 侧栏、看板、⌘J 读各台工作区 | 侧栏和鸟瞰遍历所有电脑的工作区；桌面去掉 `ssh fibo remote --stdio` 和卡片摘要 | `crates/fibo-core/tests/guard.rs` 的读数只降；远程会话在看板里和本机一样能拖；每台电脑只剩一条 ssh | 2–3 天 |

第 1 步做完，你看到的样子就基本是最终的；第 2、3 步换的是底下的结构。第 1 步加的"只画主区域"入口，第 2 步拆完后由一套界面直接用，不算白做。

**要避免的写法：**

- 新代码不要再读 `self.workspace` 这种默认一台的字段；用"当前那台"或"那个会话所在的那台"。
- 不要按"是不是远程"分支画界面。本机就是第 0 台。
- 状态、名字、要你处理、时间这些照旧从 core 拿（docs/plan.md 原则 7），不为远程另写一份。

**改的时候要试旧的：**

- 那台的 Fibo 比这边旧（没有 `fibo socket`）：照 11-14，按旧版运行目录找。
- 那台断了：侧栏那一组留着最后的样子变淡，和现在一样；主区域在那台时提示断开，不清空。
- 第 1 步时只升级了一边：只有窗口在变，后台协议不变，没有兼容问题。

## Verification

```sh
# 第 1 步：侧栏切换前后一样
python3 scripts/visual-check.py shots <sha> /tmp/one-ui-shots
sh scripts/hosts-evidence.sh

# 第 2 步：切换不退性能（BIN_DIR 放 release + visual-test 构建的 fibo 和 fibo-app）
python3 scripts/perf-gate.py target/release

# 第 3 步：读数只降
cargo test -p fibo-core --test guard
```

真机：连 agentos 走一遍，本机 ↔ agentos 来回点 10 次，侧栏不跳；数一下 `ps` 里到 agentos 的 ssh 只剩一条。

## Alternatives

- **保留每台一整份工作台，只让那台的侧栏也列出所有电脑。** 否：两份侧栏的筛选、折叠、滚动位置要同步，切换还是换掉整个窗口，鸟瞰、搜索、设置这些窗口级的东西每台一份。只能修眼前这一处。
- **把几台的空间合进本机一个大工作区。** 否：id 会撞，一个请求该发给哪台要另外记，等于在本机同步两台的数据，违反"状态留在那台"。
- **侧栏继续用手机协议的卡片。** 否：每台两条连接、两套状态，侧栏和主区域可能对不上；本机加的规则还得在卡片上再写一遍。
- **直接做第 2 步，不做第 1 步。** 可以，但第 2 步要 3–4 天，这几天侧栏一直在跳。第 1 步几小时就能让你看到对的样子。

## 待定问题

| 问题 | 影响 | 最晚 |
|---|---|---|
| 本机窗口顶上的 `RPC receive reply: failed to fill whole buffer` 是不是整个工作区的回复被截断了？ | 如果是，第 2 步的同步方式要先修 | 第 2 步开工前 |
| agentos 的工作区一次多大、要多久？ | 决定要不要改成只发变化的部分 | 第 2 步验收前 |
| 看不见的终端在后台收画面占多少？ | 决定要不要停收、续传 | 第 3 步验收前 |
| 只能本机用的功能（在访达中显示、用编辑器打开）在别的电脑上置灰还是隐藏？ | 只影响菜单，沿用 11-14 的待定 | 第 2 步验收前 |

## 放弃条件

- 第 2 步三天收不住（换成"当前那台"后串台、缓存错位修不完）→ 停在第 1 步，第 3 步也不做。
- 第 3 步发现原生协议拿到的工作区在侧栏里刷新明显比手机协议慢（agentos 上侧栏状态变化晚于 1 秒）→ 先做只发变化的部分，做了还慢再考虑侧栏留手机协议。

## 后来的发现

- 2026-11-15 第 1 步做完（#349 侧栏不跳、#350 后台刷新断了重发且不留旧报错、#351 侧栏点亮正在看的空间），真 agentos 上 `scripts/hosts-evidence.sh` PASS。agentos 的工作区约 3 MB，经 ssh 一次 0.22–0.26 秒。
- 2026-11-15 顺序改成**先做第 3 步**：第 2 步要改读工作区 470 处、连接 80 处、窗格 56 处，外加 54 处异步回调和 34 处订阅，用户看不到变化；第 3 步不依赖它，每台电脑已经有一份自己的工作台，启动时就建好并保持订阅，侧栏和看板读它们的工作区即可。第 3 步做完再看第 2 步还要不要做。用户：「能不能先做第3步吧？」
- 2026-11-15 第 3 步做完：3a（#352）启动就连上各台；3b（#353）侧栏读它自己后台的工作区，拼卡片的规则挪进 `fibo_core::remote_cards`；3c（#354）在那台的主区域里，要你处理、⌘J、鸟瞰交给窗口；3d 桌面不再常驻手机协议连接：名字和 id 由找 socket 的脚本一起报，在线、重连（15 秒）和延迟走原生连接，拖卡片、＋、偷看、审批、关终端都经那台自己的工作台；加空间的目录列表仍要 `fibo remote` 的 `dirs`，只在表单开着时连一次，关了就断，不用为它改协议、也不用先更新那台。偷看那台的终端时，第一次打字照「点击接管输入」接管，打的字等新连接拿到画面再发。真 agentos 上每台只剩一条 `ssh -N -L`。
- 2026-11-16 网慢时打字卡：转发开了压缩以后，agentos 的工作区每变一次仍要整份（约 3 MB，压缩后约 0.8 MB）走同一条 ssh，在约 54 KB/s 的链路上一次占满 10 多秒，延迟显示 1765 ms。两处一起改，用户：「全都要做」。
  - **只发变化**：窗口的刷新、编辑和启动包成 `Request::Brief(上次那份的编号, 请求)`，后台按会话比对，只回变了的会话和内容（`fibo_core::workspace_delta`），其余小字段每次整份回，窗口自己改过的那份（拖分隔条的预览）不会留下来；`Store` 把变化拼回整份再交出去，界面代码没动。本机实测 1.6 MB 的一次刷新只剩 14 KB（压缩后 3 KB）。后台在状态里报 `brief`，旧后台收不到它看不懂的请求；窗口丢了底稿就重发一次要整份。
  - **限频**：另一台的刷新做完以后，再等它刚才用掉的那么久（最多 10 秒）才做下一次，链路至少一半时间留给打字；本机不等。
- 2026-11-16 两台窗口开着同一个终端：原来是先拿到输入的一直拿着，后开的只读，要点「接管」；改成 11-14 写的「后开的接管」：窗口打开终端时一律接管，另一边变「只读 · 点击接管输入」。偷看仍是只看，第一次打字才接管。
- 2026-11-16 换上只发变化以后实测 agentos：没有会话变的刷新仍有 352 KB（压缩后 81 KB），全是「其余小字段」：那台有 677 个终端（186 KB）、任务日志 81 KB、结果历史 66 KB。两分钟 12 次取，这些字段一次没变。用户：「继续缩」。加 `Request::BriefAll`：其余部分也按字段比，只回变了的字段，窗口把它们盖到后台上次发来的那份上（不是自己改过的那份，所以「自己的编辑不留下」照旧成立）。后台在状态里报 `brief_all`，旧后台照旧收 `Brief`；旧窗口发的 `Brief` 照旧拿到整份其余部分。没细到每个终端：终端列表只在开关终端时变，那时整块发一次够了。
- 2026-11-19 另一台的会话行改由本机行的 `flat_row` 画：它从那台在本窗口里的工作台读会话（状态、标题、第二行、子 Agent、改名框、提示），点击、右键、双击改名经那台的工作台做；另一台独有的只剩电脑标记、断开变淡、先不管的样子（`sidebar_machines/shared_row.rs`）。那台没有对应会话的终端（没关联对话的 Agent、带说明的 shell）和截图样例里只有卡片的电脑仍走卡片画法，等「列哪些行」也改读那台工作区时一起去掉。用户：「开工」。
