# 后台每次刷新只复制会变的；提交前的整份复制先留着

## 背景

用户问历史会话多是不是拖慢了 Fibo。真实安装的快照有 1540 条会话，其中 671 条是 Workflow 留下的子代理，只是在列表里藏起来了，仍然在快照里；后台内存里还有 5068 条（店里存着每条绑过的会话）。

11-04 量过一次整份快照约 26 ms、0.6% 个核，低于 1% 的放弃线，当时否定了增量同步。11-16 起回复改成只发变化（`011594cc`），11-17 内容哈希沿用上次的（`ef29d302`），但后台为了算出「变了什么」，每次仍要复制整份工作区、把每条会话写成 JSON 求哈希。

测试工作区里一个 Agent 每秒写 4 行日志（`scripts/perf-refresh.py`，量后台指令数，不经窗口）：870 条会话每次刷新 43 M 条指令，1541 条 73 M，内存再多 3500 条老会话 116 M。成本跟会话条数成正比。侧栏每帧只多 0.3–1.6%，不是问题所在。

## 决定

窗口的刷新（`Brief(Workspace)`）在后台的锁里直接对后台自己的内容算差异：只复制终端里当前会话的内容（叠加只改这些），其余借用原件比较，变了的才复制进回复。会话哈希像内容一样记住上次的。快照先挑出要发的会话再复制。到期检查先看有没有到期的，再复制工作区。

发出去的增量和原来逐字节相同（`host::brief_tests::a_refresh_on_the_hosts_own_content_is_the_delta_of_its_snapshot`），手机、另一台电脑和旧窗口不受影响。

结果：1541 条 73 M → 42 M（和原来 870 条一样贵），加 3500 条老会话 116 M → 63 M。

## 没做的

每处理一批日志，`Association::apply` 仍复制整份工作区（含老会话）、改完整份比较再提交，`Store::save_applying` 也整份比较。这是后台所有写入的通用做法（复制 → 改 → 提交），改成就地改或按条记账要动每一处写入，漏一处窗口就显示旧状态。测试工作区里它让 3500 条老会话每次刷新还多 21 M。等它成为大头（比如老会话再多几倍）再做，做时先列出所有写入路径。

不从快照里删子代理：只省一部分，搜索还要找得到它们，历史会话攒多了照样涨。

## 后续（同日）

内容改成共享（`Arc<Content>`，#449）、其余字段按字段比较（#450）之后，真实安装的工作区（1621 条会话、831 个终端）上一次刷新：后台 53.0 → 15.0 M 条指令，窗口套增量 62.4 → 18.5 M（`cargo run --release -p fibo-core --example refresh_bench`）。

「没做的」那条因此大半解决：`Association::apply` 的整份复制里内容只剩引用计数，在 C 组测试工作区（带日志写入）里从占后台 39% 降到 12%，剩下的是复制 5000 多条会话本身。继续去掉要改成就地修改加记账，即上面否掉的做法；后台每次刷新现在约 48 M，这部分全省也只有约 6 M，不做。增量里剩下的逐条比较同理，没变的内容按指针比，不做。

下一块在窗口：画界面（侧栏重排、终端帧）占窗口的六成以上，要在屏幕亮着时量真实窗口再定。
