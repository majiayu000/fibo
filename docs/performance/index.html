1. 现状一览

测试工作区：2000 个会话、8 个空间、60 个终端都绑了会话、侧栏约 45 行（scripts/perf-fixture.py，接近长期使用的真实安装）。单位是每帧退休指令数。

2. 怎么量

指标：退休指令数，不是 CPU 时间

同一个版本，在机器负载 6 和 40 时，CPU 时间能差 2.5 倍；退休指令数差不到 1%。所以对照实验、门禁基线都用指令数（proc_pid_rusage(RUSAGE_INFO_V4).ri_instructions）。新旧版本交替跑，至少各两次。

虚拟机读不到指令数。GitHub 的 macOS 机器是虚拟机，ri_instructions 恒为 0。任何按指令数的断言在 CI 上都必须有退路，否则等于永远通过（见 门禁）。

找大头的两种办法

  • 去掉一块量一次：临时让某块界面不画（例如 sidebar_view 返回 None），看指令数掉多少。侧栏占 88%、348d005 的侧栏 +50 M，都是这样量出来的。比猜可靠。
  • 二分提交：门禁报警后在单独的 worktree 里逐个提交编译、跑探针，几轮就能定位（348d005 就是这样找到的）。

sample 的自身时间如果集中在 taffy::compute_flexbox_layout、line_wrapper，问题在排版（元素太多或嵌套导致反复测量）；集中在 Workbench::render 下的业务函数和 SipHash，问题在每帧重复计算。

3. GPUI 重画机制要点

  • 根视图每次 draw 都渲染。cx.notify() 把这个实体和它所有祖先标脏。
  • AnyView::cached(style)：视图没被标脏、且边界/内容遮罩/文字样式不变时，直接复用上一帧的 prepaint/paint。
  • window.refresh() / refresh_windows() 无视缓存，整窗重画。切外观、样式、快捷键时用的是它。
  • 同一次 flush 里的 Notify 会去重，所以不能用「数通知次数」来区分谁通知的。
  • draw 过程中发出的 notify 只进失效集合，下一次 draw 开始时才生效，不会自己请求新帧。
  • window.on_next_frame 在窗口不在屏幕上（锁屏、离屏探针）时永远不会触发；设置 GPUI_PAUSE_IDLE_DISPLAY_LINK=1 时空闲不出帧。

4. 规则（写代码时）

R1 窗格变化不要通知工作台。新建窗格用 Workbench::adopt_pane，或在观察回调里调 pane_changed（它通知一个空的子视图 Tick，工作台照样重画标题栏和标签，但侧栏不重画）。
不要写 cx.observe(&pane, |_, _, cx| cx.notify())：终端每输出一次，侧栏就整个重排一次（终端帧会涨到 7 倍）。
R2 侧栏要显示的状态，改动时要让工作台 notify。侧栏是缓存视图（workbench/redraw.rs 的 SidebarView），只在工作台 notify 时重画；其他途径的变化最多晚 1 秒由补画追上。在 render 里改的状态（如 open_pending_route）通知不到侧栏，要在下一帧调 ask。
R3 补画触发的那一帧必须设 asked。否则补画会自己排下一次补画，空闲时也会每秒整窗重画好几次（坏版本 5 秒 15 次）。
R4 每帧都要的派生值不要在 render 里扫全部会话。按「工作区 revision + 当前秒」缓存，参照 workbench/frame_facts.rs（会话查找和各种计数，调试版每次取用都重算核对）、redraw::quotas（额度）和 redraw::tab_name（标签名）。代价是数据最多晚 1 秒。缓存键要覆盖所有输入：标签名的键包含整个 Tab，因为改名时会传入清空标题的标签。
R5 大列表不要放进横向 flex。横向容器要先量子元素的内容尺寸，taffy 会把整张会话列表（含文字折行）多量一遍。只有确实需要并排（机器竖栏）时才套横向容器。
R6 每帧按 id 查的表用 FxHash。Workspace.content 是 FxHashMap；SipHash 曾占终端帧约一成。键来自本机日志，不是网络对端挑的。
R7 动了渲染要跑门禁。本机：python3 scripts/perf-gate.py target/release（先编探针版）。性能确实变了且是有意的，用 MOORING_PERF_UPDATE=1 重写基线并在提交说明里写原因；只能在真机写，虚拟机写不了。

5. 性能门禁

CI 任务「Window performance gate」（.github/workflows/ci.yml），和 Rust 检查并行跑，单独编一份探针版 release，约 8 分钟。脚本 scripts/perf-gate.py，基线 crates/mooring-app/perf-baseline.txt。

检查失败条件拦的是什么
终端帧、整窗重画的指令数超基线 15%任何变慢（真机）
pane-share：终端帧 CPU ÷ 整窗 CPU超基线 2 倍（仅在读不到指令数时）CI 虚拟机上的退路。两个数同一进程前后量，机器快慢基本抵消：本机 0.11（frame_facts 之前 0.17，那时 CI 约 0.2），侧栏每帧重画时 0.96
逐像素重画任何一步有差异侧栏或其他缓存视图漏刷新
终端输出时侧栏保留上次绘制侧栏重画了违反 R1
补画自己那一帧又排的补画>0违反 R3。不数补画总数：CI 机器有屏幕会自己出帧，正常版本 5 秒也有 9–15 次补画

门禁自己也测过：三个故意做坏的版本都被拦下。通知整个工作台（指令数 +666%，侧栏每帧重画）；侧栏不跟着刷新（筛选、取消筛选、改名三步有像素差异）；补画循环（15 次自我触发）。改门禁时要重做这类坏版本测试，确认还能拦住。

比对前探针会先画一帧、等 50 ms：标签栏的溢出提示是按上一帧排版算的，16 ms 后补一帧（tab_overflow），这是设计内的晚一帧，不能当差异。

终端帧指令数是双峰的（约 6.3 M 和 7.0 M），基线取高的那个，避免误报。

后台：managed_session 的 four_agents… 按每行日志的退休指令数断言（≤100 万）；读不到指令数（虚拟机）时退回「增量 CPU ≤ 2% 一核」。

6. 门禁报警的排查流程

  1. 看是哪项：指令数、pane-share、像素、侧栏重画、补画自我触发。像素差异的两张图在 CI 产物 perf-gate 里。
  2. 本机先复现：编探针版，跑 perf-gate.py 两三次，排除双峰和噪声。
  3. 指令数涨了：二分提交（每个点只跑 probe … frames-main 或 frames-pane），定位到提交后再用「去掉一块量一次」缩小到具体视图，最后用 sample 看是排版还是计算。
  4. 像素差异：先判断是不是设计内的晚一帧（标签栏溢出）；否则检查新状态有没有在改动时让对应视图 notify（R2）。
  5. 修完：门禁本机过、像素一致，再推。有意的变化才改基线。

8. 踩过的坑

  • 用 CPU 时间做对照：同版本能差 2.5 倍，得出的结论不可信。改用指令数。
  • 测试数据太假：最早的测试工作区没有会话绑定终端，侧栏是空的，量不出问题。测试数据要接近真实：会话绑定终端、日志里有额度读数。
  • 屏幕锁了：没有显示链接，on_next_frame 不触发，真实窗口量不到 CPU；离屏探针才可靠。
  • 门禁在 CI 上空转：虚拟机指令数为 0，比较全是 −100%，「通过」是假的。读数为 0 必须当作「无法测量」处理，走退路。
  • 数总数而不是数因果：补画总数受「窗口会不会自己出帧」影响；要数的是 bug 的直接特征（补画帧又排补画）。
  • 把设计内的晚一帧当差异：标签栏溢出提示本就晚一帧，比对前要先让那一帧画出来。
  • 整理提交时 git reset --soft main：如果 main 已被其他会话推进，工作区相对新 main 会显得在撤销别人的改动。正确做法是 git rebase main，或从原起点导出自己的补丁再套用。
  • 测试文件超过 800 行：VibeGuard 只允许变短；改断言时要同时压缩周围代码。

9. 外部参考：大项目怎么做性能回归

项目做法拦 PR 吗
pandasasv 基准套件在专用机器上对每个合入的提交跑，事后用阶跃检测找变慢的提交并提醒不拦。官方说明同代码同机器结果也差得明显
uv / ruffCodSpeed：专用物理机量墙钟时间 + Valgrind 模拟模式（与机器负载无关），结果作为评论和检查贴回 PR（uv 的 .github/workflows/bench.yml，crates/uv-bench）可以
Rust 编译器（rustc-perf）默认指标 instructions:u，约 0.3% 的变化可稳定看出；每周人工看曲线判断人工判断
Zed（GPUI 来源）CI 只编译 benchmark crate，没看到性能门禁—

共同点：要拦 PR，就要用与机器负载无关的指标（指令数、模拟执行）；用墙钟时间只能事后提醒。Mooring 门禁按这个思路：真机用指令数，CI 虚拟机用同进程内的比例。
