# 手机端 Markdown：解析用 remark，渲染自己画

**结论（采用，2026-11-05）**：方案 B。解析用 `remark-parse + remark-gfm + remark-cjk-friendly`，界面继续用自己的 RN 组件。不用 Enriched Markdown，不用 WebView。

## 要支撑的决定

手机只做聊天，内容主要是 Claude Code 和 Codex 的回复。要决定的是：继续补原来的正则，还是换解析器，还是换原生库。用户的要求是最好的性能和最好的 UI。

## 现状有多坏（真实语料）

本机最近 21 天的日志，去重后 20,920 条回复，其中最终回复 6,446 条。复现：`cd mobile && bun run md:corpus`（只输出统计）。

| 最终回复 | 改前 | 改后 |
|---|---|---|
| 严重（表格原样、字符被吃） | 26.0% | 0 条 |
| 严重或中等（语法字符外露） | 31.4% | 1 条 |
| 含轻微（链接点不动、代码贴左） | 41.6% | 1 条 |

改前各项：表格 23.6%，本地链接点不动 13.8%，粗体或链接里的行内码露反引号 7.4%，下划线被吃 2.7%，裸网址 2.2%，HTML 外露 1.8%（Codex 17.7%，主要是 `oai-mem-citation`）。

「改后」偏乐观：基准和产品用同一个解析器。工具另用 marked 独立比对文字，20,920 条里 3 条不同。它只看文字，不看布局。

## 真机对比

OPPO PMA110（Android 16），release 包，Hermes。样本由 `mobile/bench/synth.ts` 合成，比例照真实分布（表格 24.9%，行内码 71.5%，粗体 67.4%，列表 71.4%），不含任何日志原文。每项冷启动 7 轮。

**解析（门槛：最长消息 ≤50ms，首屏 50 条累计 ≤150ms）**

| 项目 | 结果 | 门槛 |
|---|---|---|
| 11.7KB 消息，中位 / 首次 | 34.7 / 42.7 ms | 通过 |
| 50 条，真实比例（31% 最终），中位 / 最慢 | 56 / 70 ms | 通过 |
| 50 条，全部最终回复，中位 / 最慢 | 184 / 215 ms | **超线** |
| `**结论：**后面` | `<b>结论：</b>后面` | 正确 |

全部最终回复的这一项超线，但不等于首屏卡 184ms：列表首屏只画 8 条，其余分批解析，所以这个累计值不会一次发生。真实会话里最终回复约占 31%。

**首屏（ms，p50 / 最慢）**

| 场景 | A 旧正则 | B remark | C Enriched |
|---|---|---|---|
| 50 条真实比例，首个内容 | 35 / 50 | 46 / 83 | 36 / 51 |
| 同上，稳定 | 166 / 232 | 118 / 264 | 199 / 288 |
| 50 条全最终，首个内容 | 54 / 76 | 85 / 99 | 52 / 65 |
| 200 条真实比例，首个内容 | 35 / 47 | 44 / 88 | 35 / 45 |
| 同上，稳定 | 162 / 239 | 125 / 252 | 193 / 283 |

A 和 B 是最终版的数字。C 只和早一版 B 同轮测过（当时 B 是 53 / 83、131 / 288、86 / 139、46 / 74、135 / 271），之后 C 已移除，没有重测。首个内容 C 比 B 快约 9–34ms，这是 C 唯一明确领先的地方；稳定时间 B 反而更短。

**滚动**（200 条，连续快速滑动，每种 3 轮）

| 项目 | A | B | C |
|---|---|---|---|
| 掉帧比例（gfxinfo） | 0.06–0.19% | 0–0.15% | 0–0.15% |
| 大片空白（屏幕截图抽样，空白超过 35% 屏高的帧，B 为早一版） | 0 / 97 | 0 / 97 | 0 / 103 |
| 内存 PSS | 144–174 MB | 156–190 MB | 152–156 MB |

三者滚动看不出差别。空白按抽样统计，这台手机不让 shell 录屏，抽样率约每秒 1–2 帧。

**体积**：同一配置下，含 C 的 APK 47.5MB，去掉 C 后 38.0MB，C 多 9.5MB（已关公式和视频，保留代码高亮）。B 只加约 0.4MB（remark 和 JetBrains Mono NL）。

## 为什么选 B

- **性能打平**：C 的首屏优势在 9–34ms，滚动没有差别，而这个差距不足以抵消下面的代价。消息不长（P99 约 2,100 字），host 只记录完整消息，没有流式，所以原生库的主要长处用不上。
- **显示更对**：按这次测速用的样式配置，C 在这台手机上有列表项里的行内码丢了等宽字体和底色，换行的行内码底色铺到行尾（没有查是配置还是库的问题）。md4c 不认 `**结论：**后面`，要先改写文字；B 的解析器直接处理。
- **代价小**：不增加原生构建和 RN 升级绑定，少 9.5MB，渲染逻辑能在 `bun test` 和语料工具里跑。

代价也要写清：B 没有代码高亮，不能跨块选择。现在的做法是长按复制全文，再从「选择部分文字」进入可选的纯文本。

## 放弃条件

- 产品要做流式、代码高亮或跨块选择，重新评估 Enriched。T3 Code 用同样的 Expo 58 和 RN 0.88 跑它的 fork，所以它走得通。
- 真实会话里出现明显卡顿，例如 OPPO 上最长消息解析超过 50ms，或首屏累计超过 150ms。
- 语料工具里严重或中等损坏回到 1% 以上。

## 做了什么（都在 `mobile/src/ui/`）

- `md/parse.ts`：解析和缓存（最多 400 条）。没有 Markdown 字符的文本跳过解析器，remark 在第一次需要时才加载。过滤 `oai-mem-citation`。
- `md/table.ts`：表格列宽由文字估算，不用测量。放得下就铺满，放不下就横滑，单元格不会被挤成一列单字。
- `markdown.tsx`：表格、代码块（语言标签、复制、横滑、超过 30 行折叠）、嵌套列表、列表内代码、引用、任务列表。网址点了打开；本地路径点了复制路径；本地图片只显示说明文字。不需要横滑时不创建 ScrollView。
- `message.tsx`：`memo`，长按复制全文。
- `mono.ts`：打包 JetBrains Mono NL。旧版的「改前」截图能看到，OPPO 上系统 `monospace` 确实不等宽。

两个 Android 上的坑：`fontWeight: 600` 在中文字体上显示成常规，要用 700；打包字体继承粗体时会退回系统字体，所以行内码显式设回 400。

## 工具

- `mobile/tools/md-corpus.tsx`：语料差异，只输出统计，不写磁盘。`--synth` 用来核对合成样本的比例。
- `mobile/bench/`：测速页和合成样本。只有 `EXPO_PUBLIC_MD_BENCH=1` 才进包，已确认正式包和 `expo export` 产物里没有。`run.py` 用 adb 驱动，只操作测速包，前台不是它就停止滑动。
- 切换这个环境变量后 Gradle 仍可能复用旧 bundle（它不看环境变量）。打正式包前要先 `--rerun` 打包任务，并在 APK 里核对没有 `MD_BENCH`。这次差点把测速包内容打进正式包。

## 没验

- iOS 真机和模拟器上的显示（只验了 `expo export`）。
- OPPO 之外的 Android 机型。
- 表格横滑和长按在 iOS 上的手势。
- 复制路径和复制代码的真机点按（长按复制全文在真机上看到了）。
